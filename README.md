# ThermalPilot · Windows 温控与调频小工具

根据 CPU / GPU 温度闭环调节 **风扇 PWM** 与 **CPU 频率上限**，支持 **Intel CPU 降压微调**，并内置
**环境检测 + 多阶段压测标定 + 数据拟合生成曲线**。默认目标系统 **Windows 10 / 11（1607+）**。

面向两类人：
- **小白**：装好 → 点「环境检测」→ 点「自动标定」→ 选静音/均衡/性能 → 完事；
- **高手**：高级调参面板里逐点改曲线、切目标温度 PID 模式、开降压；或用命令行实验台 `tplab` 跑可控实验、自己做回归分析（见 `docs/MODEL.md`）。

## CPU 频率：和任务管理器对上的是哪个数

并排截图：本程序 **1164 MHz**，任务管理器 **3.59 GHz**（负载 3%），差 3 倍。

### 不是算错，是三个不同的量

| 量 | 公式 | 含义 | 空闲 3% 时 |
|---|---|---|---|
| 有效频率 | `ΔAPERF / Δt` | 墙钟平均，**把休眠摊进分母** | 1164 MHz |
| 醒着频率 | `基准 × ΔAPERF/ΔMPERF` | 只在 C0 内统计 | ≈3590 MHz |
| 瞬时倍频 | MSR 0x198 当前倍频 | 内核请求的 P-state | 3610 MHz |

任务管理器「速度」= `Processor Frequency` 计数器 = `%Processor Performance × 最高频率`，
而 `%Processor Performance` 就是 APERF/MPERF 的比率（MPERF 只在 C0 推进）——**就是第二个**。
证据：本机基准 2.81 GHz，显示 3.59 GHz，比率 1.278；3.59 不是任何整数倍频档（34/35/36/38），只能是平均值。

早期把主指标定为「有效频率」，是为了避免出现"1% 负载却 3.6GHz"这种看不懂的数，代价是它和任何系统工具都对不上。现在主数字用任务管理器同口径的「当前频率」，副标题另给有效频率。

### 口径

- **主数字 = 当前频率**（`C0Mhz`）→ 与任务管理器并排能对上；
- **副标题 = `有效 1164MHz · 轻载`** → 回答"实际干了多少活"，限制度保留；
- **悬浮 = 三个口径全列** + 芯片档位（单核 3800 / 全核 3400），避免"3587 > 全核上限"的困惑；
- `tplab perf` 同时打印「有效 xx（墙钟平均）· 醒着 xx（与任务管理器同口径）」。

一句话记住：**当前频率 = 跑多快，有效频率 = 真干了多少活。** 低负载时两者差 3 倍是正常的。

## CPU 温度突然跳一下：读数毛刺

### 结论先说

不是采样太频繁。**采样越慢只会漏掉尖峰，不会制造尖峰**——1 s 采样对 500 ms 的突发
已经有 50% 概率漏掉，放到 2 s 只会让偶发高点更容易被最后一帧撞上。

真机 707 行数据逐拍分析（`lab-data/lab-deep1-20261028-191903.csv`）：

| 统计 | 结果 |
|---|---|
| 孤立尖点（单拍偏离前后均值 ≥8℃） | **43 / 704 = 6.1%** |
| 单拍最大跳变 | **35.5℃** |
| 尖点"按 R=1.21 本该需要的额外功率"中位数 | **9.5 W** |
| 尖点处实测功率增量中位数 | **−0.5 W** |

最极端一次：

```
t=30.6s  47℃ → 85℃ → 52℃     功率 9.2W → 15.4W → 14.5W
```

涨 38℃ 需要额外 31 W，实测只动了 0.9 W —— **物理上不成立**。
判据只有一条且是物理的：温度涨 X℃ 必须有 X/R 瓦的功率跟着。没有，就是读数毛刺。

### 危害不只是"显示难看"

`CriticalTempC = 95℃`。同批数据里有 93℃ / 96℃ / 97℃ 的尖点，随便一次踩线就走超温分支：
PL1/PL2 压到 10/12 W、EPP=255、风扇 100%，下一拍掉回来又恢复 —— 游戏里就是**顿一下 + 风扇猛转**。

### 修法

新增 `Core/TempFilter.cs`（5 点滑动中值），显示、趋势曲线、PI、热阻估计、CSV 全部走滤波值：

- 中值而不是平均：平均会把 85℃ 摊进后面几拍（47/85/52 → 61），中值直接丢掉（→ 52）；
- 无效读数（≤1℃ 或 >125℃）不入窗口；窗口未满时取偏小的中位，启动那一两拍也不漏刺；
- **真机回放：尖点 43 → 5（6.1% → 0.7%）**，剩下 5 个全是真实阶跃（压测开始 / 掉载），没有被削。

超温保护加安全阀：滤波值越线 **且** 原始值连续 2 拍越线才保护；原始单拍已 ≥ 保护线+3℃ 立即保护。
代价是显示滞后 1~2 s，对风扇（3 s 写一次 EC）和 PI（τ_hs≈130 s）无影响。

### 可追溯

- 大数字 = 滤波值，悬浮提示给出「原始 xx℃ / 最热核心 xx℃」；
- CSV 新增 `CpuTempRawC`（`CpuTempC` 已是滤波值）；
- 新命令 `tplab tempcheck [--sec N]`：连续采样并当场判定每次跳变是「毛刺（功率不匹配）」
  还是「真实阶跃（功率同步）」。

## 温度口径：GPU 核心 / CPU 包温度 / 最热单核

把本程序和 OMEN Gaming Hub 并排一比：

| 指标 | 本程序 | OMEN Hub | 差 |
|---|---|---|---|
| CPU 温度 | 53.0℃ | 53℃ | 0 |
| GPU 温度 | **49.5℃** | **41℃** | **+8.5** |
| CPU 负载 | **25%** | **39%** | **−14** |

### 1. GPU 温度取到了 Hot Spot

```
GPU Core     42.0     ← 应该报这个
GPU Hot Spot 51.0     ← 旧代码报的是这个
```

旧代码 `name.Contains("Core") || name.Contains("GPU")` → `Math.Max(...)`，
"GPU Hot Spot" 也满足条件，取最大值就是热点。热点比核心高 8~12℃ 是正常物理现象，
但拿它当"GPU 温度"就比所有 OEM 工具都高。

### 2. CPU 温度取到了 Core Max

本机同时有 `CPU Package 59` 与 `Core Max 60`，旧代码对两者取 max → 报最热单核。
现在固定 `Package`（AMD 为 `Tdie`/`Tctl`）→ `Core Max` → 各核最大，三级回退；
顺手把 `Distance to TjMax` 排除掉 —— 那是余量不是温度（43 ≠ 43℃）。

### 3. CPU 负载窗口被压成了 200ms

`CpuUsageCounter` 是有状态的，而 `Read()` 被引擎（1Hz）和 UI（4~5Hz）同时调用，
每次都重设基线 → 实际窗口 200~250ms，再叠加 EMA 滞后。现在固定 **≥1 秒**窗口，
窗口未到就返回上次结果；与任务管理器同量级。

### 4. 新增「内存占用」指标

`GlobalMemoryStatusEx`：已用 = 总量 − 可用，与任务管理器同一组数。
实测 `7.5 / 15.9 GB（47%）`，OEM 面板 `7.6 / 16 GB（48%）`。

仪表盘现在是五张卡：CPU 温度 / GPU 温度 / CPU 频率 / 内存占用 / 风扇；
CPU 卡悬浮里有「Package + 最热核心」，GPU 卡悬浮与副标题里是「核心 + 热点」。

### 5. 新增 `tplab sensors`

一次列出「程序实际采用的值 + 全部候选传感器 + 口径说明」。所有口径结论都以它为准，
以后遇到"对不上"直接跑它，不用再猜程序取了哪个传感器。

### 6. 顺带

有效频率的 MPERF 交叉校验从 `≤1.05×` 放宽到 `3×`：主板把 P1 报低时，
严格门槛会让有效频率**永远**不显示（比不显示更糟）。偏差改为写进说明。

## 风扇控制：写入单位与回读校验

现象：**风扇声音明显变大，界面数值几乎不动。** 现场一查就露馅：

```
nbfc status -a
  Auto control enabled : True      ← 风扇根本不由我们控制
  Target fan speed     : 0.00      ← 我们的指令没落地
当前日志里一条 "NBFC 已设置" 都没有
```

### 两个方向相反的单位错误

| 环节 | 旧代码 | 事实 | 后果 |
|---|---|---|---|
| 写入 | `percent × 197 / 100`（当步进） | `nbfc set -s` 收 **百分比 0–100** | 45%→发 89、75%→发 148 |
| 回读 | `target × 100 / 197`（当步进） | `Target fan speed` 本来就是百分比 | 79% 被读成 40% |

而 `set -s 147` 的实测结果是：**`Auto control enabled: True`、`Target: 0.00`** ——
越界值让 NBFC **静默退回自动曲线**，退出码仍然是 0。

所以曲线目标一旦超过约 51%，我们不但在"假装控制"，还顺手把风扇交还给了 NBFC 自动曲线。
用户听到的变大声来自 BIOS/NBFC，界面显示的是我们自己的目标值——两者此后再无关系。

### 第三个错误：只认退出码

`if (st.ok) return true` 把"命令执行成功"当成"控制生效"。现在写完**立刻回读校验**：

```csharp
必须 Auto control == False 且 |Target − 请求| ≤ 2%，否则算失败（带原因、进 30s 退避）
```

### 界面改成"只显示确认生效的值"

| 状态 | 显示 |
|---|---|
| 已接管 | `风扇占空比 46 %` + 绿色「已确认生效 · 本机无转速传感器」 |
| 未接管 | `风扇 -- %` + 橙色「未生效（目标 46%）：NBFC 未接管…」 |
| 节流待写 | 保持上一次已生效值，备注「待写入 50%（距上次写入 1200ms < 3000ms）」 |

诊断页新增「NBFC 接管状态（写入是否真的生效）」，直接摆出
`Auto control / Target / EC 寄存器`，不用再靠听声音判断。

### 关于 `Current fan speed`

本机在 20% / 79% / 100% 三次写入后它始终是 `112.69`（197 步的 57%）——
既不是转速也不是实际占空比，只是 EC 寄存器当前值。所以它只能做诊断信息，
不能当"实测风扇"（所以界面上只显示一个数）。

### 验证

`tplab fan --set 40` → 回读 `Auto control=False · Target=40%`（修复前发的是 79）；
`NbfcBridge.SelfTest()` 3 组用真机原始文本断言"Target 79 必须解析成 79%、Auto=true 必须判未接管"。

## 频率计算：位宽、同源、分母

截图里 `CPU 有效频率 7461MHz`，同屏却是「瞬时倍频 3610MHz、负载 17%、9W」。
7461/2800 = **2.66×**，而芯片物理上限只有 3.8/2.8 = **1.36×**。四个错误叠在一起：

| # | 错误 | 后果 |
|---|---|---|
| 1 | 64 位 APERF/MPERF 被截成 `(uint)` 再相减 | 3 秒窗口丢 2 圈计数器（3.6GHz 下低 32 位 1.19 秒就回绕），比率随机翻倍 |
| 2 | `SetThreadAffinityMask` 失败时仍把值记进该核基线 | 变成「A 核 APERF − B 核 MPERF」，且每轮轮转核，前后不是同一个核 |
| 3 | 用 `ΔMPERF` 当分母 | 只统计 C0 时间，空闲时频率被算高（17% 负载算出 2.4GHz）|
| 4 | 只有 `>100 && <8000` 这种宽泛夹取 | 7461 正好落在里面，原样显示 |

### 修法

- **64 位差值**（3.6GHz 下 146 年才回绕）；
- **按 `GetProcessAffinityMask` 的允许核枚举**，绑不上就跳过该核，绝不跨核配对；
- 分母改成**实际经过的时间**：`有效频率 = ΔAPERF / Δt`。这个定义天然不超过睿频，
  且与任务管理器同口径；基准频率退化为交叉校验角色（读错也不影响结果）；
- 保留 `C0 内平均 = 基准 × ΔAPERF/ΔMPERF` 作辅助 —— 两者对比可区分「被降频」与「只是没活干」；
- 三道门：窗口 ≥0.2s、`ΔMPERF ≤ 基准×Δt×1.05`、`30MHz ≤ 有效 ≤ 最高频率×1.02`。
  任何一道不过就**不显示数字**，退回瞬时倍频并在副标题/悬浮里写明原因，绝不编一个像真的数。

### 验证

`tplab perf`（现场连采两次，直接对"是否 ≤ 单核 turbo"）+ `PerfMetrics.SelfTest()` 7 组，
其中一条就是**把 7461MHz 这组数当输入，断言必须被拒**。自检全部通过。

## 功率上限从哪来：探测、型号表、手填

把 CPU 45W / GPU 75W 写死在代码里。这对这一台是对的，但对别的机器就是错的 ——
它把"机器的电气属性"当成了"程序的产品参数"。这一版把它变成可探测 + 可覆盖：

```
CPU 设计功耗：MSR 0x614 thermal_spec_power（Intel 规格里的 TDP）
              → MSR 0x610 PL1（BIOS 出厂配置，可能被改过）
              → 型号表（标称值）→ 内置默认 45W
PL2 上限    ：BIOS 实际 PL2 → 1.25×CPU 设计功耗
GPU 设计功耗：nvidia-smi 的 default/max power limit
              → 型号表 → 内置默认 75W
覆盖层      ：你手填的值（>0）永远优先；0 = 交回自动
```

### 哪些真能读到

| 量 | 结论 |
|---|---|
| CPU 设计功耗 | **能**。`MSR 0x614` bits[14:0] 就是 `thermal_spec_power`，单位 W（需管理员） |
| CPU 的 BIOS 配置 | 能。`0x610` 的 PL1/PL2，但可能被本程序或别的工具改过，故降一级 |
| GPU 设计功耗 | **部分能**。桌面卡与非 Optimus 笔记本可用 NVML；**Optimus/Max-Q 笔记本全是 N/A**（独显由 MUX 动态供电），本机即如此 |
| 任何 WMI 类 | **没有**。`Win32_Processor` 无 TDP 字段，`root\wmi` 里也没有 TDP 类 |

所以"全自动"并不存在：CPU 通常能真读，笔记本 GPU 基本只能型号表或手填。
程序的态度是——**能读就用真值，读不到就明说在猜，并且允许你覆盖**。

### 界面上看到什么

「③ 高级 → ② CPU 精细微调 → 平台功率上限」：

```
CPU 45W（型号表）· PL2 ≤ 56W · GPU 75W（型号表）
有数值来自型号表或内置默认，不是本机实测：想更准就在下面手填（0 = 交回自动）。
CPU 设计功耗 [0] W（0=自动）   独显设计功耗 [0] W（0=自动）   [重新探测]
```

- 来源徽章分四档：`MSR 0x614` / `MSR 0x610` / `NVML`（这三个算实测）、`型号表` / `内置默认` / `手填`；
- 全绿 = 都是实测；出现橙色那行 = 至少一个数是猜的；
- 改完「CPU 设计功耗」→ 上面 PL1 那行的提示 `PL1 ≤ 45` 立刻跟着变，校验也按新上限走；
- 诊断页新增「平台功率上限（决定 PL1/PL2 的可用区间）」，支持报告也加了这一段。

### 手填的安全边界

`AbsoluteCpuMaxW = 150` 是协议层硬边界，填 9999 会被夹到 150；
但夹完还有第二道：`PL1=150W` 会被"预测稳态温度 204℃ > 安全线 95℃"直接 Block。
两层防护，不靠用户自觉。

`tplab power` 可现场核对（本机非管理员时 CPU 会落到型号表）：

```
CPU 设计功耗  45W（型号表）   按型号「i7-7700HQ」查内置表得标称 45W（未读到 MSR，仅供参考）
GPU 设计功耗  75W（型号表）   NVML 功率字段为 N/A，按显卡型号「GTX 1050 Ti」查内置表得标称 75W
```

## 本机硬件常数：CPU 45W / GPU 75W / 3.8GHz

用户更正：**CPU 45W、GPU 75W**（不是 60W）。直接把常量改成实际值，并把三者的关系讲清：

```
CPU 设计功耗（Intel 规格 / BIOS 出厂 PL1）  45W
PL2（BIOS 出厂值 56.25W）                   56W
散热可持续功率（85℃ 上限，R=1.207）        47.6W
45W 的稳态温度                              ≈ 82℃
```

关键推论：**45W 低于 47.6W**，所以这台机器根本不会因为撞 45W 而触到 85℃；
反过来也说明"再加功率"在物理上没有空间——跑满 3.4GHz 全核只要约 41W。
把 `maxW` 写死成 80W（比设计值高 78%），就会给出"还能再加 30W"的错误建议。

### 顺带补上 GPU 那一半

CPU 45W + GPU 75W = **120W 走同一套热管**，而热阻 R 是 CPU 单负载下标定的。
所以游戏时（GPU 75W）CPU 的可持续功率会明显低于 `(上限−室温)/R`。
诊断页新增「整机热预算」：显示 CPU/GPU 当前功率与设计值，GPU >20W 时明确提示
"GPU 正在吃散热，不要把 CPU PL1 顶到 45W"。

界面文案同步：`W（0=不改，PL1 ≤ 45）`、`W（0=不改，PL2 ≤ 56）`、
执行器行 `CPU 设计功耗 45W（PL2 ≤ 56W）…；独显 75W 共用散热`。

## 睿频档位：3.8GHz 是单核，全核 3.4GHz

用户给出本机真实规格：最高频率 3.8GHz（功率上限 45W）。两处建模错误随之暴露：

### 1. PL1/PL2 上限不能写死（本机 45W / 56W）

`maxW = 80` 比任何合理上限都高。改为读 `ParamConstraints.PlatformPl1MaxW`（现为 45W），
PL2 受 `PlatformPl2MaxW`（现为 56W）约束。

### 2. 0x1AD 解码错了：低字节是单核，不是全核

```
本机: 38 / 36 / 35 / 34  →  单核 3.8 / 3.6 / 3.5 / 全核 3.4 GHz
```

旧代码取 `raw & 0xFF` 当"全核倍频"，于是拿 3.41GHz 和 3.8GHz 比，永远判不出"已顶到上限"，
把满载 40W 误判成"功率墙，还能升 PL1 换性能"。现在：

- 判定频率墙用**全核档 3.4GHz**，依据里注明"单核上限 3.8GHz，四核满载到不了"；
- 手动「睿频上限」的约束值也用全核档（写 0x1AD 会把每一档都压到 ≤ 给定值）；
- 界面提示改为 `×100MHz（0=不改；本机单核 38 / 全核 34）`、`W（0=不改，≤60）`。

## 指标口径：热阻、温度预测、频率、限制原因

换霍尼韦尔相变片之后体感明显变好（NFS 10 稳 60FPS、CPU <80℃、GPU ~60℃、噪声温和），
但程序里 `R≈2.67 / 预测 238℃ / 功率预算 40W` 这些数字解释不通。用 10-30 的标定采样（465 点）复盘：

```
满载段（380 点）最小二乘：T = 27.6℃ + 1.207 K/W × P
  真实 R ≈ 1.2 K/W；85℃ 上限对应可持续功率 (85−27.6)/1.207 ≈ 47.6W
  同一 41W：冷机首分钟 72.6℃，热透后 78.8℃ —— 这就是 τ_hs≈130s 的热容
```

### 四个离谱指标的根因

| 现象 | 根因 |
|---|---|
| `R≈2.67`、`预测 238℃` | 热阻按 `(T−室温)/P` **逐拍**算；空闲 6W/41℃ → 2.76，EMA 把满载真值顶掉 |
| 功率预算比实测小 20%+ | `(上限−室温)/(R+0.30)`，R 本身已是总热阻，R2 重复计入 |
| 空闲显示 3.6GHz、负载 1% | 主指标取的是"请求倍频"，空闲时仍停在最高档 |
| 空闲判"频率上限"、40W 判"功率墙" | 判定顺序 + 负载门槛缺失；40W 实测 3.41GHz 已是全核上限 3.40GHz |

### 修法

- **新热阻估计器**（`ThermalResistance`）：只吃负载 ≥35%、P ≥12W、|dT/dt| ≤0.8℃/s 的准稳态样本，
  用 **ΔT/ΔP 的最小二乘斜率**；要求 ΔP ≥8W 且 ΔT ≥4℃ 的激励，单次变化限幅 ±20%；
  无激励时退化为"带 5℃ 偏置的绝对式粗估"并明确标 **粗估**，不再冒充精确值。
- **预测改增量式**：`T_ss = T_now + R·(PL1 − P_now)`；稳态绝对式单独给，且只在 R 可信时显示。
- **温度可行性门**：抬 PL1 之前先把瓦数换算成温升，超上限就收到 `P_now + (上限−1−T_now)/R`，
  理由里写"原 80W → 限到 46W"。冷机不再一路抬到 80W。
- **轻载不抬功率**：`load <30%` 的"偏冷"不作为加功率依据（冷却阶段若按"偏冷就加功率"处理，就会抬回 80W）。
- **判定顺序**：温度 → 频率上限（负载 ≥30% 才算）→ 功率墙 → 轻载 → 无；每条结论都附**依据数值**。
- **仪表盘**：主指标改有效频率（APERF/MPERF），副标题给瞬时倍频与上限；功率预算改 `(上限−室温)/R`。
- **参数校验**：热阻不可信时，"预测超温"从阻断降为警告 —— 不再一条假预测把用户的 PL1 全挡掉。
- **新增「重估热阻」按钮**：换硅脂/相变片、改散热之后点一次，否则控制器还在用旧热阻。

### 离线验证（不用重压机器）

```
tplab fit    --csv samples-20261030-110552.csv --ambient 24 --ceiling 85
tplab replay --csv samples-20261030-110552.csv
```

回放结果：R 0.88（冷机首点）→ **1.19 K/W**（与离线拟合 1.207 一致），判定"频率上限（已顶 3.4GHz）→
加功率无效，保持"，PL1 稳定在 35W 一带。修复前同一条日志是 `R 2.67 / PL1 80W / 预测 238℃`。

## EC 共享总线：为什么风扇写入必须节流

**现象**：用了几天之后，系统报「检测不到电池」。

**结论：电池没有坏，是被风扇写 EC 挤掉了读数。**

查证链（都在本机日志/事件日志里，可复现）：

```
事件日志 System / ACPI / Id=13「在指定的超时期限内，嵌入式控制器(EC)未响应」
  10-27 全天    0 条   ← 当天 0 次 NBFC 写 EC
  10-28 19h     2 条   ← 当天 3790 次写
  10-29 15–19h 11 条   ← 当天 2384 次写，每小时都有
```

程序日志同一时段是每秒一条：

```
18:15:01  NBFC 已设置 51% → 寄存器值 100
18:15:02  NBFC 已设置 58% → 寄存器值 115
18:15:03  NBFC 已设置 75% → 寄存器值 148
```

原因：笔记本风扇没有标准 PWM 通道，只能由 NBFC 经 WinRing0 **直写 EC**；而
**电池电量、是否插电也由同一个 EC 上报**（`Win32_Battery` → ACPI `PNP0C0A` 的 `_BST` 读 EC）。
EC 是单总线，一次只服务一个 owner。旧逻辑只有一道闸「目标变化 ≥1% 就写」，
1 秒采样下等于 1 Hz 压 EC，ACPI EC 驱动被打到超时，电源驱动读不到电池 —— 于是「检测不到电池」。
事后核对：`Win32_Battery` 仍返回 `Primary / 97% / 充电中`，PnP 电池设备状态 OK，电池确实没坏。

### 修法：两道闸 + 退避

| 闸 | 规则 |
|---|---|
| 时间闸 | 距上次写 EC < `FanWriteMinIntervalMs`（默认 **3000 ms**）→ 跳过 |
| 死区闸 | 目标变化 < 2%（应急 1%）→ 不写 |
| 去重 | 映射后寄存器值没变 → 不写（消除抖动造成的重复事务） |
| 退避 | 连续失败 3 次 → 暂停 30 s |
| 应急旁路 | 风扇 100% 或温度 ≥ 安全线 → 跳过节流（`force`） |

写间隔可在「③ 高级 → ③ 风扇与降频开关 → 写 EC 间隔」调（1000–10000 ms）。
3 s 的依据：本机 `τ_hs ≈ 130 s`，温度响应由 die 侧主导，3 s 完全跟得上，而 EC 事务频率
从 1 Hz 降到 0.33 Hz。

### 配套

- **启动自检**：近 10 分钟有 EC 超时 → 自动把间隔抬到 ≥5 s，并在启动提示里明确告知；
- **诊断页**新增「EC 访问健康」：直接读系统事件日志 ACPI 13，0 条通过、≤2 警告、>2 失败，
  并给出处置顺序（交回自动 → EC 复位 → 重装电池驱动）；
- **命令行**：`tplab ec` 同一套判断。

### 如果你的机器已经出现「检测不到电池」

按顺序做，多数在第一步就恢复：

1. **停止一切风扇软件调速**：本程序里关掉「启用风扇曲线调速」，或在命令行 `nbfc set -a` 交回自动曲线；
2. **EC 复位**：关机（不是重启）→ 拔掉电源适配器 → 长按电源键 **15–30 秒** → 插电开机；
3. 仍缺失：设备管理器 → 电池 → 右键「Microsoft ACPI 兼容的控制方法电池」→ 卸载设备
   （**不要**勾"删除驱动程序软件"）→ 操作 → 扫描硬件改动；
4. 还不行：`powercfg -restoredefaultschemes` 后重启；最后再考虑 BIOS 里 Load Defaults。

## 平台能力：参数范围之外的第二层约束

前八版所有的约束都在回答"这个值能多大"（PL2 ≤ 2×PL1、τ 只能取 2 的幂、稳态温度 ≤ 95℃…）。
但真实机器上还有一类更基础的限制：**这台机器上根本没有那个寄存器**。

- **AMD 平台**没有 `0x610`(PL1/PL2/τ)、`0x773`(HWP EPP)、`0x1AD`(睿频倍率)、`0x150`(FIVR 偏移)；
  AMD 走 SMU 邮箱 / CPPC / PBO，是完全不同的一套协议。
- **Haswell 及以前**没有 HWP（Speed Shift），EPP 无意义。
- **赛扬/奔腾**没有睿频，`0x1AD` 倍率表不存在。
- **11 代起的 Intel 移动端**在 Plundervolt 之后关闭了 FIVR 电压偏移，降压写不进去。
- **非管理员 / 开 HVCI** 时 Ring0 驱动被禁止加载 —— 但这是"暂时"，不是"没有"。

以前这些情况的表现都是同一条："写入失败"。用户看不出那是硬件不存在，
还会反复尝试、以为程序坏了。这些参数现在是可见、可解释、且**真的禁用**：

### 1. 三态判定，而不是布尔

```csharp
enum CapState { Supported, Unsupported, NeedsPrerequisite, Unknown }
```

关键区别在 `Unsupported` 与 `NeedsPrerequisite`：

| 状态 | 含义 | UI | 配置里的值 |
|---|---|---|---|
| `Supported` | 平台有、权限也有 | 可编辑 | 保留 |
| `Unsupported` | 平台层面就没有这个寄存器 | **禁用**（灰） | **清掉** |
| `NeedsPrerequisite` | 有，但当前拿不到（提权/HVCI/驱动） | 可编辑 | **保留** |
| `Unknown` | 引擎没起，还没读过 MSR | 可编辑 | 保留 |

把"暂时不可用"当成"不支持"是很糟的体验：用户提权回来会发现参数被清空，还得重填一遍。
所以**只有平台层面不存在才清值**。

### 2. 为什么必须清值，不能只禁用界面

配置文件是跨机器的（换机、重装、公司下发）。一份 `EPP=128 / PL1=35` 的配置落到 AMD 机器上，
只在 UI 禁用而不清值，这些值会一路流到写入层，最后变成几条"写入失败"的红字。

但清值**只能在"即将写硬件"的边界**（`ControlChannels.ApplyCapabilityLimits()`：
参数中心构造 / 应用 / 强制提交、引擎启动 / 重载配置），**不能塞进 `Normalize()`** ——
归一化会被"从配置档重建基线"复用，混进运行时能力就会导致「开机加载把用户的 EPP/τ 抹平并落盘」。
这个坑是自检时真踩出来的（自检模式用伪造 AMD 平台跑一遍，就把真机配置改掉了），
现在两个入口已彻底拆开。

### 3. 界面上看得见

高级页「② CPU 精细微调」顶部多了一条能力带：

```
本机 CPU：Intel(R) Core(TM) i7-7700HQ CPU @ 2.80GHz（Intel，family 6h model 9Eh，4 核 8 线程）
PL1/PL2 ✓　EPP ✓　睿频 ✓　降压 ✓
```

AMD 机器上会变成 `PL1/PL2 ✗ 本机不支持　EPP ✗ …`，下面一行写清"已禁用：PL1/PL2/τ、EPP、睿频上限、降压"，
逐项原因进悬浮提示（`ToolTipService.ShowOnDisabled` 保证灰掉的控件也能看到原因）。
同时「智能自动」被禁用（没有 PL1 就没有执行器），③ 控制通道自动切到"电源计划限频"，MSR 那一项在下拉里是灰的。

「⓪ 当前配置档」表也据此标 `✗ 本机不支持`，并且**不再算成自定义** ——
否则一份从 Intel 带过来的配置在 AMD 上会永远挂着改不掉的"自定义"标记。

### 4. 探测分两段

```
① CPUID(leaf 0/1/6) + WMI  →  厂商 / family / model / 睿频 / HWP   （无需权限，启动即可）
② MSR 实测(0x610/0x773/0x1AD 读回值是否合理)                       （引擎启动后，Ring0 就绪）
```

第二段是必要的：`0x610` 读得到但 PL1 字段为 0，说明 BIOS 把整个 RAPL 域藏了（部分 OEM 这么干）；
`0x773` 读得到也不代表写得进。所以 `Supported` 的判据是"读得到且值合理"，之后仍靠写入回读校验兜底。

### 5. 验证

`tplab caps` 一行看全：

```
PL1/PL2/τ（功率上限）  ✓  0x610 可读写，当前 PL1=45.0W / PL2=56.2W
EPP 能效偏好          ✓  0x773 可读写
睿频倍率上限          ✓  0x1AD 可读写，当前单核上限 38×100MHz
降压（电压偏移）       ✓  0x150 可访问（写入后回读校验）
电源计划限频          ✓  对所有平台有效
```

`CpuCapabilities.SelfTest()` 8 组全部用伪造平台（AMD / 无睿频 / 无 HWP / 非管理员 / 未探测 / 11 代移动端），
不依赖真机。界面侧加了 `--smoke-caps=amd|noturbo|nohwp|needadmin`：把能力快照替换成伪造平台再截图，
核对"禁用"是否真的发生 —— 真机上没法把 CPU 换掉。

## 进程功耗归因

温度是结果，不是原因。之前程序只告诉你 96℃，你还是不知道该关谁。现在仪表盘底部有
**高负载进程 Top 10**，按你指定的优先级排序：**功耗 → CPU → 内存 → 磁盘IO**。

| 列 | 口径 | 是实测还是估算 |
|---|---|---|
| 功耗 W | 整机包功率 × 该程序的 CPU 时间份额 | **分摊估算**（RAPL 只给整颗 CPU，硬件上不存在每进程功耗计数器） |
| CPU % | Δ处理器时间 / (Δt × 逻辑核数)，全核跑满 = 100 | 实测，与任务管理器同口径 |
| 内存 MB | WorkingSetSize 合计 | 实测（同名进程重复计共享页，偏高） |
| 磁盘 MB/s | Δ(读+写字节) / Δt | 实测，但是**逻辑 IO**（缓存命中也算） |

四个不显然的设计决定：

1. **按进程名合并**。Chrome / Edge 会把一页拆成几十个进程，不合并的话第一名永远是某个 3% 的
   renderer，真正的大头被摊薄到看不见。合并后显示「实例数」，悬浮可看 PID 列表。
2. **功耗必须在合并前分摊**（每实例 = 包功率 × 该实例 CPU 份额），否则会重复计算；
   份额之和恰好等于整机使用率，所以**合计总是小于包功率** —— 差额是空闲 / 核显 / uncore。
   界面上写的是「分摊合计」，不是「总功耗」。
3. **排序照你说的做，但用颜色补漏**：只按功耗排，一个狂写盘却几乎不吃 CPU 的进程
   （杀毒扫描、备份）会沉到后面。所以 IO ≥5MB/s 或功耗 ≥2W 的行标橙，提醒你它在那儿。
4. **无 MSR 权限时功耗列显示 `--`**，排序自动退化为按 CPU —— 而不是拿 CPU 份额去伪造一个瓦数。

顺手把仪表盘右下角那格「风扇通道明细」压成窄列（本机通常 0–1 行），把版面让给进程表；
表格不再用 `DataGrid`（它的列头和滚动条是系统浅色模板，在深色面板上会露白条），改为自绘列表。

命令行也能看：`tplab procs`；加 `--write` 会先写 64MB 临时文件，用来验证 IO 列真的在工作。

## 配置档：基线 + 增量

### 一、「风扇实测」为什么删了

你在压测里看到「风扇实测」从头到尾不动，判断是对的：**这个数值没有信息量**。

本机的风扇由 EC 固件私有管理，LHM 拿不到转速；所谓「实测」其实是 NBFC 的
`Current fan speed`，而它就是 NBFC **自己上次写进 EC 的值** —— 等于我们的指令。
于是界面上并排两格：一格是我下发的 65%，另一格是"回读"的 65%，负载变了也不动。
用户第一反应只能是「风扇卡住了 / 程序没生效」。

处理方式是**从源头删掉**，而不是改文案：

- 仪表盘 5 格 → 4 格，只留一张「风扇」卡：有真转速传感器就显示 RPM，没有就显示**下发占空比**
  并在副标题写清「本机无转速传感器 · 这是下发值」；
- 删除 `HardwareService.Read()` 里用 NBFC 回读凑出来的假风扇通道；
- 删除 `HardwareService.FanDutyReadable`、`NbfcBridge.TryReadFanPercent`（没有调用点，
  留着只会让人以为"能回读"）；
- CSV 的 `FanCmdPct` 改取引擎下发值 —— 旧代码用 `snap.FanSoftwarePct`，在笔记本上恒为 `-1`。

### 二、配置档：内置基线 + 增量，这次真的落盘了

你的描述是准确的：**基线 + 增量是对的，不是新配置槽**。但「增量」不能只活在内存里，
否则升级一次就丢。现在它是显式实例（`settings.json → Profile`）：

```jsonc
"Profile": {
  "Base": "静音",                                  // 基线是谁：内置、只读
  "Delta": { "Tceiling": 84, "Pl1": 30, "Pl2": 34 },// 只有被你改过的项
  "Baseline": { "Tceiling": 88, "FanMax": 55, ... } // 保存时的基线快照，仅供比对
}
```

启动时 **先用当前版本的基线重建，再叠增量**。所以：

- 你在高级页把 PL1 改成 30W、温度上限改成 84℃ → 顶栏变「◐ 静音 · 自定义」，
  这两项（加上随之改变的 PL2）写进 Delta，重启还在；
- 将来模型修正了某个基线值（比如 PL2 倍率 1.15→1.20），**你没改过的项自动跟随新基线**，
  改过的项仍保持你的值 —— 整份拷贝做不到这一点，所以不是"另存一个档"。

**哪些参数是"启动的、数值多少、约束多少"**，现在有一张表（③ 高级 → ⓪ 当前配置档）：

| 参数 | 来源 | 内置基线 | 当前值 | 机理约束 / 为什么 |
|---|---|---|---|---|
| 温度上限 | ● 自定义 | 88℃ | 84℃ | 70–95℃（TJmax 100 留 5℃） |
| PL1 持续功率 | 自动接管 | 不改 | 30W | 5–60W；稳态温度 = 室温 + R·PL1 |
| 安全线（超温强制降档） | 🔒 锁定 | 95℃ | 95℃ | TJmax − 5℃ 余量，只许下调 |

三种来源的含义：

- **基线**：内置模型给的推荐值，可以改（改了就变增量）；
- **● 自定义**：与你选的基线不同，已持久化；
- **🔒 锁定**：模型/硬件给死的量（安全线、TJmax、τ 的 log2 可表示域、PL2/PL1 上限、
  芯片最大睿频、在线估计的热阻 R），**没有直接修改权限**；
- 另外 **自动接管**：智能自动模式下 PL1/PL2/τ/EPP 每 3 秒由控制器重算下发，
  你填的值不参与下发，因此既不算自定义，也不会被悄悄当成生效。

顺带修掉两个不一致：

1. 顶栏 chip 与配置档表格曾各有一套判定（出现过「● 纯预设」配「3 项自定义」）。
   现在 `ProfileBinding.Overrides()` 直接取 `ProfileInstance.Rows()`，只有一条判定路径；
2. 「安全线」锁定在 ≤95℃：允许填到 110℃ 等于可以取消保护；加载配置时越界值会被校正回来。

配置档类：`src/ThermalPilot.Core/ProfileInstance.cs`（8 组自检）；界面：`③ 高级 → ⓪`。

## 界面信息分层

### 说明文字收进悬浮提示

旧界面每张卡片下面都挂着 2~3 行灰字解释（为什么这样设计、历史怎么错的），
读第一遍有用，之后每次打开都是噪音。因此**静态说明**统一收进标题旁的 `ⓘ`：
鼠标停上去才展开，默认界面只剩「标题 + 控件 + 当前值」。

处理原则是**只收静态的，不动动态的**：

| 内容 | 处理 |
|---|---|
| 设计缘由、物理语义、历史错误回顾 | → `ⓘ` 的 ToolTip（鼠标悬浮才看） |
| 当前值、功率预算、校验结果、待应用 diff | 留在页面上（这是每次都要读的） |

同时做了三处版面收敛：策略页 ②③ 并排成两列；控制通道下拉左对齐（之前居中很怪）；
标定页「跟随全局取向」由一整段话压成 `跟随全局取向 静音`＋悬浮明细。

### 取向绑定：预设是基线，手改是增量

这就是「静音-自定义」要问的东西。实现不是「另存成一个新档」，而是**基线 + 增量**的合成：

```
用户选「静音」 ──► ProfileName = 静音，并把一组推荐值写进配置
                        │
   之后手改任何一项 ──► 增量（增量隐含在各项值里，不额外存字段）
                        │
              显示层合成 ──►「静音 · 自定义」＋ 明细（温度上限 88→84℃、EPP 200→128）
```

关键设计：**不用 sticky 布尔标记**，而是每次按「当前值 vs 预设值」现算。收益有三条：

1. 手改后自己又改回预设值 → 自动退回「静音」，不会留下假的自定义标签；
2. 增量是隐含的，不用新增持久化字段，重启后照样认得出；
3. 「回到预设」= 清空增量，按钮语义与显示完全一致。

一处例外值得说明：**智能自动模式下 PL1 / PL2 / τ / EPP 由控制器按档位实时决定**，
高级页手填的这几项根本不下发，所以它们不计入自定义 —— 否则用户会看到一个
永远消不掉的「自定义」标记。

> 增量是**显式持久化**的（`settings.json → Profile`），
> 并且判定只剩一条路径（`ProfileInstance.Rows`）。见上一节。

判定逻辑：`src/ThermalPilot.Core/ProfileBinding.cs`（含 6 组自检，`tplab selftest` 会跑）。

## 参数体系：全局 / 预览 / 应用

### 0.1 先说三个被问到的现象

| 现象 | 真相 |
|---|---|
| 频率卡显示「上限 99%」 | 那是**本程序写给 Windows 电源计划的 `PROCTHROTTLEMAX`**，由旧的「温度→限频曲线」在 96℃ 时算出来的。而实测已证明该旋钮在本机上**无效**（cap=100/70/40 三档，功率与温度完全一致）。所以这个数字既不是频率上限、也不是限制原因，是纯误导。现在这里显示的是真实限制源（温度墙/功率墙/睿频上限/轻载） |
| 35W、96℃、3109MHz | 三重墙同时顶：热阻 R1≈1.8（硅脂干涸）→ BIOS 的 PL1=45W 实际只能撑到 ~35W；温度墙 96℃ 已贴限；睿频上限 38×100MHz 摸不到。**软件能做的只有把 35W 用得更有效，或者换硅脂**——不是继续加功率 |
| 风扇占空比 65% / 风扇输出 20% 一直不变 | 两个数一个是**实测回读**（EC/NBFC），一个是**指令值**。当时引擎处于「已暂停」，指令根本没有下发，所以 20% 是上次遗留值、65% 是 BIOS 自己在跑。两者并排又不加区分就会误导。现在只显示一个数，并标注是否已确认生效 |

### 0.2 参数三层模型（本次重构的核心）

**同一个语义如果有四五份变量**，就一定会漂：顶栏 `ProfileCombo`、标定页 `PrefQuiet/PrefBalanced/PrefPerf`、高级页 `AutoProfileBox`、策略模型 `PolicyStrategy`，谁也不管谁；而且 `BuildConfigFromUi()` 里第一行是 `var cfg = _engine.Config;` —— 界面上每个控件的改动直接改到引擎正在用的对象上，等于"边拖边写硬件"，没有校验窗口也没有回退点。

参数分成三层，代码层也分得开（`ParameterCenter` / `ParamConstraints`）：

| 层 | 含义 | 在哪改 | 代码 |
|---|---|---|---|
| **全局（Global）** | 取向、温度上限、室温、风扇上下限、控制通道。全程序唯一一份，持久化 | 只在「① 策略」页 | `ParamTier.Global` |
| **高级（Advanced）** | PL1/PL2/τ/EPP/睿频/降压/曲线/安全线。写硬件但需要专业知识 | 「③ 高级」页 | `ParamTier.Advanced` |
| **预览（Preview）** | 标定产出曲线、自动控制器决策、MSR 现值、交付指标。只读派生，永不参与 Diff | 各页只读展示 | `ParamTier.Preview` |

对应的三个变量：`Draft`（草稿，界面编辑的对象）、`Committed`（已应用，硬件真正生效的值）、`Preview`（只读派生）。所有写入硬件的动作只有一个入口：

```
界面改动 → Draft（仅内存） → 点「应用」 → 机理校验 → Committed → engine.ApplyConfig()
                                        ↘ 有阻断级违规 → 拒绝，原样报出原因
```

底部常驻「待应用变更」条会实时列出 `PL1 30W → 35W` 这样的 diff，并给出「放弃草稿 / 应用」两个动作。**改了什么、还没生效什么，一眼可见。**

### 0.3 硬约束来自机理，不是产品偏好

`ParamConstraints` 里每条边界都带「为什么」：

| 参数 | 边界 | 机理 |
|---|---|---|
| τ | 只能取 1/2/4/8/16/32/64s | MSR 0x610 的 time 字段是 **log2 编码**，写 20s 会被硬件落成 16s |
| EPP | 0–255 | 0x773 里是 8 位字段 |
| PL2 | ≥ PL1，且 ≤ 2×PL1 | 0x610 里 PL2 是"突增上限"，低于持续上限字段失去意义；超过 2 倍会在 τ 窗口内失控 |
| 温度上限 | 70–95℃，且 ≥ 室温+15℃ | TJmax 100 留 5℃；低于室温+15 时功率预算 `(上限−室温)/R` 趋近 0 |
| 降压 | −150–0mV | 再深在负载瞬变时容易不稳 |
| 睿频倍率 | ≤ 芯片 0x1AD 原值 | 超了会被硬件静默截断，不报错也不生效 |

还有一条**预测型**约束：用在线估计的热阻 R 预测 `T_ss = 室温 + R·PL1`。若超过 95℃ 直接阻断（"你付出的只是更高温度，频率并不会涨"）；若超过温度上限则警告（"功率墙和温度墙会互相打架，频率会来回抖"）。这条在你这台 R≈1.8 的机器上，会把 PL1 > 39W 全部拦下。

### 0.4 控制通道互斥

`EnableFrequencyControl`（电源计划限频）、`EnableCpuTuning/AutoCpuMode`（MSR）、`UsePolicyModel`（策略模型）三个开关如果同时为真，三套控制器就会互相覆盖——这是"温度升了、功率升了、频率反而降了"的直接原因。`ControlChannel`（msr / powercfg / policy）负责强制归一化：**同一时刻只有一个通道拥有 CPU 频率的控制权**，其余自动关闭。

### 0.5 顺手修掉的一个显示 Bug

MSR 0x610 的时间窗字段在你这台机器上读出来是 `110`，`2^110` 就是 1.3e33 秒——旧代码直接显示成 `τ=1298074214633706907132624082305024s`。现在解码超过合法域（0–6）一律归零，显示「—（未设置）」。

## 控制目标：从「温度」换成「交付性能」

### 1.0 为什么不能只看温度

温度是**滞后且不唯一**的代理量：同一个 82℃ 既可能是 15W 轻载、也可能是 45W 满载。
它无法回答「还能不能更快」。温度只是结果：

```
T_ss = T_amb + R·P        ← 温度 = 热阻 × 功率（结果）
性能   = f(交付频率)      ← 真正要最大的东西（目标）
```

所以控制律是 **「温度是约束、交付性能是目标」**，并直接测量 CPU 交付指标：

| 指标 | 来源 | 用途 |
|---|---|---|
| **有效频率** | `ΔAPERF(0xE8)/ΔMPERF(0xE7) × 基准频率` | 真正拿到手的时钟（含睿频/降频） |
| **包功率** | `0x611` 能量差 × `0x606[12:8]` 单位 / Δt | 判断功率墙是否在顶 |
| **当前倍频 / 上限** | `0x198[15:8]` / `0x1AD` | 是否已顶睿频上限 |
| **降频标志位** | `0x64B` / `0x1B1` bit0/2/4 | 是否真被温度强制降频 |

据此判出「谁在限制变快」，再决定动作：**温度墙→降 PL1；功率墙且有余温→升 PL1 换性能；
已顶睿频上限→保持不浪费电；轻载→保持**。

### 语义倒挂：谁才是真正的限制

如果把「性能」档的目标温度设得最低（75℃），
`P_budget=(75−24)/R` 就成了三档**最小** —— 性能模式反而风扇最响、功率最低、频率最低。
正确的做法是：**温度上限 88/88/90℃，风扇 55/75/100%**，性能档上限最高 + 满转速，
因此功率预算最高。静音与平衡共用同一上限，只靠风扇/EPP/PL2/τ 区分，
**把「声学偏好」和「性能预算」彻底解耦**，想安静不会顺手把性能削掉。

实测（`tools/control_model.py`）：

| 机型 | 静音 | 平衡 | 性能 |
|---|---|---|---|
| 健康机 R1=0.21 | 108.3W | 115.3W | **129.4W** |
| 断链机 R1=1.76 | 29.9W | 30.4W | **32.0W** |

`tplab selftest` 会把「P_budget 单调递增」当硬性不变量校验（含档位方向、功率墙/温度墙/睿频上限
四类决策、以及离线收敛）。

## CPU 精细调速（智能自动 + 手工微调）

这一版把 ThrottleStop 的核心能力真正做进了桌面工具：**直接读写 Intel MSR**，不再只依赖 Windows 电源管理。

### 1.1 控制面分层（哪些能调、用什么调）

| 层 | 名称 | 软件可控 | 工具 | 旋钮 |
|---|---|---|---|---|
| 0 | 硬件固有 | ❌ | 物理换件 | TDP / 硅脂(R1) / 散热模组 |
| 1 | Windows 电源管理（粗） | ✅ | `powercfg` | 电源计划 / 最大处理器状态% / Turbo 策略 |
| 2 | **CPU 精细调控（★主力）** | ✅ | 本程序直接写 MSR | 降压 0x150、**PL1/PL2/Time 0x610**、**EPP 0x773**、**睿频倍率 0x1AD** |
| 3 | GPU 精细调控 | ✅ | `nvidia-smi` / Afterburner | 功率墙 / 频率偏移 / 温度目标 |
| 4 | 外部 | ❌ | — | 环境温度 / 散热底座 |

> 异常识别跑在「出厂默认逻辑」下只观察；调控伸到第 2 层 MSR，而不是只有 Windows 自带电源管理。

### 1.2 智能自动（推荐，默认平衡）

`高级调参 → ① 智能自动 CPU 散热`：

- 用当前「温度 / 封装功耗」**在线估计有效热阻 R = (T − T_amb)/P**（慢 EMA 抗噪），只用来给 PL1 一个起点；
- **主控制量是「谁在限制变快」**：每 3 秒采一次交付指标（见 §1.0），功率墙且有余温就升 PL1（+3W/次），
  温度墙就降（−6W/次），顶到睿频上限或轻载就保持不动 —— 不再拿温度当 setpoint 瞎调；
- 没有 MSR 权限/读不到指标时，自动退化为纯温度反馈（±3W，过热 −6W，1℃ 回差），老机器也能跑；
- **PL2 / Time / EPP 按档位**给出：静音 PL2×1.15/τ=8s/EPP200、平衡 ×1.25/16s/EPP128、性能 ×1.35/32s/EPP0（τ 用 2 的幂，因为 Intel 该字段是 log2 编码）；
- 超温（≥保护温度）无条件把 PL1 压到最低，压过一切策略；
- 可勾「预览模式」只计算不写 MSR，安全试用。

不需要跑标定，换机器/换室温也能自动收敛到温度上限内；界面上会实时显示 `有效 xxxMHz · 包功率 xxW → 谁在限制`，
手工微调时也能立刻看到改动的效果。

### 1.3 高级手工微调

`高级调参 → ② CPU 精细微调`：降压(mV)、PL1(W)、PL2(W)、Time/τ(s)、EPP(0–255)、睿频上限(×100MHz)，
配 **读取当前值 / 应用旋钮 / 还原 MSR**。每项写入后立刻读回校验，被 BIOS 锁定的项会明确显示失败。

### 1.4 一个真实的 bug 修复

旧 `UndervoltService` 用「1 参/2 参」签名去找 LHM 的 MSR 读接口，而 LHM 0.9.4 的真实签名是
`ReadMsr(uint, out uint eax, out uint edx)`（3 参）。签名永远匹配不上 → 读回恒为 0 → **降压校验必然失败**。
为此抽了共享的 `MsrAccess`（按真实签名调用），并支持 `Ring0.Open()` 兜底。

### 1.5 安全边界

| 项 | 说明 |
|---|---|
| 默认关闭 | 所有 MSR 写入默认关闭，需用户显式勾选 + 二次确认 |
| 读回校验 | 每次写入后立即回读目标字段，不符即判失败（BIOS 锁 / 平台不支持） |
| 退出还原 | 首次写入前保存 0x610/0x773/0x1AD 原始值，停止/退出时精确还原；降压回零 |
| 前提 | 管理员权限；关闭「内存完整性(HVCI)」；LHM 驱动加载成功 |
| 易失性 | MSR 偏移重启即失效，不会永久改坏硬件；最坏情况是死机，重启恢复 |

## 实现要点：几个容易踩的坑

| 问题 | 处理 |
|---|---|
| **CPU 使用率超过 100%（实测 148%）** | 根因：原实现取监控库的 `CPU Total` 计数器，部分平台该值按睿频折算（`% Processor Utility` 语义）可超 100%。已改为 `GetSystemTimes` 差分自算，**物理上限就是 100%**，并做 EMA 平滑，跨机型一致 |
| **风扇没有数据（HP OMEN 15-ce0xx）** | 判定为 EC 私有固件管理，LHM 无该机型配置。新增**机型探测 + 机型化方案建议**（诊断页直接告诉你该用哪个社区工具），并内置 **NBFC 后端**：装好 NBFC 并选配置后，本程序自动通过 `nbfc` CLI 写占空比，风扇曲线重新可用（NBFC 只能写 EC、不提供转速，所以「风扇」卡显示的是下发值） |
| **隐藏的严重 bug：退出可能把 CPU 锁在 5%** | `powercfg /query` 输出里有最小值/最大值/当前值多个 16 进制数，旧代码取"第一个"，拿到的是**最小值**（本机读出 0）。已改为精确匹配「当前交流电源设置索引」并加 [5,100] 防御 |
| **要能自己跑实验、拿数据、拟合** | 新增命令行实验台 `tplab`（探测 / 压测 / 采集 / 风扇控制）+ 分析器 `tools/lab_analyze.py`（稳态判定、拟合、因素排序、控制律反解、生成 HTML 报告） |
| **要能自动化调参，而不是靠手调** | 新增建模器 `tools/lab_model.py`：7 类模型族（均值/线性/二次/**阶梯表**/风扇线性/**二维阶梯网格**/**神经网络 MLP**）按阶段留一交叉验证排序，导出 `model-*.json` 策略；C# 端 `PolicyModel` 直接推理，界面上「高级调参 → ④ 实测策略模型」一键启用 |
| **要知道实验跑够了没有** | 新增 `tools/lab_doe.py`：用 Fisher 信息矩阵算**目标温度处的 95% 预测区间**，判断这套数据能辨识什么、再跑一档值不值、什么时候该停；输出「不确定性税」（模型不够准导致必须让出多少 cap） |
| 风扇卡片会显示 "34%" 但没有通道 | 无调速通道时不再显示伪造输出值，改为「无调速通道 · 见诊断页」 |
| 缺少电压等热学关键量 | 新增采集 **核心电压 V**、**最热核心温度**，仪表盘 CPU 卡片直接显示 `负载 · 功耗 · 电压` |

## 2. 能力边界

| 能力 | 原理 | 支持范围 |
|---|---|---|
| 温度/负载/频率/功耗/电压/转速采集 | LibreHardwareMonitor 签名内核驱动 | 多数 Win10/11 x64（需管理员） |
| CPU 动态降频 | `powercfg` 最大处理器状态 + Turbo 策略 | **全平台可用**，安全可还原 |
| 风扇曲线调速 | ① 主板 SuperIO PWM（LHM Control 通道）② 笔记本经 **NBFC** 写 EC | 台式机多数可用；笔记本需装 NBFC 并选对机型配置 |
| CPU 降压 | Intel OC Mailbox（MSR 0x150） | 仅 Intel；10 代以后多数被 BIOS 锁定；HVCI 开启时不可用；写入后读回校验，失败回零 |
| **CPU 精细调速** | MSR 0x610（PL1/PL2/Time）、0x773（EPP）、0x1AD（睿频倍率） | 仅 Intel；需管理员 + 关 HVCI；BIOS 锁定项写不进（读回校验拦下） |
| **智能自动 CPU** | 在线热阻估计 + 目标温度闭环 | 同上；无 CPU 功耗传感器时退化为纯温度反馈 |

### 笔记本风扇到底怎么才能控（本机实测结论）

本机 `HP OMEN by HP Laptop 15-ce0xx`（i7-7700HQ + GTX 1050 Ti）：
- LHM 识别到 **73 个传感器，0 个风扇转速、0 个调速通道** → 风扇挂在 EC 上，主板没有 SuperIO 风扇通道；
- HP 只暴露了 `HP_BIOSEvent` WMI 类，没有风扇控制接口；
- 可行路径：**NoteBook FanControl 1.6.3 + "HP OMEN Notebook PC 15" 配置**（社区验证 OMEN 15/17 通用）。
  装好后本程序自动接管，风扇曲线恢复生效。

> NBFC 自带内核驱动（WinRing0）直接读写 EC，属高风险操作：写错寄存器可能导致风扇狂转或停转。
> 本程序只在"检测到 NBFC 已安装且已选配置"时才调用它，并在退出/停止时交还固件策略。

## 3. 技术选型

| 方案 | 结论 |
|---|---|
| **C# / .NET 8 + WPF** | ✅ LibreHardwareMonitorLib 原生 .NET、自带签名驱动、单文件 65MB、曲线编辑/图表成熟 |
| Python + PySide6 | 需 pythonnet、打包 200MB+ ✗ |
| C++ / Win32 | 需自写并签名驱动 ✗ |

ThrottleStop 的核心是 MSR 写入，必须带驱动、易被杀软拦截。本方案复用 LHM 已验证的签名驱动做 ring0：
**CPU 精细调速**（降压 / PL1 / PL2 / Time / EPP / 睿频倍率）与**智能自动**都落在这一层；
Windows 电源管理保留为「安全兜底层」，两者可并存。所有 MSR 写入默认关闭 + 二次确认 + 读回校验 + 退出还原。

## 5. 热模型方法论（摘要，全文见 `docs/MODEL.md`）

目标写成双目标优化，避免"温度与噪声打架"：

```
min  J = w_t · max(0, T_hot − T*)² + w_n · SPL(fan)
```

三条物理关系支撑全部推理：

1. `P ≈ c·f^α`（α>1，降频降温是超线性收益）；
2. `T = T_amb + R_th·P`（`R_th` 是机器指纹，℃/W）；
3. `SPL ≈ 50·log₁₀(RPM)`（噪声随转速强非线性 → 风扇是"最贵"的手段）。

控制律反解（这就是"反向参数取值"）：

```
P* = (T* − T_amb) / R_th      →     由 P* 反解 cap（二次模型取根）
顺序：先降频 → 再关 Turbo → 再降压 → 最后才拉风扇（前三个不加噪声）
```

## 6. 实验台与建模（先拿数据，再谈调参）

### 6.0 先诊断：热链路哪个环节有问题（5.3 分钟）

```cmd
lab\run-diag5.cmd     :: 管理员双击。判断故障在 硅脂/压装、风扇/风道、整体规模、还是供电
python tools\lab_diagnose.py lab-data\lab-diag5-<时间戳>.csv --tamb 室温 --design-w 设计功率
```

输出判定树结论 + 三档温度目标的功率预算 + 换硅脂反事实（`lab-data\report-diag.html`）。
核心物理量 R1（die↔散热器热阻）由「掉载瞬间温度塌落」反解，不受环境温度与风扇状态影响。
验证：4 仿真场景 + 真实 19 分钟数据，10 个随机种子 40/40 分类正确。详见 `docs/MODEL.md` §12。

### 6.1 先跑短的：3 / 5 / 10 分钟

```cmd
lab\run-lab.cmd quick5       :: 推荐从这里开始。5 分钟，BIOS 风扇策略，产出可用的离散阶梯
lab\run-lab.cmd quick3       :: 3 分钟。只够看趋势与量级，别拿它定控制参数
lab\run-lab.cmd quick10      :: 10 分钟。多一个功率层级，能检验线性/二次项
```

5 分钟**到不了稳态**（每档要走 ≥3τ，而 τ 通常 60~120s）。它之所以能用，
是因为程序不等稳态，而是把升降温轨迹**拟合成指数曲线再推到稳态**：

    τ·dT/dt = (T_amb + R·P) − T   ⇒   T(t) = A + (T₀−A)·exp(−t/τ)

对固定 τ 这个式子对 (A, T₀) 是线性的，所以求解只是「外层一维搜 τ + 内层解 2 参数最小二乘」，
不需要非线性优化器。详见 `docs/MODEL.md` §11。

离线用已知真值校准过的精度（`python tools\validate_transient.py`）：

| 计划 | 预算 | 外推最大误差 | 直接取段尾均值的误差 |
|---|---|---|---|
| quick3 | 3 分钟 | 7.48℃ | 14.45℃ |
| **quick5** | **5 分钟** | **1.03℃** | 10.50℃ |
| quick10 | 10 分钟 | 1.14℃ | 6.10℃ |

右边那列是关键：同样 5 分钟的数据，**不做外推就差 10℃，做了外推差 1℃**。

### 6.2 再跑长的：18 分钟全量（需要精细阶梯时才跑）

```cmd
lab\run-lab.cmd              :: 右键→以管理员身份运行；BIOS 固定风扇策略，8 阶段 ≈18 分钟
lab\run-lab.cmd nbfc         :: 装了 NBFC 后跑两因子设计（cap×fan 3×3），≈30 分钟
lab\run-lab.cmd -DryRun      :: 只做环境自检（找 dotnet / python / nbfc），不压测
```

`run-lab.cmd` 只是个 ASCII 垫片，真正的逻辑在 `run-lab.ps1`（批处理在 UTF-8 中文下会被 cmd 解析器拆行，这个坑踩过）。

短时模式跑完会依次做：施加控制量 → 每秒采一行 CSV → `lab_transient.py` 外推稳态并导出阶梯表。
全量模式跑完会依次做：`lab_analyze.py` 出热模型报告 → `lab_doe.py` 判**这套数据够不够用** → `lab_model.py` 出**模型选择与策略导出**。

命令行分步：

```
tplab probe                                                    # 硬件 + 风扇后端 + 电源原始值
tplab lab --plan lab\plan-quick5.json  --out lab-data --tag q5      # 5 分钟快测
tplab lab --plan lab\plan-doe-v1.json  --out lab-data --tag doe1    # BIOS 阶梯（全量）
tplab lab --plan lab\plan-nbfc-v1.json --out lab-data --tag nbfc1   # cap×fan 全因子
tplab fan --status | --set 60 | --restore                       # 风扇直控（LHM 或 NBFC）
tplab model --file lab-data\model-doe1.json --list                      # 查看策略阶梯
tplab model --file lab-data\model-doe1.json --temp 80 --strategy quiet  # 查单点
tplab procs [--write]                                          # 进程 Top10（--write 顺手验证 IO 计数）
tplab caps                                                     # CPU 平台能力矩阵（哪些高级参数被禁用）
tplab power [--set-cpu N] [--set-gpu N]                        # 功率上限来源（含手填覆盖验证）
tplab perf                                                     # 现场测有效频率（需管理员，验证是否 ≤ turbo）
tplab sensors                                                  # 程序采用值 + 全部候选传感器（对账用）
tplab ec                                                       # EC 访问健康（近 30 分钟 ACPI 13 次数）
tplab fit    --csv samples-*.csv [--ambient 24] [--ceiling 85]  # 拟合热阻（T = a + R·P）
tplab replay --csv samples-*.csv [--ceiling 85] [--turbo 3400]  # 回放控制律，逐步看判定
python tools\lab_transient.py lab-data                         # 短时数据：外推稳态 + 导出策略
python tools\validate_transient.py                             # 离线校准：3/5/10 分钟够不够
python tools\lab_analyze.py lab-data                           # 只重跑热分析
python tools\lab_doe.py     lab-data                           # 只看数据够不够、下一档跑什么
python tools\lab_model.py  lab-data                             # 只重跑建模
```


产物：

| 文件 | 内容 |
|---|---|
| `lab-data/lab-<tag>.csv` | 原始采样（18 列，见 `docs/MODEL.md` 数据字典） |
| `lab-data/report-<tag>.html` | 热分析：拟合曲线、因素影响力、控制律反解（仅全量） |
| `lab-data/transient-<tag>.html` | **短时实验**：每段外推稳态、τ、线性性、判断（仅快测） |
| `lab-data/lab-<tag>-synth.csv` | 温度列被替换为外推稳态的副本，供下游建模复用（文件名带 synth） |
| `lab-data/model-<tag>.json` | **策略模型**（稳态模型 + τ + 阶梯表），C# 端可直接推理 |
| `lab-data/model-<tag>.html` | 模型排行榜（按阶段留一 CV）、阶梯表、稳态特征 |
| `lab-data/validation-quick.html` | 3/5/10 分钟计划的离线校准报告（已知真值对比） |

建模方法、模型排行榜与踩坑记录见 `docs/MODEL.md` §8；短时实验的方法与精度边界见 §11。

**短时实验的限制要说清楚**：5 分钟只有 2 个满载档，做不了模型族比较（`lab_model.py` 要求 ≥4 个）。
所以它导出的策略是**阶梯表**，而且**只在实测过的 cap 上给档位**（例如 60% 与 100%），
中间不插值——因为 `cap→功耗` 受 Turbo 台阶影响强烈非线性，插值会偏 5℃ 量级。
要连续曲线或 4 档以上精细阶梯，还是得跑全量。<br>
**策略模型怎么被程序用上**：打开「高级调参 → ④ 实测策略模型」→ 点「用最新结果」（自动找最新的 `lab-data\model-*.json`，短时的 `model-*-transient.json` 同样能被找到）→ 选取向 → 保存并应用。
之后引擎不再走曲线，而是按阶梯表查表：`cap` 与风扇都由模型给出，实测温度明显超出目标时自动收紧一档，超温保护永远优先。
界面会直接显示当前档位与预测：“按目标 85℃ 查表 → 频率上限 95%，风扇 30%，预测稳态 83.7℃，噪声 −26.1 dB”。
运行时只做 JSON 推理，不需要 Python、不需要联网。控制律细节见 `docs/MODEL.md` §9。

## 7. 自动标定怎么算的（应用内，给想看明白的人）

1. **阶段**：空闲基线 → CPU 满载（频率上限 100/70/50…）→ CPU 满载（风扇强制 100/60/45…）→ 冷却。
2. **稳态判定**：取每阶段后 45% 窗口，波动 ≤ 2°C 判定稳态。
3. **拟合**：一元最小二乘 `T = A + B·x` → 频率模型 `T=A_cap+B_cap·cap`、散热模型 `T=A_fan+B_fan·fan`。
4. **生成曲线**：以目标温度为锚点，低温段维持最小转速，接近目标线性升速，目标 +10°C 满转。
5. **可解释**：结论写进结果区（如「每降 10% 频率上限约降 3.1°C（R²=0.97）」），仍可逐点改。
6. **数据可带走**：全程 CSV，高手可自己做回归。

## 9. 排错清单

- **风扇显示「--」/通道 0**：笔记本 EC 私有控制（预期）；看诊断页给出的机型化方案，装 NBFC 后重测。
- **只有输出%、没有 RPM**：同上；装上 NBFC 并选对配置即可同时拿到两者。
- **CPU 使用率**：现在恒 ≤100%（`GetSystemTimes` 差分）；若与任务管理器差 1–2% 属正常（采样窗口不同）。
- **HVCI 已开启**：驱动被禁，调速/降压不可用，诊断页给了关闭路径。
- **降压提示被 BIOS 拒绝**：10 代以后 Intel 常见，属预期。
- **杀软误报**：带内核驱动的温控程序大概率被误报，请加白名单 `C:\Program Files\ThermalPilot`；正式分发建议代码签名。首次运行会在程序目录释放 `ThermalPilot.sys`。
- **兼容性**：Win10 1607+ / Win11 x64；更低版本未验证，**需在目标机实测**。
