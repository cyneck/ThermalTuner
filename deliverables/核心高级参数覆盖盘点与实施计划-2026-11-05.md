## 一、结论

1. **现有高级参数页只有 5 项**：PL1、PL2、Tau、EPP、睿频倍率上限
   （`Views/ParamsPage.xaml:78-204`）。用户要的 EPP=128 是**均衡档内置默认值**
   （`Core/Taxonomy/UserProfile.cs:33`），界面把 EPP 填 128 点「应用（真实写入）」即可，
   不需要改代码；当前 `settings.json` 的 `Manual.Epp=0` 是历史手动值，与均衡档不符。

2. **确有缺口**：`0x774` 里还有 **Min Perf / Max Perf / Activity Window** 三个对性能与散热
   直接有效的位域没开放；其中 **Max Perf 是比 PL1 更直接的限频手段**。
   这三项低风险、可逆、可回读校验，建议无条件补上。

3. **有一个必须先拍板的冲突**：`0x150` FIVR 电压偏移是降温最有效的参数，
   但项目既有约定是「**电压不碰**」（`MEMORY.md` 硬件事实段），且它可能导致系统不稳定/蓝屏。
   你现在的说法「核心高级参数都需要可以微调」与该约定冲突，**需要你一句话明确授权**，
   我不会擅自接入。

4. **明确不开放的项**：`0x1A2` TjMax Offset（改温度墙会让散热判断失真）、
   `0x774 [23:16]` Desired Perf（写死会破坏 HWP 自主选频）、`0x772`（本机不可读）、
   `0x1A0/0x194` 的 Turbo Disable / OC Lock、风扇/EC/PWM、C-state/电源计划。
   「都能微调」不等于「把每个可读寄存器都做成输入框」——只开放**确实有效且可安全回滚**的。

## 七、回滚方案

| 触发 | 动作 |
| :--- | :--- |
| 任一写入失败 / 回读不一致 | `MsrGuard` 自动回滚到写前原值；失败留审计日志 |
| 电压偏移导致不稳定 | **重启机器**（MSR 易失，固件重新初始化）；或界面「恢复原值」强制回零 |

## 八、假设与待核实（不编造）

- **假设**：`0x774` 各字段写入后 Windows 电源计划 / Intel DTT 不会立刻覆盖。
  单次实读一致不能证明长期稳定，**需 `--hwp-probe` 写入后延时回读验证**。
- **待核实**：`0x150` 在本机（i7-7700HQ / Win10 19045）是否真的接受写入——
  7 代 Kaby Lake 原则上开放 OC Mailbox，但 Plundervolt 修复微码可能已禁用；必须实测。
- **待核实**：HVCI / Defender 是否拦截 WinRing0（项目已知残留），会影响所有 MSR 写入能力。
- **口径**：「有效」指对 CPU 频率/功耗/温度有可观测影响；#5 睿频倍率在本机**实测无效**，
  接入不等于有效，UI 不得暗示性能提升。
- **待核实**：TjMax Offset=3 时有效温度墙约 97 °C（100−3）为按 Intel 位域常规解释，
  未用热失控实测确认，不作为量化依据。

### 9.2 关键实测一：0x774 写入会被系统覆盖

```
写入前   : Min 28 / Max 38 / Desired 0 / EPP 0 / AW 414 / 0x0000019E0000261C
探针目标 : Min 27 / Max 37 / EPP 128 / AW 413
探针写入 : Success（回读校验通过）
即时实读 : Min 27 / Max 37 / EPP 128 / AW 413   ← 写入确实生效
250ms    : Min 28 / Max 38 / EPP 0   / AW 414   ← 已被覆盖回原值
1.25s    : Min 28 / Max 38 / EPP 0   / AW 414
最终     : 等于出厂备份，未留脏状态
```

**结论**：本平台的 Windows 电源计划 / Intel DTT 会周期性重写 `0x774`。
因此 **EPP 从 0 改到 128 在本机不会持续生效**——这与方案阶段「EPP=128 即可」的假设不符。
产品应对：高级参数页加 `HwpHintText` 提示 + `--hwp-probe` 复核入口；
**L2 智能标定的稳定推荐只覆盖 `0x610` 的 PL1/PL2/Tau**，`RecommendedEpp` 标注「仅供参考、可能被覆盖」。
不引入周期性重写的自动补偿（避免复杂化，且会与系统电源策略争抢寄存器）。

### 9.3 关键实测二：本机 0x150 电压不可写

```
CPU 预筛   : Intel 第 7 代 / 移动版 / HWP 预期可用 / 电压「可能可用，需实测」
0x150 响应 : 0x000000000001857B（OC Mailbox 响应，不是实时电压）
探针 -10mV : WriteFailed（BIOS / Plundervolt 修复微码拒绝 或 读回不匹配），已强制回零
强制回零   : Restored，最终响应仍为 0x1857B
结论落盘   : VoltageWritable=False（settings.json）
```

**结论**：即使型号预筛为「第 7 代原则上开放」，本机 OEM BIOS / 微码仍拒绝了 OC Mailbox 写入。
这正好印证「型号判断只是提示，能力一律以实测为准」。产品应对：
`SessionState.VoltageEditable` 综合「0x150 可读 + 型号不排除 + `VoltageWritable != false`」，
本机 UI **自动禁用电压项**并给出原因；换一台自检 PASS 的机器则自动开放。
不伪装成可用、不保存失败值、`RestoreOriginal()` 强制回零。

### 9.4 三层模型落地（已实现，不新增页面）

| 层 | 载体 | 谁产生 | 标定是否触碰 |
| :--- | :--- | :--- | :--- |
| L1 固件固化 | `backup/msr-*-startup.json`（4 份，首次启动备份永不覆盖） | 固件上电 | 只读基准，任何流程不改 |
| L2 智能标定推荐 | `Settings.Calibration`（新增 `RecommendedPl1W / RecommendedEpp / VoltageContextMv`） | 两段式标定 | 只产出通用安全参数，不碰电压/睿频/温度墙 |
| L3 用户编辑值 | `Settings.Manual`（新增 `MinPerf / MaxPerf / ActivityWindow / VoltageOffsetMv`） | 高级参数页应用成功后 | **重新标定只更新 L2，绝不覆盖 L3** |

- 电压会改变热模型 → 标定快照记录 `VoltageContextMv`，推荐值可能随个性化微调变化，符合用户判断。
- 界面在同一张参数表里用两行分组标题区分「通用参数（L2 可推荐 / L3 可编辑）」与
  「个性化可选微调（仅 L3 手动）」，顶部三行文字展示 L2 / L3 / CPU 能力状态，**没有新增页面或对话框层级**。
- 应用顺序已修复：先写 `0x610` → 一次写 `0x774` 全字段 → 睿频 → 电压（独立二次确认，输入「降压」），
  **全部完成后才一次性保存 L3**；任何一项写入失败就不落盘，避免开机反复重放失败值。
