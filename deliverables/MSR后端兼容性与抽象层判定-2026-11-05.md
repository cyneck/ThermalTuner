# MSR 后端兼容性与抽象层判定

生成时间：2026-11-05 20:10　回应：PawnIO 到底用没用 / WinRing0 在部分电脑不可用是否需要抽象层 / UI 文案收敛

## 一、事实核查：PawnIO 到底用没用

**没用。** 运行时只有一条链路：`LibreHardwareMonitorLib 0.9.4 → WinRing0 → Ring0.ReadMsr / WriteMsr`。

| 证据 | 结论 |
| :--- | :--- |
| `ThermalTuner.App.csproj` / `ThermalTuner.Monitor.csproj` | 均固定 `LibreHardwareMonitorLib 0.9.4` |
| `MsrChannel.Open()` | 反射取 `Ring0` 的 `ReadMsr/WriteMsr`，`BackendName` = `LHM 0.9.4 / WinRing0` |
| `MsrChannel.InvokeRaw()` | 恒返回 `0x80070002`（「不是模块函数」），Pawn 函数路径已废弃 |
| `Services/Msr/PawnIoNative.cs`(115 行) / `LhmPawnModule.cs`(48 行) | **零调用点**，是 v0.4.2 误升级 0.9.6+ 时留下的死代码 |
| 全库 `PawnIO` 字样 | 只出现在注释、环境自检的告警文案、上述死文件里，无运行时调用 |

本轮已把这两个死文件用 `<Compile Remove>` 从编译中排除（保留文件作历史参考，不参与产物），
并把 `MsrChannel.BackendName` 从**硬编码常量**改成**运行时探测版本 + 是否有 WriteMsr**，
让环境自检报告反映真实后端，而不是永远打印 0.9.4。

### 口径更正

上一轮我写「**不要安装 PawnIO 作为替代**」过于绝对。按你的兼容视角，准确说法是：

> 0.9.6+ / PawnIO 的 IntelMSR 模块只有 `ioctl_read_msr`，**只能作为只读降级**用于查看参数，
> **不能替代 WinRing0 完成写入**。若本机 WinRing0 被 HVCI / 安全软件拦截，
> 请关闭内存完整性或加白名单；PawnIO 能否绕过同类拦截**尚未实测，不作兼容性承诺**。

已据此改掉 `EnvironmentCheck` 的三处文案。

## 二、是否需要新增抽象层：**现在不需要，别为了抽象而抽象**

你的痛点是「有的电脑 WinRing0 读写不了」。但现状已经覆盖了这个场景，缺的不是一层接口：

| 已有机制 | 覆盖的降级路径 |
| :--- | :--- |
| `MsrChannel` 是**唯一入口**：`MsrGuard` / `RaplPowerMeter` / `EnvironmentCheck` / `MsrProbe` / `SessionState` 都只调 `TryRead/TryWrite/CanWrite/Status`，**上层零处直接引用 WinRing0** | 换后端时上层不用改 |
| `MsrStatus` 六态：`Writable / ReadOnly / NoAdmin / NotInstalled / DriverUnavailable / ModuleUnavailable` | 驱动不可用 / 缺权限 / 程序集不对都能分别判定 |
| 演练模式（双开关：管理员 + 「允许写入 MSR」） | 写不了时完整走校验与确认，但不写硬件 |
| 首次环境自检 `capability.json` + `ParamsPage.IsEditable` | 读不到的参数项自动置灰，并给依赖处置建议 |
| `HardwareTelemetry` 独立于 MSR 通道（直接用 LHM `Computer` 读传感器） | **驱动挂了仍可看温度 / 频率 / 负载 / 包功耗**，软件不会整个不可用 |

再叠一条关键事实：**PawnIO 是只读后端**。把它接成第二个 provider，只能扩大「能读」的覆盖面，
**解决不了你说的「读写不了」中的写入部分**；而它能否绕过 HVCI / Defender 对未签名内核驱动的拦截，
本项目没有实测依据，不能当兼容性卖点。

因此现在的结论是：**引入 `IMsrTransport` 接口而不新增一个可写后端，是纯结构开销**，
与你反复强调的「避免复杂化设计」相悖。真正需要兼容的是**能力分级**，这一层已经有了。

### 什么时候才加（可判定触发标准）

出现以下**任一**条件时，再按接口化改造，届时上层零改动：

1. 出现**第二个可写后端**（例如厂商签名驱动、OEM SDK、跨平台 `msr` 设备），且实测能写 `0x610`；
2. 确认 PawnIO 在某类被 HVCI 拦截的机器上**确实能加载并读到 MSR**，且产品明确接受「只读降级」；
3. 需要支持非 Windows 平台的功耗寄存器访问。

**接口草案（现在不落地，避免死抽象）**

```csharp
public interface IMsrTransport
{
    string Name { get; }              // 运行时探测，不写死版本
    bool CanWrite { get; }            // 只读后端必须返回 false
    MsrStatus Status { get; }
    string Detail { get; }
    bool TryRead(uint msr, out ulong value);
    bool TryWrite(uint msr, ulong value, out int hr);
    string[] ListFunctions();
}
```

`MsrChannel.Open()` 改为按优先级探测 provider 链，失败逐级降级；
`MsrGuard` 的备份 / 回读 / 回滚 / 审计逻辑完全不变。
**关键约束**：只读 provider 永远不得进入 `Apply*` 写入路径，UI 必须标「只读演练」。

## 三、UI 收敛（本轮已改）

上一轮高级参数页顶部堆了 12 行说明（三层口径、电压风险、HWP 覆盖、依赖建议、自检摘要……），
确实像迭代日志。已按「一行状态 + 详情归位」收敛：

| 位置 | 改动 |
| :--- | :--- |
| 高级参数页头部 | **删掉 11 行常驻文字 + 整块自检卡片**；只留「模式/通道 chip」+ 一行 `MsrHint`（演练/真实写入）+ 一行 `CapabilityOneLineText`（如「自检 11/12 项可获取 · 禁用 1 项 · 1 条依赖提示见诊断页」） |
| 右侧按钮组 | 「重新自检」并入，去掉按钮旁的说明文字，改放 `ToolTip` |
| 诊断与日志页 | 新增「环境自检报告」卡片，承载完整 `CapabilityReportText`（只读文本框、可滚动） |
| 诊断页旧文案 | 「当前为只读版本，尚无需要恢复的写入」是过时描述，改为「写入前备份 → 回读校验 → 失败回滚；异常退出后下次启动自动恢复」 |
| 参数行「为什么是这个范围」列 | **保留**：这是功能说明，不是迭代日志 |

原则：**状态常驻、详情归位、风险提示放 ToolTip / 诊断页**，不在主操作区堆注释。
