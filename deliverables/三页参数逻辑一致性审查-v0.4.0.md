# ThermalTuner 三页参数逻辑一致性审查（v0.4.0）

审查对象：概览页 / 智能调优页 / 高级参数页（2026-11-03 18:20 前后截图）
审查方式：截图逐项抄录 → 全量代码交叉核对 → 结合当前业务模型判定
结论先行：**三页数值本身大多"分别自洽"，但合起来不自洽。根子不在显示，在于同一件事有三套算法、两个真相源，以及软件侧优化值在这三页里根本没被呈现。**

## 二、不一致清单（分级）

### 🔴 P0 — 会写错硬件 / 让标定白做

**P0-1　「低载维持」保持的是决策值，不是固件实值；且只升不降（棘轮）**
- 位置：`AutoCpuController.cs:95`（`CurrentPL1W = _pl1`）、`LightLoadFilterNode.cs:23`（`TargetPL1W = snapshot.CurrentPL1W`）、`AutoCpuController.cs:42`（`_pl1` 初始 35W）、`SessionState.cs:1158`（每拍 `TryAutoApply`）
- 事实：`_pl1` 是控制器内部"上一拍决策结果"，不是 MSR 实读。轻载规则输出「保持当前设置」= 保持这个内部值。一旦曾因高负载被推到平台上限 65W，之后负载回落到 7%、温度 48℃，规则把它**永久锁在 65W**，永不回落。截图评估路径 `SafetyWatchdog → LightLoadFilter` 正是这个状态。
- 后果（结合 v0.4.0 模型）：只读下无害；但用户一旦按新模型开启「允许写入 MSR」+「自动接管」或「开机重放」，**软件会在最不需要性能的时候把 PL1 从固件默认 45W 抬到 65W**，与规则自述「避免频繁步进 / 保持静音」完全相反。这是会被写进寄存器的错误行为。
- 修复：轻载分支的 `TargetPL1W` 取 `_fwLimits.Pl1W`（固件实读）而非 `_pl1`；`_pl1` 每拍以固件实读为锚做回落钳制，禁止内部状态自锁。

**P0-2　三套「预测稳态」，基准/公式/含义全不同，谁也不消费谁**
- 位置：
  1. `AutoCpuController.cs:81`：`tempC + (_pl1 - powerW) * rth` → 48+(65−10)×0.98 = **101.9℃**，透传到 `AutoCpuDecision.PredictedSteadyC`，**全项目无消费点**（僵尸字段），且公式正是上一轮判定为"虚高"的旧公式，只改了 App 层展示、没改源头。
  2. `ThermalPredictiveNode.cs:31`：`CurrentTempC + (StepUpWatts) * rth`，ΔP 用「PL1 设定值之差」，第三套口径。
  3. `SessionState.cs:1123`：`_baseTempC + (45W − _basePowerW) * Reff`，界面展示的 86.7℃。
- 后果：同一个名字对应三个物理量；Core 里躺着一个 101.9℃ 错误值随时可能被误用；上一轮的"预测虚高修复"只修了展示层，属于**改了症状没改病灶**。
- 修复：删除 Core 的 `PredictedSteadyTempC` / `AutoCpuDecision.PredictedSteadyC`；统一由 `ThermalCalibration` 提供唯一 `PredictSteady(rth, idleT, idleP, targetP)`，三处共用。

**P0-3　标定结果（用户花 1–3 分钟实测）对实际调优零影响**
- 位置：`ThermalDecisionEngine.cs:19-26`（节点顺序：SafetyWatchdog → **LightLoadFilter** → CeilingExceeded → **ThermalPredictive** → BottleneckArbiter）、`SessionState.cs:997`（`ApplyCalibratedRth` 后仅 ±15% 微调）
- 事实：轻载时第 2 个节点短路，**第 4 个热预测节点根本执行不到**；截图评估路径可证。标定出的 Rth 只驱动了「统计热阻 0.98」和「预测稳态 86.7℃」两个展示数字，以及结束时的推荐档位弹窗。
- 后果：正面回答了你最早那个问题——**目前「一键标定」的实际作用仍只是产出两个可看的数字，不改变任何决策行为，也不落地推荐档位**。这与 v0.4.0「实测标定是软件侧优化依据」的定位不符。
- 修复：二选一，别模棱两可——(a) 把标定 Rth 作为前馈接入决策（轻载节点之前先做一次可行性判断）；(b) 明确承认热模型只做展示，把标定定位改成"预测参考"，并在界面写清楚。我建议 (a)。

### 🟡 P1 — 数字不可复算 / 会误存非用户意图的值

**P1-4　86.7℃ 与界面其他数字算不自洽，基线不透明**
- 位置：`SessionState.cs:1090-1096`（基线只在 `PowerW < _basePowerW − 0.3` 时更新）、`:577-578`（开机灌入标定时 53.2℃@13.5W）、`:1123-1126`
- 事实：预测用 `_baseTempC/_basePowerW`——**会话内历史最低功耗时刻**的温度，不是卡片上的当前 48.0℃@10W。该温度只在功耗创新低时才刷新，室温/散热漂移后不更新。用当前值按 0.98 复算应得 ≈82.3℃，用标定基线得 ≈84.1℃，都对不上 86.7℃。
- 附带冲突：86.7℃ 距天花板 88℃ 仅 1.3℃，按产品逻辑本应触发保守/降档，但决策仍是 PL1 65W（平台上限）+ 风扇 75%，**没有任何降档动作**——因为决策树只看实测 48℃，不消费这个预测。预测与决策各自为政。
- 修复：预测卡片下方显示基线 `T_idle xx.x℃ @ P_idle xx.xW`，让数字可复算；基线增加"温度持续 N 拍稳定才刷新"的条件，不要绑死在功耗创新低。

**P1-5　EPP：当前生效 `--` / 待应用 128 / 「无改动」三处矛盾，且会把决策默认值当用户微调值持久化**
- 位置：`ParamsPage.xaml.cs:40`（`FwEpp` 为 NaN 时回落 `s.Epp`=128 填待应用）、`:160`（`baseEpp` 同样回落 `s.Epp` → 128 对 128 → 无改动）、`FwEppText` 显示 `--`
- 后果：本机 0x774 读不出（已确认）。用户点「应用真实写入」时，128 会被当成"用户微调值"写进 0x774 **并保存进 settings.json 供开机重放**——但它只是决策树的默认 EPP，用户根本没改。这直接违背 v0.4.0「只持久化用户实测/微调结果」的模型，会把一个非用户意图的值固化。
- 修复：固件 EPP 不可读时，待应用框显示 `--` 并禁用 EPP 项，`BuildDiff` 跳过该项；补 0x1B0（IA32_ENERGY_PERF_BIAS）回退读取。

**P1-6　Tau 校验对象错位 + 「无改动」仍可触发一次原样写入**
- 位置：`ParamConstraints.cs` 两级校验、`ParamsPage.xaml.cs:137/202`
- 事实：校验器拿**固件默认值 28672s** 去警告「待应用」框，等于在警告用户一个他没改的值；同时 diff 报「无改动」，但「应用」按钮仍可点，会把 45.0/56.2/28672 原样写回寄存器并触发一次持久化保存（伪写入）。
- 修复：`diffs.Count == 0` 时禁用应用按钮；校验只针对与基线不同的项。

**P1-7　「最高核频 3510.00 GHz」错 1000 倍，且已进决策输入**
- 位置：`HardwareTelemetry.cs:171-180`（LHM `SensorType.Clock` 单位是 **MHz**，直接返回）、字段命名 `MaxCoreGhz`、`SessionState.cs:1067`、`:1108`（`PerfSample.CoreClocksGhz = ClockGhz`）、`OverviewPage.xaml:69`（拼 `" GHz"`）
- 后果：显示 3510.00 GHz；错误值进入 `ThermalSnapshot.CoreClockGhz`。当前因 `MaxTurboGhz = 0` 使 `ThermalSnapshot.cs:30` 跳过频率封顶判断，暂未炸，但 `BottleneckArbiterNode.cs:99` 会把它打进因果理由文案（「已达最大睿频时钟 3510.00 GHz」）。**一个错 1000 倍的物理量已经进入决策链路**，属于埋雷。
- 修复：`PickMaxClock()` 返回前 `/ 1000.0`，或把字段改名为 `MaxCoreMhz` 并在消费端统一换算。

**P1-8　v0.4.0 真正要持久化的「软件侧优化值」，三页一页都没呈现**
- 事实：`SavedTuningText`（`SessionState.cs:712`）只在设置页有。截图里智能调优页只显示「已保存标定 Rth 0.98」，高级参数页「待应用」预填的是**固件实读值**，不是上次保存的微调值。
- 后果：用户做完标定+微调后，在三个主页面看不到「我保存的优化参数是什么、下次开机会重放什么」。更关键：重放成功后 `RefreshFirmwareValues()` 每拍直读 0x610，「当前生效」会变成优化值，而页面文案仍写着「固件值是出厂默认」——**用户无法分辨当前 55W 是 OEM 默认还是软件写进去的**，这正是你强调要分清的「固件自身参数」与「智能微调部分」。
- 修复：在高级参数页增加两行锚点：`固件出厂默认`（取 `MsrGuard._startupRaw` 解码，该文件首次创建后不覆盖，是真默认值）与 `已保存的软件侧优化值`（`Settings.Manual`）；「当前生效」单独标注来源（固件默认 / 软件重放）。

## 三、结合当前业务模型的判断

你上一轮确立的模型（本轮按此核对）：

| | 固件默认（0x610/0x774） | 软件侧优化值 |
|---|---|---|
| 性质 | 出厂默认，掉电即恢复，**不可持久化** | 实测标定 + 手动微调 |
| 生效 | 开机默认 / 软件不运行时按默认散热逻辑 | **每次开机由软件重放写入寄存器** |
| 高于固件值 | — | 正常优化，不按拟合误差处理 |

**核心矛盾**：代码把「决策树目标值」当成了主线索——三页里到处是 65W/81.2W/16s/128，而按模型它只是**每拍重算、不持久化的易失意图**。真正该被突出、被持久化、被重放的「软件侧优化值」反而藏在设置页。结果形成三个错位：

1. **真相源错位**：`CurrentPL1W` 取控制器内部状态而非 MSR 实读 → 轻载规则"保持"了一个假真相，且会把它写进硬件（P0-1）。
2. **算法错位**：同一「预测稳态」三套实现，展示层修了、Core 层没修，热模型没接入决策（P0-2/P0-3）。
3. **呈现错位**：固件默认、软件优化值、决策意图三者没有稳定锚点，用户分不清哪个是哪个（P1-8）。

一句话：**现在这套参数体系是"按决策树的意图"组织的，而你的模型是"按固件默认 / 软件优化值"组织的。两套组织方式没对齐，截图上的不一致只是表象。**
