# 智能微调会不会有实际效果？——生效性判定（v0.4.3）

> 判定日期：2026-11-03 ｜ 机器：Intel Core i7-7700HQ / 4C8T / Windows 10 19045
> 依据：`stress-report-v0.4.2.txt`、`calibration-sweep-v0.4.2.txt`、`turbo-stress-v0.4.3.txt`
> 本文不引入新实测，只把三轮 A/B 压测统一成**一份产品口径**；与 v0.4.2 / v0.4.3 报告数字一致。

---

## 一句话结论

**有条件地有效，且只有「把 PL1 压到实际满载功耗之下」这一条路径被实测证明有效；
默认状态下无感；性能释放类微调（拉平 38x / 放宽 PL1）在本机实测零收益。**

换句话说：这台机器上，智能微调算出来的最优解恰恰是「不用改」——
阶梯标定反解 85°C 上限得到推荐 PL1 **45.0W**，即固件默认值，散热余量本来就够。
只有用户主动「牺牲性能换温度」时，才有明显可测的效果。

## 三档判定矩阵

| 档 | 动作 | 0x610 / 0x1AD 实读 | 实测结果（A/B） | 判定 |
|---|---|---|---|---|
| A · 有效 | PL1 45W → **15W**，Tau 缩到 8s | 45.0 → **15.0** → 65.0 W | 均温 **−7.10 °C**、包功耗 −9.51 W、核频 −0.58 GHz | ✅ 效果直观可测，代价是降频 |
| B · 零收益① | PL1 45W → **65W**（放宽） | 45.0 → **65.0** W | 均功耗仍 24.6 W，温度/频率无变化 | ⛔ 天花板之上物理等价 |
| B · 零收益② | 0x1AD 拉平 **38x** | 38/36/35/34 → **38/38/38/38** | 满载核频 **3.41 → 3.41 GHz**，功耗 +2.04 W、温度 +1.11 °C | ⛔ 写入成功但 PCU 不采纳，只多发热 |
| C · 默认无感 | 装完软件不操作 | 全程 **45.0 W** | 决策树只算目标值，未授权不下发 | ⛔ 设计使然，非 bug |

> B② 的根因（推断，非固件层证实）：`HWP 0x770` 已启用，Speed Shift 接管选频；
> `HWP_REQUEST Max=38 / EPP=0`、无 PROCHOT、峰值 31.7 W 远低于 PL1 45 W →
> 瓶颈不在倍率表，也不在功耗墙，而在 PCU/BIOS 对非 K 移动 U 多核睿频表的采纳。

## 生效的四个必要条件（缺一即无感）

1. **管理员权限 + WinRing0 驱动可加载** —— `--write-test` 必须 PASS（LHM 固定 0.9.4）。
2. **`允许写入 MSR = true`** —— 默认 false，需用户在设置页显式开启。
3. **PL1 < 该负载场景下的实际功耗** —— 老标量负载只有 25~34W，场景化 `SIMD_FULL` 可达 44W 级（≈实读 PL1 的 98~100%）。必须先跑 `--scenario-sweep` 确认当前场景是否顶到墙；**重载已顶墙时放宽 PL1 才可能有收益**，只有轻载下往上调才物理等价。
4. **Tau 缩到秒级** —— 固件 Tau = 28672 s（≈8 h）是超长平均窗口，短时压测须改到秒级才看得到钳制；本机 `settings.json` 的 `Manual.TauS=16` 已由开机重放写入 0x610，当前生效 Tau=16s。

> ⚠️ **口径更正（2026-11-05）**：本文 v0.4.2 / v0.4.3 阶段的「本机峰值约 25W、仅 56%」只适用于当时的单一标量 `Math.Sqrt` 负载，
> **不是机器的物理上限**。场景化压测实测全核 SIMD/FMA 峰值 **43.93~44.89W**，已逼近固件 PL1 45W。
> 判断「是否顶到功耗墙」必须以当前负载场景的实测功耗为准，不能沿用历史报告里的某个固定瓦数。
>
> ✅ **管理员复核（2026-11-05 18:22）**：`deliverables/scenario-sweep-admin-2026-11-05.txt` 以
> 0x610 实读确认出厂基线 45.0W / 56.2W / Tau 28672s、当前生效 Tau 16s，
> SIMD_FULL 峰值 43.93W = **98% 覆盖**，FLOAT_FULL 41.65W(93%) 起即可触墙。
> 同时证明「开机重放把软件侧微调写入寄存器」确实生效（Tau 28672s → 16s）。

**可判定验收标准**（任一不满足即判「未生效」）：

```
管理员 + PL1=15W + Tau=8s + 6 线程满载 40s
预期：0x610 实读 = 15.0W；稳态均温较默认低 ≥5°C；核频较默认低 ≥0.4GHz；
     收尾 Restored，最终实读回到 45.0W / 56.2W / 28672s。
```

复跑：`ThermalPilot.App.exe --stress-test --out r.txt --csv s.csv --seconds 40 --low-pl1 15`（管理员）。

## 产品判断（分级，每条可执行）

- 🔴 **P0 · 不得承诺性能提升**：界面、文案、发布说明里禁止出现「睿频 38 倍释放更多性能」「提升主频」等表述——已被 `--turbo-stress` A/B 实测否定。0x1AD 能力可以保留为「规格内档位配置」，但不能作为卖点。
- 🟡 **P1 · 决策值与实读值必须分列**：决策树默认「只算不写」，界面须明确标「只读演练 / 已生效」并展示 0x610/0x1AD **实读**，避免把算法目标值误认为寄存器实值。建议启动时做一次无害写探测来判定通道状态。
- 🟡 **P1 · 价值定位改为温控/静音**：本机标定结论是「无需降墙」，因此产品价值不在优化出厂默认，而在用户主动设定温度/噪音目标时把 PL1 压下去，由 EC 自动降风扇转速（软件不直写风扇）。
- 🟡 **P1 · 收益与代价同屏展示**：降墙有效但核频掉 0.58 GHz，界面应同时给出「预计降温 °C」与「预计降频 GHz」，让用户自己权衡。
- 🔟 **P2 · 保留自动接管为显式授权**：默认关闭符合「固件值不可持久化、软件侧结果才持久化」的模型，不要改成默认开启。

## 边界（勿说反）

- 固件 0x610 / 0x774 / 0x1AD 里的值是**出厂默认，掉电即恢复，不可持久化修改**。
- 可持久化的是**软件侧实测标定值 + 手动微调值**（含睿频倍率），存 `%LOCALAPPDATA%\ThermalPilot\settings.json`；开机后由软件重放写入寄存器；软件不运行、未提权、未开写入开关时，CPU 按固件默认散热逻辑运转。
- 标定值可能高于固件值，属正常优化，不简单判为拟合误差。
- 软件**不控制风扇 / EC / PWM / 电压 / 电源计划 / 倍频**；0x150 电压偏移与超频能力未接入；0x1AD 调节范围限制在 `[8, 出厂单核上限]`，产品不做超频。
