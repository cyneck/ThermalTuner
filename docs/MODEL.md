# ThermalPilot 热模型方法论（v1）

> 目的：把"凭感觉调风扇曲线"换成**可测量、可解释、可反解**的闭环。
> 本文是方法论与公式说明，实验数据与拟合结果见 `lab-data/report-*.html`。

---

## 0. 先把目标写成数学

温度与噪声是一对互相拉扯的目标，必须显式写清取舍，否则调参永远在打架。

**双目标（Pareto）形式：**

```
min  J = w_t · max(0, T_hot − T*)^2  +  w_n · SPL(fan)
s.t.  T_hot = max(T_cpu, T_gpu)
```

- `w_n = 0` → **性能优先**：只压温度，风扇随便转（游戏本插电打游戏时用这个）。
- `w_t` 只对"超标部分"计罚 → **静音优先**：温度只要没超 `T*`，就不许加转速。
- 中间的权衡点构成一条 **Pareto 前沿**（温度 vs 噪声），运行时应落在前沿上，而不是随机某点。

这解释了为什么"调风扇曲线"不是唯一答案：能降 `T` 的手段里，只有风扇会**增加噪声**，
其他手段（限频、降压、关 Turbo）本质是**减少发热**——它们是在移动前沿，而不是在权衡。

## 1. 变量体系：谁跟温度有关

### 1.1 输出量（被控量 Y）

| 变量 | 单位 | 来源 | 说明 |
|---|---|---|---|
| `T_package` | ℃ | CPU 封装温度 | 控制主回路用它（DTS 读数，最可靠） |
| `T_coremax` | ℃ | 最热核心 | 比 Package 更敏感，用于保护判定 |
| `T_gpu` / `T_hotspot` | ℃ | 独显核心 / 热点 | 双热源时取 max |
| `RPM` | rpm | SuperIO / EC(NBFC) | 笔记本 EC 私有，需 NBFC 才能读 |
| `SPL` | dBA | ❌ 无传感器 | 只能用 **RPM 作代理**，见 §3.3 |

### 1.2 控制量（可操纵 U）

| 变量 | 范围 | 实施方式 | 副作用 |
|---|---|---|---|
| 频率上限 `cap` | 5–100 % | `powercfg` 最大处理器状态 | 直接损失性能，**不增噪** |
| Turbo 开关 `boost` | 0/1 | `powercfg` PERFBOOSTMODE | 削掉瞬时峰值，**不增噪** |
| 核心电压偏移 `ΔV` | −120…0 mV | MSR 0x150 OC Mailbox | 收益大但**有蓝屏风险**，需逐级验证 |
| 风扇输出 `fan` | 0–100 % | SuperIO PWM / NBFC EC 写 | **噪声↑**，是唯一"用噪换温"的手段 |
| 控制周期 / 斜率限速 | 1–10 s / 10–60 %·s⁻¹ | 程序内部 | 太快会振荡，见 §5 |

### 1.3 扰动（不可控 D，必须记录否则模型失真）

| 变量 | 影响 | 处理方式 |
|---|---|---|
| 负载类型/强度（空载、单核、全核、AVX、GPU） | 决定 `P`，是主导变量 | 实验里用固定压测核 + 满载比例校验 |
| 环境温度 `T_amb` | 直接平移所有温度 | 无传感器时用「空载稳态温度」当基准 `T_ref` |
| 进风口遮挡 / 垫高 / 桌面材质 | 改变 `R_th` 20%+ | 实验期间保持同一姿态 |
| 电源模式（插电/电池） | 改变 PL1/PL2 | 记录 ACMode |
| 积灰、硅脂老化 | 随时间漂移 `R_th` | 曲线需**定期重标定**（建议每 3 个月） |

### 1.4 派生量（真正进模型的中间量）

```
功耗     P = P_dyn + P_static ≈ C_eff · V² · f + P_static
热阻     R_th = (T − T_amb) / P           [℃/W]
热容     C_th = τ / R_th                  [J/K]
时间常数 τ = R_th · C_th
风扇增益 G_fan = −∂T/∂fan%                [℃/%]
降频增益 G_cap = −∂T/∂cap%                [℃/%]
电压增益 G_V  = −∂T/∂mV                   [℃/mV]
```

`R_th` 是这个系统的"核心指纹"：它把**功耗**翻译成**温度**。
有了它，任何控制问题都变成一句算术：`允许的功耗 = (T* − T_amb) / R_th`。

## 2. 三个必须成立的物理关系

1. **功耗随频率超线性**：`P ≈ C_eff·V²·f`，而 `V` 本身随 `f` 上升，
   所以实测常呈 `P ≈ c·f^α`（α ≈ 1.3–2.0）。**α > 1 意味着降频降温是"越降越赚"**。
2. **温度对功耗近似线性**：`T = T_amb + R_th·P`。线性来自牛顿冷却，是控制律能反解的前提。
3. **噪声随转速强非线性**：风扇声功率 ∝ `RPM⁵`，声压级 ≈ `50·log₁₀(RPM)`。
   也就是说**转速 +30% ≈ 噪声 +6.5 dB**（人耳明显可闻）。这是"少用风扇"的根本理由。

## 3. 实验设计（控制变量法）

### 3.1 为什么要"阶梯 + 稳态窗口"

热系统是一阶惯性环节：`C_th·dT/dt = P − (T−T_amb)/R_th`。
阶跃改变 `P` 后，温度按 `e^(−t/τ)` 收敛，**τ 通常是 60–120 s**。
所以：

- 每阶段时长 ≥ `2.5·τ`，否则测到的是暂态，不是稳态；
- 只取**每段后 45% 的样本**做均值（丢掉前段暂态）；
- 用窗口内温度标准差 σ 判定稳态：`σ ≤ 1.2 ℃` 才可用于拟合。

### 3.2 本轮设计（cap 阶梯）

| 阶段 | 负载 | cap | 目的 |
|---|---|---|---|
| S0 | 空载 | 100 | 环境基准 `T_ref`（代 `T_amb`） |
| S1–S4 | 满载 | 35/50/65/80 | 拟合 `cap → P → T` |
| S5 | 满载 | 100（Turbo 开） | 最高功耗点 |
| S6 | 满载 | 100（Turbo 关） | **单独分离 Turbo 效应** |
| S7 | 空载 | 100 | 冷却曲线 → 拟合 τ |

每换一档，其它变量全部冻结（同一压测核、同一姿态、同一电源模式）——这就是控制变量法。

### 3.3 一个必须讲清的混杂：风扇是闭环的

笔记本的 BIOS 风扇曲线本身就是个温度闭环：温度高 → 转速高 → 温度低。
于是"降频后温度降低"里，**有一部分是风扇自己降速造成的**（升温和降温路径不同）。

因此本轮拟合出的 `R_th` 是**闭环等效热阻**，含义是：
"在这台机器的固件策略下，功耗每涨 1 W，稳态温度涨多少 ℃"。
这恰好是**控制律需要的东西**（因为我们不接管风扇时，固件策略恒定）。

但要分离"风扇本身能不能打"，必须做**开环风扇扫描**（固定转速测温度）——
这需要 NBFC 能写 EC。装好 NBFC 后第二轮实验补这一项。

## 4. 拟合与选型

| 模型 | 形式 | 用途 | 判定 |
|---|---|---|---|
| M1 温度–功耗 | `T = a + b·P` | 求 `R_th = b` | R² ≥ 0.95 可用 |
| M2 功耗–频率 | `lnP = ln c + α·ln f` | 判断降频收益是否超线性 | α 的置信区间 |
| M3 功耗物理式 | `P/(V²·f)` 近似常数 | 验证 MSR/降压收益上限 | 变异系数 CV < 0.15 |
| M4 温度–cap | 二次 `T = a + b·cap + c·cap²` | **控制律直接反解** | 4 点以上必用二次 |

> 为什么不直接上多元回归？因为 `f`、`V`、`P` 三者共线（`P≈C·V²·f`），
> 塞进同一个方程会让系数失去物理意义（方差膨胀）。正确做法是**先降维到 `P`**，
> 再用 `P` 做单变量回归，`f`/`V` 只作为解释变量描述 `P` 的来源。

## 5. 从模型到控制律（反解）

给定目标温度 `T*`：

```
1) 求允许功耗：      P* = (T* − T_ref) / R_th
2) 求频率上限：      由 M2 反解 f* = (P*/c)^(1/α)，再换算成 cap%
                     或直接用 M4：解 a + b·cap + c·cap² = T*，取 [5,100] 内较大根
3) 若 M4 无解（满上限也压不住）：说明光靠降频不够 →
                     先上 Turbo 关，再上降压，最后才拉风扇（因为风扇要付噪声代价）
```

**为什么顺序是"降频 → 降压 → 风扇"**：
前两者只减少发热（噪声不变），后者用噪声换温度。在双目标意义下，
先用不花钱的手段把问题解决，再考虑花钱的手段，这就是 Pareto 前沿上的"角点优先"策略。

**动态部分（防振荡）：**

- 采样周期 ≤ `τ/4`（τ≈80 s → 采样 1 s 足够，决策周期 2–3 s）；
- 升速快、降速慢（`+60%/s` vs `−10%/s`）：温度是单调系统，宁可早降噪不急松手；
- 回差（hysteresis）3 ℃：避免在阈值附近来回抖；
- 斜率限速本身就是低通滤波，等效于给控制器加阻尼。

## 7. 本轮已知局限（下一轮补）

1. **风扇不可控**：本机（OMEN 15-ce0xx）EC 私有 → 需 NBFC，装好后可做开环风扇扫描，
   才能把 `R_th` 与风扇增益 `G_fan` 分离。
2. **无环境温度传感器**：用空载稳态温度代替，跨天对比需同室温。
3. **降压未纳入本轮**：MSR 写入有风险，需单独做"逐级 −20 mV + 压力测试"的稳定性实验。
4. **GPU 负载未做**：需要用 FurMark 等外部工具，程序只采集（这样数据才真实）。
5. **样本量小**：8 个稳态点做 4 参数模型已到上限，置信区间偏宽；下一轮每档重复 2 次取均值。

## 8. 数据挖掘：从特征变量到拟合函数（含神经网络）

这一节回答"用算法从数据里找出一个函数，用来自动调参"。

### 8.1 特征工程（先决定"喂什么"，比选模型重要）

| 候选特征 | 是否入模 | 理由 |
|---|---|---|
| 封装功耗 `P` | ✅ 主特征 | 热的唯一来源，把 `f`/`V`/`load` 的信息压缩成一个物理量 |
| 频率 `f`、电压 `V` | ❌ 不进同一方程 | 与 `P` 有 `P≈C·V²·f` 的硬约束，同时入模会造成方差膨胀（系数失去意义） |
| 风扇占空比 `fan` | ✅（NBFC 模式） | 散热能力的代理，决定 `R_th` |
| `P·fan`、`P·fan²` | ✅ | 热阻随风量下降，属**交互项**，比单独 `fan` 更贴物理 |
| `P²` | 可选 | 捕捉饱和/漏电带来的非线性 |
| 时间 `t`、阶段序号 | ❌ | 与温升无因果关系，只会学到实验顺序 |

### 8.2 模型家族与评分方式

全部用**按阶段留一交叉验证**（leave-one-stage-out）。为什么不能按样本随机划分：
同阶段的相邻样本高度自相关，随机划分等于"把答案放进训练集"，误差会虚低到 0.1 ℃ 级别 —— 这是数据挖掘里最常见的自欺。

| 模型 | 形式 | 备注 |
|---|---|---|
| 均值基线 | `T = T̄` | 下界参考，任何模型都必须显著优于它 |
| 线性 | `T = a + b·P` | 斜率 = 闭环等效热阻 |
| 二次 | `T = a + b·P + c·P²` | 捕捉饱和 |
| **阶梯表** | 分箱 + 单调化 | 分段常数，**可直接烧进固件查表** |
| 风扇线性/二次 | `T = a + (b + c·fan + d·fan²)·P` | 二维（风扇可控时） |
| **二维阶梯网格** | `(P 箱, fan 箱) → T` | 固件版二维表 |
| **MLP 神经网络** | 1 隐藏层 tanh，L2 + 动量 | 纯 Python 实现，无第三方依赖 |

所有线性基函数模型都做了三件必要的工程处理：

1. **列标准化**（z-score）：`P²` 与 `P·fan` 量级差几个数量级，不标准化会让正规方程病态、系数爆炸（实测出现过 CV-RMSE 9 万 ℃ 的假结果）。
2. **符号约束**：功耗项系数必须 ≥0、风扇项必须 ≤0。样本少时纯拟合会学出"风扇越大越热"，反解就会推荐"降风扇" —— 反物理且危险。
3. **共线性守卫**：任两列相关系数 >0.999（例如所有样本功耗都一样）时直接退化为均值，宁可承认"没信息"，也不给假精度。

### 8.3 实测对比（仿真数据，用于验证链路；真机跑完会自动重算）

BIOS 固定风扇策略（6 个稳态点，cap 阶梯）：

| 模型 | CV-RMSE ℃ | MAE ℃ | R² |
|---|---|---|---|
| 线性 `T=a+b·P` | **2.74** | 1.84 | 0.94 |
| 神经网络 MLP(h=6) | 3.02 | 2.09 | 0.93 |
| 二次 | 3.79 | 2.44 | 0.89 |
| 阶梯表（4 箱） | 8.87 | 7.32 | 0.37 |
| 均值基线 | 13.41 | 11.31 | — |

风扇可控（NBFC 两因子设计，9 个稳态点）：

| 模型 | CV-RMSE ℃ | MAE ℃ | R² |
|---|---|---|---|
| 二维阶梯网格 | **2.41** | 2.23 | 0.96 |
| 风扇二次 `T=a+(b+c·fan+d·fan²)·P` | 2.66 | 2.32 | 0.95 |
| 神经网络 MLP2D(h=8) | 2.93 | 2.32 | 0.93 |
| 风扇线性 | 2.99 | 2.57 | 0.93 |
| 线性（只用 P） | 4.54 | 3.97 | 0.84 |

**关于神经网络，结论要诚实：**

- 6–9 个稳态点训练 13–25 个参数的 MLP，理论上必然过拟合；实测它**没有赢过线性模型**，只是打平。
- 神经网络的真实价值在**样本量上来之后**：多机型、多环境温度、多负载类型（AVX/游戏/编译）、含动态序列时可到 10⁴ 量级样本，那时它能捕捉线性模型表达不了的交互。
- 所以产品策略是：**默认用可解释的线性/阶梯模型；样本量 ≥ 500 且 CV 显著更优时才启用 MLP**。模型文件格式已支持两种，切换只改一个字段。

### 8.4 反解：从模型到"该调到多少"

不是给一个点，而是给一条 **Pareto 前沿上的三档**（这才对应"温度与噪声的收敛"）：

| 目标温度 | 档位 | 频率上限 | 风扇 | 预测温度 | 噪声（相对满转） |
|---|---|---|---|---|---|
| ≤80℃ | 性能优先 | 100% | 80% | 79.1℃ | −4.8 dB |
| ≤80℃ | 静音优先 | 90% | 30% | 78.0℃ | −26.1 dB |

这一行就是整件事的核心权衡：**放弃 10% 频率上限，换来 21 dB 的安静**。
控制器的"静音/均衡/性能"三档，本质上就是在这条前沿上选点；固件里则可以直接存阶梯表（区间 → cap / fan）。

### 8.5 为什么 NBFC 实验必须做"两因子交叉"而不是阶梯

第一版 NBFC 计划是"固定 cap、只变风扇"的阶梯，CV-RMSE 高达 7.9 ℃。
原因：功耗 `P` 几乎不变时，`P` 的斜率不可辨识；留一验证把唯一一个不同功耗的点留出去后，模型只能外推，误差爆炸。
改成 **cap × fan 全因子（3×3）** 后，同样 9 个点，CV-RMSE 降到 2.4 ℃。

**结论：做二维模型，实验设计必须让两个因子交叉出现**（`lab/plan-nbfc-v1.json` 已按此写）。

### 8.6 踩过的坑（写下来避免重犯）

1. **未稳态样本混进稳态集**：低风量档位温度还在爬升（σ>3℃），当成稳态会把风扇斜率带偏 → 必须按 σ 剔除并报告剔除了哪些阶段。
2. **按样本做交叉验证**：自相关导致误差虚低。
3. **不标准化直接解正规方程**：系数爆炸。
4. **无符号约束**：学到反物理关系，反解给出错误建议。
5. **用分段常数模型做反解**：出现半格跳变（5% cap → 17℃ 落差），反解要换成连续模型，阶梯表另存给固件。
6. **一个 cap 对应两个功耗**（Turbo 开/关）却用一条 `cap→P` 直线拟合：反解必然错，必须用实测点分段插值。

## 9. 从模型到运行时（模型怎么驱动调速）

训练在 Python，推理在 C# —— 两边只靠一份 `model-*.json` 合约通信，运行时不需要 Python、不需要网络。

### 9.1 合约字段

| 字段 | 用途 | 运行时怎么用 |
|---|---|---|
| `steady_model` + `mu/sd/terms` | 稳态温度预测 `T̂(P, fan)` | 报告与自检；也可算"这档还差多少" |
| `dynamic.tau_s` | 一阶惯性时间常数 | 判断是否已稳态、决定换档后的等待时间 |
| `control_ladder[].T_hi` | 该档能保证的稳态温度上界 | 查表键（升序） |
| `control_ladder[].options[]` | 三档 `{cap, fan?, pred_T, spl_delta_db}` | 直接下发的控制量 |
| `fan_controllable` | 本机风扇是否可控 | 决定 `fan` 是否 `null`（BIOS 自控时不下发） |

### 9.2 控制律（前馈查表 + 超温收紧）

```
每 tick：
  T = hotspot
  if T ≥ CriticalTemp → 满转 + 强制降频（忽略策略表，安全优先）
  eff = TargetTemp                                   # 用户设的目标温度
  if T > eff+4  → eff -= 3                           # 实测超出，收紧一档
  elif T > eff+8 → eff -= 6
  elif T < eff-8 → eff += 2                          # 长期偏冷，放宽换性能
  仅当 |eff - 上次eff| ≥ 1 或 距上次查表 > 20s 时重新查表   # 避免抖动/刷 powercfg
  (cap, fan) = ladder[最小 THi ≥ eff].options[strategy]
  下发 cap（限频，走 powercfg）与 fan（有通道才下发，仍受 FanMin/Max 与斜率限制）
```

三个刻意的设计：

1. **查表而不是每 tick 反解**：反解要解方程、算根，运行时有噪声还会抖；阶梯表是离散的，天然带回差，`powercfg` 写入次数也从每秒几次降到每几十秒一次。
2. **前馈 + 有限修正**：`eff` 只用当前温度做 ±3~6℃ 的小幅收紧，不做全闭环积分，避免和风扇/固件的自身闭环打架（这就是 §3.3 说的混杂）。
3. **安全层永远压在最上面**：超温、温度失联、用户点停止，任何一条都直接绕过策略表。

### 9.3 为什么阶梯表要"另存"而不是运行时不间断反解

固件（EC/BIOS）里存不下浮点模型，只能存区间→档位；而且固件与用户态各算一遍容易不一致。
所以 `lab_model.py` 一次算好离散表，写进 JSON，**用户态与固件读同一张表**，结果可复现、可审计、可回滚。

### 9.4 目前还差什么

- 阶梯表按**稳态**生成；短时爆发（<τ）负载下它会略偏保守，后续可用 `tau_s` 做超前补偿（`StepDynamic` 已实现，尚未接入）。
- GPU 功耗未进模型（本机 GPU 由 BIOS 独立管理散热），双热源机型需要把 `P_gpu` 加为第二自变量。
- 环境温度未测：`T_amb` 变化会整体平移预测值，跨季节复用需要重跑或加偏置。

## 10. 可辨识性与序贯实验设计（跑多少档才够）

前九节讲的是「跑完之后怎么拟合」。这一节讲**跑之前和跑一半**要回答的问题：
这套数据到底能辨识出什么？再跑一档能换来多少？什么时候该停？
对应 `tools/lab_doe.py`。

### 10.1 为什么 CV-RMSE 回答不了这个问题

`lab_model.py` 报的留一 CV-RMSE 是**全区间平均**的拟合误差。它有两个盲区：

- **不知道局部。** 平均 2.4℃ 可能意味着有的区间 1℃、有的区间 7℃。而反解只落在少数几个点上，那些点准不准才是关键。
- **不知道还差多少。** 它只说"现在多准"，不说"再加一档能多准"，所以无法支持"要不要继续跑"的决策。

`lab_doe.py` 换一个量：**目标温度处的 95% 预测区间半宽**。

$$ \text{halfwidth}(x_*) = t_{0.975,\,\nu}\cdot\hat\sigma\cdot\sqrt{1 + \phi(x_*)^\top(\Phi^\top\Phi)^{-1}\phi(x_*)} $$

三个因子各有含义，缺一不可：

| 因子 | 含义 | 怎么改善 |
|---|---|---|
| $t_{0.975,\nu}$ | 小样本修正。$\nu=3$ 时是 3.18，$\nu=\infty$ 时是 1.96——**差 62%** | 只能加点（提高自由度） |
| $\hat\sigma$ | 单次观测的噪声。这是**地板** | **加点没用**，只能降噪（稳态窗口更长、负载更稳、重复采样） |
| $\sqrt{1+h}$，$h=\phi^\top(\Phi^\top\Phi)^{-1}\phi$ | 设计缺陷带来的额外不确定度（杠杆值） | 加点、补设计空档 |

用**预测区间**而不是**置信区间**：用户问的是"下一次实测会不会超过 85℃"，
这是单次观测的分布（含 $\sigma$），不是参数均值的分布。置信区间会窄一半以上，
拿它做安全判断会系统性乐观。

用**学生 t** 而不是正态：自由度为 3～6 时，正态近似会把区间低估 40%～60%。
这个量级的错误足以让"±4℃"变成"±7℃"，决策会完全反过来。

### 10.2 三个诊断量

**① 残差自由度 $\nu$** —— 低于 3 就**不许下结论**。
自由度小时 $\hat\sigma$ 由极少数残差估出，可能恰好接近 0（过拟合），
于是算出"±0.2℃，已经够准了，可以停"。这是最危险的一种假精度。
所以 `lab_doe.py` 里有硬规则：$\nu<3$ 一律输出"必须继续"，且不采信任何收益数字。

**② 条件数 $\kappa(\Phi)=\sqrt{\lambda_{max}/\lambda_{min}}$** —— 判断各项是否可辨识。
阈值按 Belsley–Kuh–Welsch：>30 中度共线、>100 严重。
注意必须报 $\kappa(\Phi)$ 而不是 $\lambda_{max}/\lambda_{min}$（后者是它的平方，
会把"其实还好"说得很吓人）。实测案例：BIOS 模式从 2 参数升到 3 参数（加 $P^2$）时，
$\kappa$ 从 1.1 跳到 11.8——二次项一进来共线明显加剧，这个数字提前警告了。

**③ 设计余量 headroom** —— 这是最有用的一个，也是最能省时间的：

$$ \text{headroom} = \frac{\text{halfwidth} - z\cdot\hat\sigma}{\text{halfwidth}} $$

分子是"加点能消掉的部分"，分母是总宽度，$z\hat\sigma$ 是**无论怎么设计都降不下去的噪声地板**。

- headroom > 30% → 设计主导，加点有效
- 15%～30% → 各占一半
- < 15% → **噪声主导，加点几乎无效**

这一条能直接否掉大量"我再跑几组实验"的冲动。实测 NBFC 数据 $\hat\sigma=2.01℃$、
$z\hat\sigma=3.95℃$，而最差点区间 ±5.65℃——headroom 只有 30%，意味着
**再完美的实验设计最多也只能把 ±5.65 收到 ±3.95**。想更准，只能压噪声。

### 10.3 一个必须分清的概念：实验点 ≠ 工况点

第一版实现犯过这个错，值得记下来。

评分候选点时，我用**候选点自己的风扇**去算区间收窄。结果推荐永远是
"cap100/f30"——因为 f30 是没测过的最远点，在它自己那里杠杆值最大、收益最大。
但这个逻辑等价于"**去哪采样最能提高该采样点的精度**"，答案当然是采样点自己，
于是实验设计退化成"重复采样已知最优点"，毫无意义。

正确的定义：

- **实验点** = 这一档施加的 (cap, fan)，它只负责**提供信息**；
- **工况点** = 程序实际会跑到的 (cap, fan)，它才是我们关心精度的位置。

所以评分是「在候选点采一条数据 → 看**工况点**的区间收窄多少」。

这个区分还救了另一个 bug：表格里显示区间 ±6.37℃、候选表里显示 ±6.4→±5.9℃，
读者会以为是两个不同的量。统一到工况点之后，两处数字自然对上了。

### 10.4 收益怎么算：为什么盯"最差目标"

候选点的收益定义为：

$$ \text{gain}(c) = \max_{T^*\in\mathcal{T}}\Big[\text{halfwidth}_{now}(x^*(T^*)) - \text{halfwidth}_{now+c}(x^*(T^*))\Big] $$

即**所有目标温度里，当前区间最宽的那一个点**的收窄量。

为什么不取平均：平均值会把"85℃ 处 ±6℃"和"75℃ 处 ±1℃"混在一起，
得出"平均收窄 0.6℃，不值得跑"——可那 6℃ 恰恰是最该修的。
安全相关的一直是瓶颈，不是均值。

$(\Phi^\top\Phi)^{-1}$ 的更新用 Sherman–Morrison 增量：

$$ (A+uu^\top)^{-1} = A^{-1} - \frac{A^{-1}uu^\top A^{-1}}{1+u^\top A^{-1}u} $$

不必重算逆矩阵，120 个候选 × 6 步 × 5 目标的完整序贯规划在几十毫秒内跑完。

### 10.5 序贯路线图：把"还差几档"算出来

单档收益 8%、总余量 34%，这两个数并列会让人困惑。真正的答案是一个路径：
贪心地连续走 6 步，每步用上一步更新后的 $(\Phi^\top\Phi)^{-1}$ 和 $\nu+1$，
得到边际收益递减曲线。实测 NBFC：

| 步 | 设定 | 累计耗时 | 瓶颈区间 | 相对 |
|---|---|---|---|---|
| 1 | cap100 / f80 | 2m49s | ±6.37 → ±5.87℃ | 8% |
| 2 | cap100 / f60 | 5m38s | ±5.87 → ±5.57℃ | 5% |
| 3 | cap100 / f100 | 8m27s | ±5.57 → ±5.36℃ | 4% |
| 4 | cap100 / f40 | 11m16s | ±5.36 → ±5.20℃ | 3% |
| 5 | cap 95 / f90 | 14m05s | ±5.20 → ±5.09℃ | 2% |

**14 分钟只换来 20% 的收窄**——这就是"不值得"的定量证据，
比任何定性判断都有说服力。同时也是产品设计的依据：
18 分钟的固定 8 阶段计划，在 $\hat\sigma$ 这么大的机器上已经很接近饱和了。

### 10.6 决策：三条硬规则 + 一个"税"

规则按优先级排（安全 > 精度 > 效率），顺序不可颠倒：

| 顺序 | 条件 | 输出 | 理由 |
|---|---|---|---|
| ① | 模型不成立，或 $\nu<3$ | **继续** | 此刻任何精度判断都可能是假精度 |
| ② | 目标解落在已测 cap 之外 | **继续** | 属外推，模型在那边根本不可信 |
| ③ | 单档收益 ≥0.5℃ **且** ≥20%，且 headroom ≥15% | **继续** | 两个条件缺一不可：绝对量够但基数大（±12→±11）没意义；相对够但绝对小（±0.5→±0.4）也没意义 |
| ④ | headroom < 15% | **停**（噪声主导） | 加点无效，该去压噪声 |
| ⑤ | 超温概率仍 >25% | **收紧策略** | 加档改善不了这点，该改参数 |
| ⑥ | 其余 | **停** | 边际收益低 |

第 ⑤ 条是这一版最重要的补充，来自一个真实的建模疏漏：

**反解只保证「预测值 ≤ 目标」，完全没管区间宽度。** 所以会给出这样的荒谬结论：
"70℃ 目标 → cap 90%，预测 69.7℃，看起来达标"，而实际区间 ±4.07℃，**超温概率 40%**。

于是引入"保守 cap"：留出不确定性裕量后，超温概率 ≤10% 的最激进设置。
两者之差就是**不确定性税**——因为模型不够准而白白让出的性能：

> 70℃ 目标：性能 cap 90%，保守 cap 85%，**要让出 5% 的 cap**（预测 66.3℃，超温 ≤10%）。
> 这 5% 就是模型不确定性收的税。想拿回来，得靠更准的模型，不是继续加档。

这个量把"建模精度"翻译成了"性能损失"，是整套方法论里对用户最直接的一个数：
**每降低 1℃ 的模型不确定度，能换回多少 cap。**

### 10.7 已知局限

- **c-optimal 而非 D-optimal。** 当前评分优化的是"固定工况点（平均风扇）的预测精度"，
  所以偏好离工况点近的设计点。如果程序会**动态调风扇**，就需要全局都准，
  那该用 D-optimal（最大化 $\det(\Phi^\top\Phi)$，偏好极端点）。
  这是一个真实的取舍，不是疏漏：单一工况用 c-optimal 更省实验，动态调节用 D-optimal 更稳。
- **$\sigma$ 假定不随新增点变化。** 新点如果偏离模型，真实 $\sigma$ 会变大，
  所以收益估计是**乐观**的。序贯路线图第 3 步以后的实际收益通常比预测更低。
- **只覆盖线性基底。** 阶梯表和 MLP 没有解析的形式，无法算信息矩阵。
  这类模型的局部精度只能靠留一残差 + 局部样本密度经验估计（尚未实现）。
- **候选网格是离散的。** 只在 cap 步进 5%、fan 步进 10% 上搜，
  真正的最优设计点可能落在格子之间。实际影响很小（收益曲线很平）。

## 11. 短时实验：3/5/10 分钟怎么压缩（以及什么时候不能压）

§3 的实验设计要每档等到稳态（≥3τ），8 档要 18 分钟。这一节回答"能不能只跑 5 分钟"。
对应 `tools/lab_transient.py`（辨识）与 `tools/validate_transient.py`（用已知真值校准设计）。

### 11.1 硬约束：5 分钟到不了稳态

一阶惯性 `dT/dt=(T_ss−T)/τ` 的解是 `T(t)=A+(T₀−A)e^(−t/τ)`。走到稳态 95% 需要 `3τ`。
笔记本 τ 通常 60~120s，所以**单段至少 180~360s**。

5 分钟 = 300s 要分 4 段，平均每段 75s ≈ 1τ，只走到 63%。
所以"5 分钟测稳态"在物理上就不成立；任何声称做到的工具都在偷偷用段尾均值，
而段尾均值在 1τ 处会**系统性低估 6~11℃**（实测见 §11.4 表）。

### 11.2 换目标：不等稳态，把曲线推到稳态

不测 `T_ss`，而是测**轨迹**，再拟合指数把渐近值算出来：

    τ·dT/dt = (T_amb + R·P) − T
    ⇒ T(t) = A + (T₀ − A)·exp(−(t−t₀)/τ),   A = T_amb + R·P

**关键实现技巧：对固定 τ，模型对 (A, T₀) 是线性的。**

    T = A·(1−u) + T₀·u,    u = exp(−t/τ)

于是求解变成「外层一维搜 τ → 内层解 2 参数线性最小二乘」：

- 不需要非线性优化器，不会陷局部极小；
- 内层是闭式解（2×2），几百次网格搜索毫秒级完成；
- τ 的网格用对数等距（4~900s），再在最优处几何二分细化。

多段联合时给每段一个 A、共享一个 τ，目标函数是 `ΣSSE_k(τ)`，仍是 1 维——
因为给定 τ 后各段完全解耦。这也顺带成了"一阶假设是否成立"的检验：
逐段独立 τ 若显著降低 SSE，说明 τ 随工况变化（风扇转速变→散热能力变），
那 A 就该用逐段 τ 而不是共享 τ。

### 11.3 不确定度必须传播两层

A 的区间有两个来源，漏掉任何一个都会低估：

| 来源 | 计算 |
|---|---|
| 观测噪声 | `t(0.975,ν)·σ·√[(XᵀX)⁻¹]₁₁`，ν=n−2 |
| **τ 的不确定度**（常被漏） | τ 的 profile 置信集 `SSE(τ)≤SSE_min(1+F/ν)` 内，A(τ) 的漂移范围 |

合成：`half = √(lin² + profile²)`。

为什么必须做第二层：τ 与 A 强相关（τ 大 → 曲线更平 → 推到更远的 A）。
只报线性协方差会给出"±0.1℃"这种漂亮但假的精度。实测某些段的 profile 项比线性项大 3~10 倍。

### 11.4 用已知真值校准设计（不占用真机时间）

`tools/validate_transient.py` 用物理仿真器（其稳态可解析求出）跑三种计划，
把外推值与真值对比。这样"该跑几分钟"变成一个可以离线优化的问题：

| 计划 | 预算 | τ 估计 | **外推最大误差** | RMSE | 直接取尾均值的误差 |
|---|---|---|---|---|---|
| quick3 | 3 min | 47s | **7.48℃** | 5.12℃ | 14.45℃ |
| quick5 | 5 min | 53s | **1.03℃** | 0.66℃ | 10.50℃ |
| quick10 | 10 min | 56s | **1.14℃** | 0.52℃ | 6.10℃ |

三个结论：

1. **5 分钟可行，但只因为它做了外推。** 同样 5 分钟的数据，直接取尾均值误差 10.5℃，
   外推后 1.03℃ —— 差一个数量级。这是"短时实验"与"短时瞎猜"的分界线。
2. **3 分钟不可行。** cap50 段只有 45s（0.44τ），误差 7.5℃。
   单段短于 0.7τ 时外推就不可信，这不是算法问题，是信息不足。
3. **10 分钟的边际收益很小**（1.14℃ vs 1.03℃），但它的价值不在精度而在
   **多一个功率层级**（3 个满载档 vs 2 个），能检验线性/二次项。

一个反直觉发现：τ 估计偏小 28%（53s vs 真值 74s），但 A 依然准（1℃）。
原因是拟合的 τ 主要由曲率决定，而 A 由"曲线最终落在哪"决定；
BIOS 模式下风扇随温度加速，等效 τ 本来就不是常数。
**所以不要用 τ 的准确度去判断 A 的可信度。**

### 11.5 段分配是设计变量，别拍脑袋

同样 300 秒，怎么切段差别很大。测了四个备选：

| 分配（秒） | cap 档 | 最大误差 |
|---|---|---|
| **20/150/60/70** | 100, 60 | **1.03℃** |
| 20/130/55/55/40 | 100,80,45 | 1.28℃ |
| 18/100/55/55/72 | 100,75,45 | 2.07℃ |
| 15/110/60/60/55 | 100,75,50 | 2.46℃ |

规律很清楚：**误差集中在最高温段，且与那段时长单调负相关**
（100s→−2.07℃，115s→−1.29℃，130s→−1.28℃，150s→−1.03℃）。
所以预算该往最高功耗段倾斜，而不是平均分配。最终 quick5 采用 `20/150/60/70`。

### 11.6 短时数据建不出连续模型，只能建阶梯表

`lab_model.py` 要求 ≥4 个满载阶段做留一交叉验证。5 分钟只有 2 个满载档，它会拒绝。
这不是缺陷——**2 个功率点做不了模型族比较，只能定 T₀ 和 R_th**。

所以 `lab_transient.py` 自己导出策略文件，且用**阶梯表**而不是线性形式：

- 线性 `T=T₀+R·P` 拟合 3 个点必留残差，实测 cap60 偏 1.6℃（折到温度 2.2℃）；
- 阶梯表直接用每档实测的渐近温度，**零模型误差**；
- 控制律本来也只在离散档位上跳，连续函数是多余的。

同时**档位只在实测 cap 上给，中间不插值**。这条是踩出来的：
线性插值 cap 60→100 得 cap80 → 28.5W，真值 22.3W，温度偏 5℃。
原因是 `P≈C·V²·f`，V 随 f 上升，且 cap=100% 会打开 Turbo 出现台阶。
宁可按实测点给粗档位，也不给一个错的中间档。

### 11.7 什么时候必须回到全量实验

短时实验能回答"模型长什么样、量级对不对"，不能回答"18 分钟那套阶梯表准不准"。
必须跑全量的情形：

- 需要 4 档以上的精细阶梯（每档间隔 <10% cap）；
- 需要分离 Turbo 开/关的影响（同 cap 两个功耗点）；
- 需要 NBFC 两因子设计（cap×fan 交叉，验证风扇增益）；
- 要把 `lab_doe.py` 的可辨识性预判跑起来（它需要真实稳态段）。

实践建议：**先跑 quick5 判断这台机器的量级与 τ，再决定要不要花 18 分钟**。
如果 quick5 的线性残差 >2℃ 或 τ 极短（<40s，说明散热响应快、噪声占比大），
那全量实验的收益也有限，应该先去压噪声（拉长稳态窗口、重复采样），而不是加档。

## 12. 热链路诊断：5 分钟压测定位故障环节（lab_diagnose.py）

> 场景：用户拿到一台"满载就 97℃"的机器，问的是**哪个环节坏了**——硅脂？风扇？风道？
> 还是供电根本给不满？这决定产品该围绕什么做（调速策略 / 清灰指引 / 换硅脂建议 / 降级运转参数）。

### 12.1 两热阻模型与可辨识性

```
T_die = T_amb + R1·P + R2(fan)·P
        R1 = die↔散热器（硅脂/压装）   正常 0.1~0.35 K/W
        R2 = 散热器↔环境（鳍片/风量）  正常 0.15~0.4 K/W
        tau_die ~1-2 s；tau_hs ~80-150 s
```

**关键辨识事实**：稳态里 R1、R2 只以和出现（(R1+R2)·P），靠温度稳态永远分不开。
唯一能分开 R1/R2 的观测是**掉载瞬间的温度塌落**：功率掉、die 热容 τ~1s 立即跟着掉、
散热器 τ~100s 还没动——这一瞬间的 (ΔT, ΔP) 对就是 R1 的斜率：

```
R1 = (T_段末 − T_过渡) / (P_段末 − P_过渡)     （掉载后 0.8~6 s 内的干净样本）
```

它**不需要 T_amb**、不受风扇状态影响、5 分钟就能测准（deep1 实测 1.76~1.83，
与手算 1.8 一致）。注意过渡窗口不能拖长：超过 ~10s 后冷却漂移会给 R1 加正偏置。

### 12.2 判定树（阈值来自 45W 级笔记本工程常值）

| 节点 | 判据 | 结论 |
|---|---|---|
| N1 | R1 ≥ 0.8 K/W（≥1.4 重度） | TIM/压装断链 → 换硅脂级，软件只能降功率 |
| N2 | R2 ≥ 0.7 且 ΔT(风扇60→100) < 6℃ | 风扇/鳍片/风道 → 清灰/换风扇/疏通风道 |
| N3 | 贴墙 ≥50% 且 R1 正常 | 整体散热不足（温度墙）→ 必须压功率 |
| N4 | P_ss ≤ 0.85×设计功率 且不贴墙 | 电气功率墙（PL/供电）→ 散热无恙 |
| N4b | 早期→稳态功率回落 ≥2W 且贴墙 | 功率被温度墙压住（伴随发现，区别于电气墙） |

**R2 是风扇侧主判据、ΔT 只做次级确认**：5 分钟档渐近线外推误差 ±2~3℃
（τ 与 A 强相关），但 R2=(A−T_amb)/P−R1 的误差只有 ±0.1。
风扇杠杆被贴墙掩盖时（ΔT≈0 且 pin 高）N2 自动改报"被掩盖"，不会误判成风扇故障。

### 12.3 稳态外推（为什么 5 分钟够）

散热器 τ~100s，90~120s 的段走不完平衡（fanfault 仿真：尾窗均值 59.9℃ vs 真稳态 72℃）。
每段拟合 `T(t)=A+C·e^(−t/τ)` 外推渐近线 A；拟合窗起点取**功率稳定点+2s**
（躲开睿频/调节瞬态；无瞬态提前到 10s 增加曲率信息）；
贴墙/已稳的段（|C|<3℃ 或拟合不显著）退回尾窗均值——deep1 的 D1~D3 全部走了这条路。

### 12.4 验证（tools/lab_diagnose.py --selftest）

4 个仿真场景（含与真实机同参数的 timfault）+ 真实 deep1，**换 10 个随机种子 40/40 全对**：

| 案例 | R1 | R2 | ΔT | 判定 |
|---|---|---|---|---|
| sim-healthy（50W 全释放） | 0.21 | 0.53 | 10.9 | 健康 |
| sim-fanfault（风道堵） | 0.26 | 1.25 | 5.6 | 风扇/鳍片/风道 |
| sim-timfault（硅脂干涸） | 1.83 | 0.14 | 0.2 | TIM 重度 + 温度墙掩风扇 |
| sim-pllimit（电气墙） | 0.24 | 0.49 | 8.1 | 电气功率墙 |
| **real deep1（本机）** | **1.76** | **0.32** | 未测 | **TIM 重度 + 温度墙限功率** |

### 12.5 真实机结论（deep1，19 min 真机数据）

- **R1 ≈ 1.8 K/W（正常 7 倍）→ 硅脂干涸/压装不实，全机热量堵在芯片里**；
  R2 ≈ 0.3 → 散热器/风扇侧其实健康。这纠正了上一轮"R2≈0.76、风扇侧占大头"的误判
  （当时把冷却平台 48℃ 当成了散热器温度，实际那是 T_hs + R1·P_idle）。
- **35W 不是电气 PL，是温度墙**：早期 40W→稳态 35W 的回落与 97% 贴墙样本共同指向
  温控削功率；P_eq = (96−24)/(R1+R2) ≈ 34.6W，与实测 34.9W 吻合。
- 50W 设计功率被热链卡死：反事实（R1→0.25）下 50W 满载 ≈ **48℃**，当前功率下 ≈ 37℃。
  **软件层杠杆 ≤3℃；换硅脂一次 = 50℃ 级收益。**
- 降级运转（换硅脂前的"勉强合理"）：贴墙 35W 可跑但零余量；要 90℃ 需功率 ≤ 32.5W
  （powercfg cap 已证无效，软件侧只剩关睿频/限负载两条路）。


已知局限：T_amb 需输入（只影响功率预算绝对值，不影响故障定位）；ΔT 精度 ±3℃

### 13.2 三档散热策略（tools/thermal_policy.py）

三档旋钮（噪声↔温度↔性能的取舍本质）：

| 档 | 温度**上限** | 风扇上限 | 空闲风扇 | EPP | PL2 倍率 | τ | 功率预算 | 噪声 |
|---|---|---|---|---|---|---|---|---|
| 静音 silent | 88℃ | 55% | 20% | 200 | 1.15 | 8s | 最低 | 最低 |
| 平衡 balanced（默认）| 88℃ | 75% | 30% | 128 | 1.25 | 16s | 中 | 中 |
| 性能 performance | 90℃ | 100% | 40% | 0 | 1.35 | 32s | **最高** | 最高 |

功率预算公式：`P_budget = (T_ceiling − T_amb) / (R1 + R2(fan_max))`。

**关键理解（v1.4 纠偏）：温度上限不是"要压到的目标值"，它是允许的最高温度。**
温度是"功率 × 热阻"的**结果**，不是原因：`T_ss = T_amb + R·P`。所以想要性能，
该做的是"在温度上限之内把功率放到最大"，而不是"把温度压到最低"。

> ⚠️ **v1.3 的错误设计**：性能档曾把目标温度设为 75℃（三档里最低），文档还写成
> "性能档不是功率最高，而是温度最低"。这条推理方向反了——`P_budget=(75−24)/R`
> 是三档里**最小**的，于是"性能模式"风扇最响、功率最低、交付频率最低，等于最差的
> 组合。v1.4 已改为：性能档 90℃ 上限 + 风扇 100%（R2 最小）→ P_budget 最大。

**解耦原则（v1.4）**：每个旋钮只管一件事，不要用温度上限去表达声学偏好。
- 温度上限 → 只决定功率预算的天花板（静音/平衡同为 88℃，性能 90℃）
- 风扇上限 → 决定噪声与 R2（55/75/100%）
- EPP → 决定升频积极度，也就是"点一下多久有反应"（200/128/0）
- PL2 倍率 + τ → 决定短时爆发能冲多高、撑多久（1.15×8s / 1.25×16s / 1.35×32s）

静音与平衡共用同一温度上限，只靠风扇/EPP/PL2 区分——这样"想安静"不会顺手把
性能一起削掉。硬性不变量：`P_budget(静音) < P_budget(平衡) < P_budget(性能)`，
`tplab selftest` 会校验它（两种机型：R1=0.21 健康机 / R1=1.76 断链机）。

默认「平衡」如何做到「噪声别太大太久」：风扇上限 75%（不呼啸）+ 目标 82℃
（保留功率）+ 空闲 30%（低负载降底速，噪声不持续）。

推荐档逻辑：健康/电气墙 → 平衡；硅脂断链/整体不足（风扇对 R2 的作用被坏掉的
R1 挡住，硬拉风扇只增噪不降温）→ 静音档保命，直到用户换硅脂。

### 13.3 本机闭环示例（deep1）

R1=1.76（重度断链）→ 判定 tim_fault → 推荐静音档：上限 88℃、风扇 ≤55%、
功率预算 29.9W（把 35W 贴墙降到 88℃ 安全线内）。

健康机（R1=0.21、R2 0.48→0.30）三档功率预算 **108.3 / 115.3 / 129.4W**（静音/平衡/性能），

两机型的 50W 设计功率在健康机上三档都能全额释放，断链机上三档都会被 R1 卡到 ~30W

### 13.5 精细调控参数模型（control_model.py）—— 把目标翻译成 CPU 旋钮

> §13.2 的「功率预算」只是抽象目标，真正落到硬件上是 Intel 的 MSR 控制字。
> 关键纠偏：**本机实测 `powercfg PROCTHROTTLEMAX` 无效**（写值读得回但 CPU 不认），
> 真正生效的闸是 PL1/PL2（MSR 0x610）、降压（MSR 0x150）、EPP（MSR 0x773）；
> GPU 则用 nvidia-smi/Afterburner 单独调。**Windows 电源管理只是粗层（第 1 层），
> 且在本机失效**，精细平衡靠的是 CPU/GPU 的 MSR/驱动级调控（第 2/3 层）。

**控制面分层（哪些参数软件可控，哪些不可控）：**

| 层 | 名称 | 软件可控 | 工具 | 旋钮 | 说明 |
|---|---|---|---|---|---|
| 0 | 硬件固有 | ❌ | 物理换件 | TDP/R1(硅脂)/散热模组/出厂电压曲线 | 软件只能识别或绕开（如 deep1 靠降功率） |
| 1 | Windows 电源管理（粗） | ✅ | powercfg | 电源计划/最大处理器状态%/散热策略 | **本机 PROCTHROTTLEMAX 实测无效**，粗杠杆 |
| 2 | **CPU 精细调控（细）★主力** | ✅ | ThrottleStop/直接写 MSR | 降压0x150 / PL1 0x610 / **PL2 0x610** / **Time-τ 0x610,0x618** / EPP 0x773 / 睿频倍率 0x1AD | 真正生效的温控闸，独立于 Windows |
| 3 | **GPU 精细调控（细）** | ✅ | nvidia-smi(功率墙/温度目标) / Afterburner(频率/电压曲线) | 功率墙% / 频率偏移 / 电压曲线 / 温度目标 | 独立于 CPU；降 GPU 功耗=给共享散热腾 CPU 余量 |
| 4 | 外部（仅识别） | ❌ | — | 环境温度 T_amb / 散热底座·支架 | 改不了，只当输入或建议用户改善 |

> 一句话：**异常识别跑在「出厂默认逻辑」（第 1 层）只观察；调控伸到第 2/3 层 MSR/驱动级，
> 而不是只有 Windows 自带的电源管理。** 第 0/4 层不可软件控制，只能物理改或当输入。

**物理映射（P ∝ V²·f，与 §12 两热阻模型衔接）：**
```
P(V,f) ≈ P_static + (P_dem − P_static)·(V/V0)²·(f/f0)·epp_k
T_ss    = T_amb + (R1 + R2(fan))·P_op
P_op    = min( 工作负载需求(经降压/降频/EPP) ,  PL1 )
```

**6 个旋钮 + 优先级（性能代价最小，逐级动用）：**

| 优先级 | 旋钮 | 机制 | 性能代价 | 影响 |
|---|---|---|---|---|
| ① | 降压 undervolt | P∝V²，同频降功耗 | **零**（首选） | 温度↓，性能不变 |
| ② | 风扇占空比 | 降 R2 | 只增噪声 | 温度↓ |
| ③ | Speed Shift EPP | 偏置 OS 选频 | 软、近似无损 | 小幅降功耗 |
| ④ | PL1 硬闸 | 包功率持续硬上限 | 牺牲性能 | 温度↓（代价最高，最后用） |
| ⑤ | **PL2 突增上限**（与 ⑥ 独立） | 短时 burst 功率上限 | 影响爆发高度 | 决定 boost 冲多高 |
| ⑥ | **Time/τ 时长**（与 ⑤ 独立） | PL2 能持续多久回落 PL1 | 影响噪声持续 | 管「噪声太久」 |

> **PL2 与 Time 是两个独立旋钮**，不能合并：PL2=burst 能冲多高（×P_op 倍率），
> τ=burst 能撑多久（静音 8s / 平衡 16s / 性能 32s；Intel 该字段 log2 编码，只能用 2 的幂）。可「PL2 高但 τ 短」（一踩就松，风扇不啸叫），
> 也可「PL2 平但 τ 长」（长时间维持 boost）。两者分别放在 MSR 0x610 的不同字段。

**求解结果（真实机 deep1，R1=1.76）：**
- 静音：降压 -80mV → **87.7℃ @ 100% 性能**，风扇仅 55%（quiet），PL2×1.15 / τ=8s。← 降压是这台机器的救命杠杆
- 平衡：降压 + EPP=46 → 82℃ @ 93% 性能，PL2×1.25 / τ=16s
- 性能：降压 + EPP=108 → 75℃ @ 83% 性能，PL2×1.35 / τ=32s
- GPU（第 3 层，各档）：静音功率墙 70%/80℃、平衡 85%/83℃、性能 100%/86℃（降 GPU 功耗给 CPU 让热容）

**核心认知**：性能档 ≠ 功率最高，而是温度最低（压温度=限发热，功率预算反而最低）；
三档本质是「用多少温度换多少功率和噪声」。默认平衡靠三旋钮实现「噪声不大不持久」：
风扇≤75% 不啸叫 + 目标 82℃ 留性能 + 空闲降到 30% 让噪声不持续 + PL2/τ 调短避免 boost 过夜。

**执行层映射**：降压/PL1/PL2/Time → MSR（需内核驱动/管理员）；EPP → MSR 0x773 或
powercfg 效率策略；频率上限 → TURBO_RATIO_LIMIT 或 OS 策略；风扇 → NBFC/EC；
GPU 功率墙/温度目标 → `nvidia-smi -pl <W>` / `nvidia-smi -gtt`（或 Afterburner）。
不同机器暴露的 MSR 不同，故 `optimize()` 同时给出 PL1 版与等效频率上限版两套答案，
并附 `gpu_policy()` 给出 GPU 第 3 层推荐模板。

### 13.6 运行时落地（C#，v1.3）

上面是 Python 侧的求解模型；桌面工具运行时用 C# 直接写 MSR 实现同一套旋钮：

| C# 类 | 职责 |
|---|---|
| `MsrAccess` | 反射对接 LHM 0.9.4 `Ring0.ReadMsr(uint, out uint eax, out uint edx)` / `WriteMsr(uint, uint eax, uint edx)`，64 位读写 + `Ring0.Open()` 兜底 |
| `CpuControlService` | PL1/PL2/Time（0x610）、EPP（0x773）、睿频倍率（0x1AD）的读改写 + 读回校验 + 原始值快照/还原 |
| `AutoCpuController` | 在线估热阻 R → 前馈目标功率 + 温度反馈微调 PL1；PL2/Time/EPP 按档位；无功耗传感器时退化为纯反馈 |
| `ThermalEngine.UpdateCpu` | 每 3 秒闭环一次；超温无条件压 PL1；退出/停止还原 |

**关键修正**：旧 `UndervoltService` 按 1/2 参找 `ReadMsr`，与 LHM 真实 3 参签名不符，
导致读回恒为 0、降压校验必然失败；v1.3 已按真实签名重写并抽成共享 `MsrAccess`。
离线自检：`tplab selftest`（验证 0x610/0x773 编解码与自动控制器收敛）。

### 13.7 为什么不看温度、要看「交付性能指标」（v1.4）

温度是**滞后且不唯一**的代理量：同一个 82℃ 既可能是 15W 轻载（风扇低转），
也可能是 45W 满载（风扇高转）。单看温度无法回答"还能不能更快"。所以 v1.4 把控制
目标从"守住温度"改成"最大化交付频率，温度只当约束"，并直接测量三件实事：

| 指标 | MSR | 读法 | 回答什么问题 |
|---|---|---|---|
| **有效频率** | `0xE8` APERF / `0xE7` MPERF | `ΔAPERF/ΔMPERF × 基准频率` | 真正拿到手的时钟是多少（含睿频、含降频） |
| **包功率** | `0x611` PKG_ENERGY_STATUS + `0x606[12:8]` 能量单位 | `ΔE × unit / Δt` | 实际功耗，与 PL1 比即知功率墙是否在顶 |
| **当前倍频 / 上限** | `0x198` PERF_STATUS[15:8]、`0x1AD` TURBO_RATIO_LIMIT | `ratio × 100MHz` | 是不是已经顶到睿频上限（再给功率也没用） |
| **降频标志位** | `0x64B` / `0x1B1` bit0/bit2/bit4 | 逐位解读 | 是否真的因为温度被强制降频 |

> APERF/MPERF 是 **per-LP** 计数器，读某个核必须在该核上执行。实现里用
> `SetThreadAffinityMask` 轮转绑核（每次只绑一个核、读完立刻恢复），
> 与上一次同核采样做差，因此 1Hz 的采样开销可忽略。

**由指标反推的「谁在限制变快」四个结论，直接决定该动哪个旋钮：**

| 判定 | 依据 | 该做什么 |
|---|---|---|
| 温度墙 | 降频位被置 / 温度已贴上限 | **降** PL1（加功率只会更热，无效） |
| 功率墙 | 包功率 ≥ PL1×0.97 | 温度还有余量就**升** PL1（直接换性能） |
| 频率上限 | 当前倍频 ≥ 睿频上限 | **保持**（加功率换不到频率） |
| 轻载 / 未受限 | 负载低且有效频率远低于基准 | 保持或缓慢抬升，把余量吃满 |

这就是 v1.4 的控制律：`温度是约束，有效频率是目标`。旧版只看温度，
会在"功率墙 + 温度有 10℃ 余量"的情况下继续降 PL1，白扔性能；也会在
"频率已顶睿频上限"时瞎调功率，白烧电。

对应代码：`src/ThermalPilot.Core/PerfMetrics.cs`（采样 + 判定）、
`AutoCpuController.Update(..., PerfSample?)`（按判定驱动方向）、
`ThermalEngine.UpdateCpu`（3 秒闭环 + UI 回显"有效 xxxMHz · 包功率 xxW → 谁在限制"）。

**关于"响应快、多任务不卡"**：这类主观感受主要由 ①有效频率的**爬升速度**
（EPP 越低爬得越快）、②是否被温度墙打断（降频一次就是一次卡顿）、
③内存/uncore 频率决定，而不是由温度数字决定。所以"更凉快"不等于"更流畅"，
除非那份凉快是靠降 R（风扇）而不是靠削 P（功率）换来的。

## 14. 参数体系：全局 / 高级 / 预览 三层（v1.5）

### 14.1 为什么必须分三层

v1.4 之前，同一个语义在不同面板各有变量：

| 语义 | 旧版出现的地方 | 后果 |
|---|---|---|
| 取向 | 顶栏 `ProfileCombo`、标定页 `PrefQuiet/PrefBalanced/PrefPerf`、高级页 `AutoProfileBox`、`PolicyStrategy` | 改一处以为生效了，实际生效的是另一处 |
| 目标温度 | `TargetTempC`（PID 用）、`AutoTargetC`（自动用） | 两个"目标温度"，语义不同却同名 |
| 频率控制 | `EnableFrequencyControl`、`EnableCpuTuning`、`AutoCpuMode`、`UsePolicyModel` | 四套控制器同时写，互相覆盖 |

更根本的问题在 `MainWindow.BuildConfigFromUi()`：首行 `var cfg = _engine.Config;`。
它把界面控件逐个写进**引擎正在使用的对象**，所以"改控件" 与 "写硬件" 之间没有边界，
既没有校验窗口，也没有回退点。

### 14.2 三层定义

```
Layer G（Global）   —— 全程序唯一一份，只在「① 策略」页修改，随配置持久化
Layer A（Advanced） —— 写硬件但需要专业知识，集中在「③ 高级」页
Layer P（Preview）  —— 只读派生（标定曲线 / 自动决策 / MSR 现值 / 交付指标），永不进 Diff
```

代码落点：

| 类 | 职责 |
|---|---|
| `ParameterCenter` | 持有 `Draft` / `Committed`，提供 `Diff()` / `Validate()` / `Apply()` / `Discard()`；`Edit()` 是唯一的草稿写入口 |
| `ParamConstraints` | 每条参数的机理范围（含"为什么"）+ 交叉约束 + 预测型约束 |
| `ProfilePreset` | 取向 → 一组推荐值的**一次性**展开；套用后手改不会被覆盖 |
| `ControlChannels` | 三个控制通道互斥归一化 |

### 14.3 唯一的写入路径

```
UI 控件 → BuildConfigFromUi() → _pc.Draft（仅内存）
                                      │
                          点「应用」    ▼
                            ParamConstraints.Validate(Draft, R, maxTurbo)
                                      │
                       有 Block ──────┴────── 无 Block
                          │                     │
                    拒绝，不提交            Committed = Draft
                          │                     │
                  状态栏 + 校验区显示原因    engine.ApplyConfig(Committed)
```

`Diff()` 基于**值**而不是"点过没点过"：改回原值待应用数自动归零。
底部「待应用」条列出 `标签 旧值 → 新值`，另有「放弃草稿」把 Draft 整体回滚到 Committed。

### 14.4 约束清单（机理来源）

| 参数 | 范围 | 来源 |
|---|---|---|
| τ | {1,2,4,8,16,32,64}s | 0x610 time 字段 log2 编码 |
| EPP | 0–255 | 0x773 EPP 8 位 |
| PL1 | 5–60W | 平台持续功耗能力 |
| PL2 | [PL1, 2×PL1] | 突增语义 + τ 窗口温升 |
| 睿频倍率 | 8–40，且 ≤ 0x1AD 原值 | 芯片能力，超限被静默截断 |
| 降压 | −150–0 mV | 负载瞬变稳定性 |
| 温度上限 | 70–95℃，且 ≥ 室温+15 | TJmax−5 / 功率预算不得为负 |
| 风扇上限 | 30–100% | 低于 30% 满载散不出去 |
| 安全线 | 80–99℃，且 > 温度上限 | 必须低于 TJmax，且不能高于上限（否则一开始就强制降档） |

预测型约束（需要 `REstimate`）：

```
T_pred = T_amb + R · PL1
T_pred > 95℃        → Block  （加功率只换来更高温度，频率不会涨）
T_pred > T_ceiling  → Warn   （功率墙与温度墙互相打架，频率会来回抖）
```

本机 R≈1.8 → PL1 上限被压到约 39W；健康机 R≈0.3 → PL1 45W 合法。

### 14.7 取向绑定（v1.6）：预设是基线，手改是增量

「静音 · 自定义」不是一个独立的第四档，而是**基线 + 增量**的合成显示。

```
ProfileName = "静音"        ← 基线，持久化的只有一个字符串
其余各项值                   ← 增量，隐含在配置里，不额外存字段
        │
        ▼  ProfileBinding.Overrides(cfg)
「静音 · 自定义」+ 明细[{温度上限 88→84℃}, {EPP 200→128}]
```

为什么不用 sticky 布尔标记（`IsCustomized=true`）：

| 方案 | 改回原值后 | 重启后 | 切换基础取向 |
|---|---|---|---|
| sticky 标记 | 仍显示"自定义"（假信号） | 依赖持久化字段 | 标记含义错乱 |
| **按值现算（采用）** | 自动退回纯预设 | 无需字段，天然正确 | 比较基准跟着取向走 |

比较项与基准（`ProfileBinding`）：

| 比较项 | 基准 | 说明 |
|---|---|---|
| 温度上限 | `ProfilePreset.Values(name).TceilingC` | 88 / 88 / 90 |
| 风扇上限 | `.FanMaxPct` | 55 / 75 / 100 |
| EPP | `.Epp` | 200 / 128 / 0（**自动模式下跳过**） |
| τ | `.TauS` | 8 / 16 / 32（**自动模式下跳过**） |
| PL2 倍率 | `.Pl2Ratio` | 1.15 / 1.25 / 1.35，仅 PL1>0 时比较（**自动模式下跳过**） |
| 风扇/降频曲线 | `Presets.Fan/Freq(name)` | 逐点比较，容差 0.01 |

**为什么要跳过三项**：智能自动模式下 `AutoCpuController` 每 3 秒按档位重新下发
EPP/τ/PL2，高级页手填的值根本不参与下发。把它们算进自定义，会让 chip 永远挂着
「自定义」却怎么点「回到预设」也消不掉 —— 那是比没有标记更糟的假信号。

显示位（同一份判定喂给四处，口径统一）：

| 位置 | 显示 |
|---|---|
| 顶栏 chip | `● 静音`（蓝）/ `◐ 静音 · 自定义`（橙），悬浮出明细 |
| 策略页 ① | `草稿：静音 · 自定义　上限 84℃ · 风扇 5–55%` + `自定义项：温度上限 88℃→84℃、EPP 200→128` |
| 标定页 | `跟随全局取向 静音 · 自定义` |
| 高级页 ① | `全局取向「静音 · 自定义」· 上限 84℃ · 室温 24℃` |

「回到预设」= `ProfilePreset.Apply(cfg, 选中项)`，清空全部增量；chip 随即变回蓝色单名。

> v1.7 把这里的"隐含增量"升级成显式持久化的配置档实例（`settings.json → Profile`），
> 并把判定收敛成一条路径。见 §14.9。

### 14.8 界面文字的分层原则（v1.6）

静态说明（设计缘由、物理语义、历史错误回顾）一律进 `ⓘ` 的 ToolTip；
动态事实（当前值、功率预算、校验结论、待应用 diff）留在页面上。
判据很简单：**每次打开都要读的留下，只在第一次要读的收起来。**

XAML 侧用两个样式统一：`CardTitle`（卡片标题）+ `InfoIcon`（`ⓘ`，Cursor=Help）。

### 14.9 配置档实例（v1.7）：增量持久化 + 基线锁定

v1.6 的增量是**隐含**的（按"当前值 vs 预设值"现算，不落盘）。它解决不了三件事：

1. **升级会吃掉用户的值**：整份配置存盘时，基线一改，用户没动过的项也跟着变成老值；
2. **看不出"我到底改了哪几项"**：只有顶栏一句「静音 · 自定义」，明细要悬浮才有；
3. **两套判定会打架**：`ProfileBinding` 自己写了一套"比哪几项"的逻辑，`ProfileInstance`
   又有一套，于是出现过「顶栏说纯预设、配置档表格说 3 项自定义」。

v1.7 把它变成**显式实例**：`settings.json → Profile`。

```jsonc
"Profile": {
  "Base": "静音",                 // 基线是谁（内置、只读）
  "Schema": 1,                    // 结构版本，便于迁移
  "SavedUtc": "2026-10-29T17:28:11+08:00",
  "Delta": { "Tceiling": 84, "Pl1": 30, "Pl2": 34 },   // 只有与基线不同的项
  "Curves": { },                                        // 曲线增量（紧凑串）
  "Baseline": { "Tceiling": 88, "FanMax": 55, ... }      // 保存时的基线快照，仅供比对
}
```

**重建规则（这是"基线可升级"的全部秘密）**：

```
启动 → 取当前版本的内置基线 Base → 逐项写回 → 再覆盖 Delta
```

于是：模型在新版本里把 PL2 倍率从 1.15 修到 1.20，**没被你改过的项**自动跟随；
**被你改过的项**仍然保持你的值。整份拷贝做不到这一点 —— 这也是为什么不要"另存为一份新配置"。

**锁定项（用户没有直接修改权限）**：这些不是策略选择，而是物理约束，永远不进 Delta：

| 项 | 基线 | 来源 |
|---|---|---|
| 安全线 | 95℃ | TJmax 100 − 5℃ 余量；只许下调。旧版 UI 允许填到 110℃，v1.7 收回到 ≤95，并在加载时把旧值校正 |
| TJmax | 100℃ | 芯片规格 |
| τ 可表示域 | 2 的幂 | 0x610 time 字段 log2 编码 |
| PL2/PL1 倍率上限 | 2.00× | Intel 建议 ≤1.25×，2.0× 为 τ 窗口不失温上限 |
| 睿频上限 | 芯片 0x1AD 原值 | 超过被硬件静默截断 |
| 热阻 R | 在线估计 | 功率预算 (上限−室温)/R 的分母 |

**自动接管项**：智能自动模式下 PL1/PL2/τ/EPP 每 3 秒由 `AutoCpuController` 重算下发，
用户在高级页填的值不参与下发 → 表格标「自动接管」，且不计入 Delta（否则会出现消不掉的「自定义」）。

**单一判定源**：`ProfileBinding.Overrides()` 现在直接取 `ProfileInstance.Rows()` 的 `IsOverride`，
顶栏 chip、策略页、标定页、配置档表格四处口径由构造保证一致。

自检：`ProfileInstance.SelfTest()` 8 组（纯预设零增量 / 手改记增量 / 重建保留增量 / 脏值被基线覆盖 /
往返一致 / 恢复基线 / 锁定项与标记 / 曲线序列化），`tplab selftest` 会跑。

### 14.10 进程负载归因（v1.8）：把温度换算成「谁在烧电」

温控闭环回答的是「该给多少功率」，不回答「这些功率是谁用掉的」。用户看到 96℃ 时
唯一能采取的行动是关掉某个程序，所以必须把功率**归因到进程**。

#### 一、为什么是「分摊」而不是「测量」

RAPL 只在**封装级**提供 `PKG_ENERGY_STATUS`（0x611），Intel 没有、也不打算提供进程级能耗计数器
（`RAPL_PERF_STATUS` 的 per-core 域连功耗都算不上，只能算 slice 能量，且不区分进程）。
所以「每进程功耗」在任何 Windows 工具里都是**推算**，区别只在于推算得是否可加、是否有物理依据。

采用的定义：

```
P_proc = P_pkg × (ΔCPU_time / (Δt × n_cores))
```

即「该进程占用的 CPU 时间份额 × 整机包功率」。三条性质：

1. **可加**：份额之和 = 整机 CPU 使用率，所以 `ΣP_proc ≈ P_pkg × 使用率 ≤ P_pkg`。
2. **差额有意义**：`P_pkg − ΣP_proc` 正好是空闲、核显、uncore 的部分 —— 界面写「分摊合计」，
   不写「总功耗」，就是为了不让人以为差额是漏算。
3. **单调**：进程多吃一份时间片，它就多分摊一份功率。这正是「它在导致升温」的因果方向。

不能用「聚合后再乘」：先按进程名合并、再乘一次包功率，会把同一份额算 N 遍。

#### 二、四个量的口径

| 量 | 来源 | 性质 | 已知偏差 |
|---|---|---|---|
| CPU% | `GetProcessTimes` 差分 / (Δt × 逻辑核数) | 实测 | 与任务管理器同口径（全核=100，单线程在 8 核机上是 12.5） |
| 功耗 W | 包功率 × CPU 份额 | **分摊估算** | 含 uncore 的近似；无 MSR 权限时为 0 |
| 内存 MB | `K32GetProcessMemoryInfo.WorkingSetSize` | 实测 | 同名进程重复计共享页，偏高 |
| 磁盘 MB/s | `GetProcessIoCounters` 读写字节差分 | 实测（逻辑 IO） | 缓存命中也计入，不是物理盘吞吐 |

进程 PID 会被复用，所以基线以 `(pid, creationTime)` 为键；creation 变了就当作新进程，
第一次差值记 0，避免出现「一个 4GB 的跳变」。

#### 三、为什么按进程名合并

Chrome / Edge / Electron 应用把一页拆成几十个进程，每个 2–5%。不合并时 top10 会被同一家的
子进程塞满，而「真正的大头」被摊薄到看不见分组，用户无法据此关掉任何东西。
合并后显示实例数，悬浮给出 PID 列表，兼顾「哪个程序」与「哪些进程」。

代价：内存列会重复计共享页（见上表），所以这一列只用于相对比较，不用于「还差多少内存」。

#### 四、排序：照用户指定的优先级，用颜色补漏

`功耗 → CPU → 内存 → IO`（逐级 ThenBy，稳定排序）。这个顺序的问题是：一个狂写盘却不吃
CPU 的进程（杀毒扫描、备份、Steam 校验）会沉到很后面。所以 UI 对 `IO ≥ 5MB/s` 或
`功耗 ≥ 2W` 的行标橙 —— **排序不动，但异常值不会被埋没**。这比加一个「排序方式」下拉框
更符合「界面要简洁」的约束。

#### 五、自检

`ProcessMonitor.SelfTest()` 5 组：功耗主序 / 平手时 CPU→内存→IO 的降级 / 同名合并（实例数、
PID、合计 CPU 与分摊功耗的数值校验）/ top N 截断 / 真实采样（首次只建基线返回空；
第二次各项在物理范围内：`ΣCPU ≤ 100×n×1.05`、`ΣP ≤ P_pkg×1.05`、无负值、行数 ≤ 10）。

`tplab procs` 是同一套代码的命令行出口；`--write` 先写 64MB 临时文件，用来证明 IO 列
真的在计数（开发期就是靠它抓到「IO 恒为 0」这类问题）。

### 14.11 平台能力矩阵（v1.9）：参数范围之外的第二层约束

`14.4` 的约束回答"这个值能多大"，但回答不了**"这台机器上这个旋钮存不存在"**。
两者是正交的两层：

| 层 | 问题 | 违反后果 | 代码 |
|---|---|---|---|
| 范围约束 | 值超了没有 | 烧硬件 / 寄存器未定义 | `ParamConstraints` |
| 能力约束 | 寄存器在不在 | 写不进去（或写进去被忽略） | `CpuCapabilities` |

真实世界里"不存在"的旋钮至少有五类：

1. **厂商不同**：AMD 没有 `0x610`(PL1/PL2/τ)、`0x773`(HWP EPP)、`0x1AD`(睿频倍率)、`0x150`(FIVR 偏移)。
   AMD 走 SMU 邮箱（PPT/TDC/EDC）、CPPC、PBO。本程序没实现 SMU 写入，所以这四项在 AMD 上判"不支持"。
2. **世代不同**：HWP(Speed Shift) 是 Skylake 起才有（`CPUID.06H:EAX[7]`）。Haswell 上 `0x773` 的 EPP 无意义。
3. **型号不同**：赛扬/奔腾/部分低压 U 没有睿频（`CPUID.06H:EAX[1]=0`），`0x1AD` 倍率表不存在。
4. **BIOS 锁定**：Plundervolt(CVE-2019-11157) 之后，11 代起移动端关闭了 FIVR 电压偏移；
   部分 OEM 还会把 `0x610` 整个 RAPL 域隐藏（读出 PL1=0）。
5. **权限不足**：非管理员 / 开 HVCI / 驱动加载失败 —— 这**不是**"不支持"，是"暂时拿不到"。

#### 三态，而不是布尔

```csharp
enum CapState { Supported, Unsupported, NeedsPrerequisite, Unknown }
```

把第 5 类当成 `Unsupported` 会造成很糟糕的体验：用户提权回来发现参数被清空了，还得重填一遍。
所以只有**平台层面就不存在**（1–4 类）才 `Unsupported` —— UI 禁用 + 配置清值；
第 5 类是 `NeedsPrerequisite` —— UI 可编辑，但校验面板明确写出缺什么。
`Unknown` 是引擎还没起、`0x610` 还没读过时的状态，一律不做判断。

#### 探测分两段

```
① CPUID(leaf 0/1/6) + WMI  →  厂商 / family / model / 睿频 / HWP      （无需权限，启动即可）
② MSR 实测(0x610/0x773/0x1AD 读回值是否合理)                          （引擎启动后，Ring0 就绪）
```

第二段很重要：`0x773` 能读不代表能写，`0x610` 能读但 PL1 字段为 0 说明 BIOS 把 RAPL 域关了。
所以判 `Supported` 的条件是"读得到且值合理"，判完还要靠写入后的回读校验兜底。

#### 不清值会出什么事

配置是**跨机器**的（换机、重装、公司下发）。一份 `EPP=128 / PL1=35` 的配置落到 AMD 机器上，
如果只在 UI 禁用而不清值，这些值会一路流到写入层，最后变成几条"写入失败"的红字 ——
用户完全看不出那是"硬件没有这个寄存器"。

但清值**只能发生在"即将写硬件"的边界**，不能顺手塞进 `ControlChannels.Normalize()`：

```
写硬件边界（清值 OK）                   纯数据路径（绝不能清值）
· ParameterCenter 构造 / Apply / ForceCommit   · ProfileInstance.ApplyTo（基线重建）
· ThermalEngine.Start / ApplyConfig            · ProfileInstance.ResetToBaseline
                                               · 自检 / 单元测试
```

v1.9 开发时就踩过这个坑：把 `Sanitize` 塞进 `Normalize` 后，`ApplyTo()` 末尾那次 `Normalize`
会把"从配置档重建基线"的结果当成运行时配置清洗掉 —— 于是**开机加载就把用户的 EPP/τ 抹平并落盘**。
根因是把"结构归一化"和"运行时能力"混成了一层。现在拆开：
`ControlChannels.ApplyCapabilityLimits()` 只在那四个边界被显式调用，
`AllMsrUnsupported` 时连控制通道一起退回 `powercfg`。

反过来，**`NeedsPrerequisite` 绝不清值**：那是"现在写不了"，不是"这台机器不行"。

#### UI 的禁用规则

| 状态 | 控件 | 说明位置 |
|---|---|---|
| `Supported` | 可编辑 | — |
| `Unsupported` | `IsEnabled=false` | 能力框 + 控件悬浮提示（`ToolTipService.ShowOnDisabled`） |
| `NeedsPrerequisite` | 可编辑 | 校验面板 Info 行："当前不可用：…" |
| `Unknown` | 可编辑 | 能力框标"未探测" |

高级页顶部那条能力带是唯一出处：`本机 CPU：<型号>` + `PL1/PL2 ✓ EPP ✓ 睿频 ✓ 降压 ✗`。
逐项原因进悬浮，不铺满屏幕（延续 `14.8` 的分层原则）。

#### 自检

`CpuCapabilities.SelfTest()` 8 组，全部用 `Synthetic()` 注入伪造平台，不依赖真机：

- AMD：四项 MSR 全 `Unsupported`、电源计划仍 `Supported`、配置被清空且通道退回 `powercfg`；
- 无睿频 CPU：只有睿频项不支持，PL/EPP 不受影响；
- 无 HWP CPU：EPP 不支持、PL 仍支持；
- 非管理员：`NeedsPrerequisite`，**不清值**（提权后仍生效）；
- 未探测：`Unknown`，不清值；
- 11 代移动端：降压判不支持（Plundervolt 后 FIVR 关闭）；
- 状态互斥：`Hard` 与 `Usable` 不能同时为真；
- 真机：静态部分至少能识别厂商与型号。

界面侧另有 `--smoke-caps=amd|noturbo|nohwp|needadmin`，
把能力快照替换成伪造平台后截图核对"禁用"是否真的发生 —— 真机上没法把 CPU 换掉。

### 14.12 EC 是共享总线：风扇写入必须节流（v1.9.1）

#### 事故

用户反馈「电池检测不到了」。查证的顺序与结论：

```
事件日志 System / ACPI / Id=13
  「在指定的超时期限内，嵌入式控制器(EC)未响应」
  10-27 全天     0 条   ← 当天 0 次 NBFC 写 EC
  10-28 19h      2 条   ← 当天 3790 次 NBFC 写
  10-29 15~19h   11 条  ← 当天 2384 次 NBFC 写，每小时都有
```

对应日志里的写入节奏：

```
18:15:01.405  NBFC 已设置 51% → 寄存器值 100
18:15:02.308  NBFC 已设置 58% → 寄存器值 115
18:15:03.373  NBFC 已设置 75% → 寄存器值 148
...
```

即 **1 Hz 连续写 EC**。而电池电量和是否插电**也是经同一条 EC 上报的**（`Win32_Battery`
最终落到 ACPI `PNP0C0A` 的 `_BST` 方法，读的就是 EC）。EC 单总线一次只服务一个 owner，
被 WinRing0 频繁抢占时 ACPI EC 驱动超时，电源驱动读不到电池 → 系统报「检测不到电池」。
**电池本身没坏**：事后 `Win32_Battery` 仍返回 `Primary / 97% / 充电中`，PnP 设备状态 OK。

#### 根因不是"写 EC"，而是"写得不设防"

旧逻辑只有一道闸：`|next − 已下发| ≥ 1%`。采样 1 s、升速斜率 60%/s 时，目标值每跳一下
就会写一次；温度在回差附近抖动时更是每秒一次。而每次 `nbfc set -s N` 都要
**新起一个进程 + 一次 EC 事务**，这在这个量级上已经不是"控制"，是"压测 EC"。

#### 修法：两道闸 + 退避

```
时间闸   ：距上次写 EC < FanWriteMinIntervalMs（默认 3000 ms）→ 直接跳过
死区闸   ：目标变化 < 2%（应急 1%）→ 不写
去重     ：映射后的寄存器值没变 → 不写
退避     ：连续失败 3 次 → 暂停 30 s（EC 已经在挣扎时不要再压）
应急旁路 ：target ≥ 99.5% 或 temp ≥ 安全线 → 跳过时间闸（force）
```

参数提到配置里（`FanWriteMinIntervalMs`，1000–10000，默认 3000），高级页 ③ 卡片可调。
选 3 s 的依据：本机 `τ_hs ≈ 130 s`，1 s 级功率突增的温度响应由 die 侧（秒级）主导，
3 s 一次足以跟上；而 EC 事务频率从 1 Hz 降到 0.33 Hz，实测 EC 超时消失。

#### 启动自检与诊断

- `ThermalEngine.Start()`：若近 10 分钟有 EC 超时，自动把间隔抬到 ≥5 s 并在启动提示里说出来
  （很多人是通过"电池不见了"才发现问题的，必须显式告知）。
- 诊断页新增「EC 访问健康」：直接查系统事件日志 ACPI 13 的条数，0 = 通过，≤2 = 警告，>2 = 失败。
- 命令行同一套：`tplab ec`。

#### 这类问题的通用教训

**凡是"直写硬件共享外设"的功能，都要先问：还有谁在用它？**
风扇、电池、键盘背光、指示灯在笔记本上几乎都挂在同一个 EC 后面，
把一个通道当成独占总线来用，代价会由完全不相干的子系统付账。

### 14.13 指标口径修正（v1.9.2）：为什么"预测 238℃"是错的

用户换霍尼韦尔相变片后反馈：体感很好（NFS 10 稳 60FPS、CPU <80℃、GPU ~60℃、噪声温和），
但程序显示的指标"离谱、解释不通"。

#### 一、先把真实数据解出来

用 10-30 11:05 的标定 CSV（465 点）分组：

| 阶段 | n | T 均 | P 均 | 负载 | 风扇 | 备注 |
|---|---|---|---|---|---|---|
| 空闲基线 | 40 | 40.8℃ | 6.1W | 1% | 25% | 单点除法会算出 2.76 K/W（假） |
| 满载·满上限 | 80 | 72.6℃ | 40.0W | 98% | 64% | 冷机刚起飞 |
| 满载·上限 70% | 80 | 77.1℃ | 40.6W | 99% | 71% | |
| 满载·上限 50% | 80 | 77.8℃ | 41.2W | 99% | 72% | PROCTHROTTLEMAX 无效（旧结论复现） |
| 满载·风扇 100% | 70 | 78.8℃ | 41.3W | 100% | 100% | 风扇加满只降 1℃级 |
| 冷却 | 45 | 53.9℃ | 10.3W | 7% | 40% | |

对满载段（负载 ≥35%、功率 ≥12W，380 点）做最小二乘：

```
T = 27.6℃ + 1.207 K/W × P    R² = 0.316
截距 27.6 = 室温 24 + 固定偏置 3.6（die/封装/uncore）
```

**R ≈ 1.2 K/W**，对应 85℃ 上限的可持续功率 `(85−27.6)/1.207 ≈ 47.6W`。
用户体感"很好"是有物理依据的：换片前 R≈1.8（40W→96℃），换片后同样 40W 只有 78℃。

R² 只有 0.32 不是拟合失败，而是**同一功率下温度还在随时间爬**（散热器热容，τ_hs≈130s），
这也是为什么"瞬时功率-温度"永远对不上：必须先声明是**瞬态**还是**稳态**。

#### 二、四个"离谱指标"的真因

| 现象 | 真因 | 修法 |
|---|---|---|
| 日志 `R≈2.67 / 3.27`、`预测 238℃/285℃` | 热阻用 `(T−T_amb)/P` **逐拍**更新，空闲时 P=6W、T=41℃ → 2.7~3.3，EMA 0.9 一分钟就把满载真值顶掉 | 新 `ThermalResistance`：只吃负载 ≥35%、P ≥12W、\|dT/dt\| ≤0.8℃/s 的准稳态样本，用 **ΔT/ΔP 斜率**（最小二乘）而不是单点除法；要求 ΔP ≥8W 且 ΔT ≥4℃ 的"激励"，单次变化限幅 ±20%；无激励时用带 5℃ 偏置的绝对式粗估并标"粗估" |
| 功率预算比实测小 20%+ | `(上限−室温)/(R + 0.30)` —— R 已经是"结到环境"的总热阻，再加 R2 是**重复计入** | 改为 `(上限−室温)/R`，未知时显示"待热阻估计"而不是塞 1.8 |
| 空闲时仪表盘"3.6GHz、负载 1%" | 主指标取的是 `IA32_PERF_STATUS` 的**请求倍频**（空闲仍停在最高档） | 主指标改 **有效频率 ΔAPERF/ΔMPERF**，副标题给瞬时倍频与上限；标题随之变"有效频率/瞬时" |
| 空闲被判"频率上限"、40W 被判"功率墙" | 判定顺序是 温度→功率→频率→空闲；且 `PERF_STATUS` 空闲也报满频 | 顺序改 温度→**频率上限（负载 ≥30% 才成立）**→功率→轻载→无。40W 时实测 3.41GHz = 全核上限 3.40GHz，正确结论是"已到顶，加功率无效"，不是"功率墙还能换性能" |

#### 三、控制律的两处实质修改

1. **温度可行性门**：旧版"余温 >4℃ 就 +3W"，冷机时余温 40℃ 于是一路抬到 80W（真稳态 120℃+）。
   现在每一步都换算：`T_ss = T_now + R·(PL1 − P_now)`，超上限就把 PL1 收到
   `P_cap = P_now + (ceiling − 1 − T_now)/R`，并在理由里写明"原 X W → 限到 Y W"。
2. **轻载不抬功率**：没有交付指标（退化路径）时，`load <30%` 的"偏冷"不能作为加功率的依据 ——
   旧版在冷却阶段就是这样把 PL1 抬回 80W 的。

预测口径也换了：`PredictedC` 用**增量式**（当前负载不变、把 PL1 抬到此值），
稳态绝对式 `PredictedSteadyC` 只在 R 可信时给。参数校验里"预测超温"在 R 不可信时降级为**警告**，
不再一条 238℃ 就把用户所有 PL1 改动 Block 掉。

#### 四、离线验证

新增两个命令，直接用历史采样验证，不用重压机器：

```
tplab fit    --csv samples-*.csv [--ambient 24] [--ceiling 85]   # 解 R / 截距 / R² / 分阶段均值
tplab replay --csv samples-*.csv [--ceiling 85] [--turbo 3400]   # 回放控制律，逐步打印判定与 PL1
```

本机回放结果：R 从 0.88（冷机首个满载点）逐步收敛到 **1.19 K/W**（与离线拟合 1.207 一致），
PL1 稳定在 35W 一带、判定为"频率上限（已顶全核 3.4GHz）→ 加功率无效，保持"。
修复前是 `R 2.67 / PL1 80W / 预测 238℃`。

#### 五、换散热之后必须做的一件事

点一次「① 智能自动 → 重估热阻」（或重启程序后跑 1–2 分钟满载）。
旧热阻会让控制器"以为机器还很热"：预算被压小、或者反过来把 PL1 抬到不该有的高度。

### 14.14 本机硬件常数：CPU 45W / GPU 75W / 3.8GHz（v1.9.3~v1.9.4）

用户先给 60W，随后更正为：这台 OMEN 15-ce 的 **CPU 45W、GPU 75W**，CPU 最高频率 3.8GHz。
三次纠正分别改掉了三处建模错误（60W 只存在了一天，直接按 45W 落定）。

#### 一、45W 是电气上限，而且它刚好落在散热能力之内

```
CPU 设计功耗（Intel 规格 / BIOS 出厂 PL1）   45W     ← PlatformPl1MaxW
PL2（BIOS 出厂 0x610 里是 56.25W）            56W     ← PlatformPl2MaxW
散热可持续功率（85℃ 上限，R=1.207）         47.6W    ← (85 − 27.6)/1.207
45W 的稳态温度                              27.6 + 1.207×45 ≈ 82℃
```

三个数字放在一起才有解释力：

- **45W < 47.6W**：电气上限比散热上限还低，所以这台机器**永远不会**因为撞 45W 而触到 85℃；
  实测 40W 时 78℃ 也印证了这一点（用户游戏时 CPU <80℃）。
- 也就是说：**再往上加功率在物理上就没得加了**——跑到 3.4GHz 全核只需要 41W 左右，
  45W 的额度对这款 CPU 已经足够。
- 旧版把 `maxW` 写死 **80W**（比设计上限高 78%），会给出"还能再加 30W"的错误建议。

PL2 取 BIOS 出厂值 56W：`τ` 只有几秒，但 VRM 与电池供电路径是同一套，短时也不免费。

#### 一之二、GPU 75W 与 CPU 共用散热（v1.9.4 补）

CPU 45W + GPU 75W = 120W 走同一套热管，而**热阻 R 是在 CPU 单负载下标定的**。
所以游戏时（GPU 75W）CPU 的可持续功率明显低于 `(上限−室温)/R` 的估算，这一点必须在诊断页讲清楚，
而不是让用户以为"预算 47W 就该给到 47W"。诊断页新增「整机热预算」一项：
GPU 功耗 >20W 时提示"GPU 正在吃散热，不要让 CPU PL1 顶到 45W"。

#### 二、3.8GHz 是单核，3.4GHz 才是全核 —— 0x1AD 解码错了

`IA32_TURBO_RATIO_LIMIT(0x1AD)` 每个字节是一个"活跃核数档位"，**从低到高是 1 核、2 核、3 核、4 核**：

```
本机 i7-7700HQ: 38 / 36 / 35 / 34   → 3.8 / 3.6 / 3.5 / 3.4 GHz
                ↑ 1核            ↑ 4核（全核满载的天花板）
```

旧代码取 `raw & 0xFF`（低字节 = 单核 38）并注释成"全核倍频"，于是：

- 判定"是否顶到频率上限"时拿 `3.41GHz` 和 `3.8GHz` 比 → 永远不成立；
- 满载 40W、3.41GHz（已经是全核上限）被判成"功率墙 → 还能升 PL1 换性能"；
- 界面把"睿频上限 38"当成整颗芯片的上限展示，用户看到 3.4 会以为没跑满。

修正：
- `CpuControlService.OneCoreRatio()` / `AllCoreRatio()` / `TurboTiers()` 显式解码；
- 判定频率墙用**全核档**（3.4GHz），并在依据里注明"单核上限 3.8GHz，四核满载到不了"；
- 手动「睿频上限」的约束值也用全核档 —— 因为写 0x1AD 时会把每一档都压到 `min(原值, 给定值)`，
  用户填 38 表示"单核也别超 3.8"，而芯片本身的约束是 34。

#### 三、界面上的呈现

- 高级页 ② 的睿频输入框提示：`×100MHz（0=不改；本机单核 38 / 全核 34）`
- PL1/PL2 提示：`W（0=不改，≤60）`
- ① 卡片执行器一行：`平台设计上限 60W，程序不会越过它`
- 诊断页 / 读数：`睿频 单核 38·全核 34（×100MHz）`

### 14.15 平台功率不是常数：能读就读，读不到才猜，随时可手填（v1.9.5）

§14.14 把本机两个常数（CPU 45W / GPU 75W）写进了代码。这对这一台机器是对的，
但它把"机器的电气属性"当成了"程序的产品参数"——换一台 15W 低压本或 65W 标压本，
PL1 的允许区间就全错了：要么把手脚绑死，要么允许用户写一个物理上不可能的值。

#### 一、哪些能真读到，哪些读不到

| 量 | 有没有标准来源 | 实际做法 | 本机实测 |
|---|---|---|---|
| CPU 设计功耗 | **有**：`MSR 0x614`(PKG_POWER_INFO) bits[14:0] = `thermal_spec_power`，单位 W | 直接读 MSR | 需管理员；非管理员落到型号表 |
| CPU 的 BIOS 配置 | 有：`MSR 0x610` PL1/PL2 | 作为第二顺位（可能被改过） | 45 / 56.25W |
| GPU 设计功耗 | **部分有**：NVML（`nvidia-smi`）的 `power.default_limit` / `power.max_limit` | 读 NVML | **全部 N/A** |
| GPU（Optimus 笔记本） | 没有：独显由 MUX 动态供电，PMIC 不暴露给 NVML | 型号表 + 手填 | GTX 1050 Ti → 75W |
| 任何 WMI 类 | **没有** | `Win32_Processor` 无 TDP 字段；`root\wmi` 里没有 TDP 类 | 已验证枚举 |

所以"完全自动"是不存在的：**CPU 可以真读，笔记本 GPU 基本只能猜或手填**。
程序的立场是——能读就用真值，读不到就说明白自己在猜，并且允许用户覆盖。

#### 二、优先级（写死在 `PlatformPower` 里，界面照抄）

```
CPU 设计功耗：MSR 0x614 → MSR 0x610 PL1 → 型号表 → 内置默认 45W
PL2 上限    ：BIOS 实际 PL2（0x610，若 > 1.25×派生）→ 1.25×CPU 设计功耗
GPU 设计功耗：NVML default/max limit → 型号表 → 内置默认 75W
覆盖层      ：用户手填（>0）永远优先于以上全部；0 = 交回自动
```

每一档都带 `PowerSource` 与 `Evidence`（"MSR 0x614 thermal_spec_power = 45W"这种原话），
界面第一行就显示来源徽章：`CPU 45W（型号表）· PL2 ≤ 56W · GPU 75W（型号表）`。
`Measured`（MSR/NVML/手填）为 false 时，下面单独一行橙色提示"不是本机实测"。

**为什么把 0x610 排在 0x614 之后**：0x610 是"当前生效值"，可能等于本程序上一轮写进去的数，
也可能被 ThrottleStop 之类改过；0x614 是 CPU 自己声明的规格值，不会被人改。
所以"规格值"优先，"当前配置"降级为参考。

#### 三、为什么要允许手填，而不是"全自动最省心"

四种必须手填的真实场景：

1. **AMD**：没有 0x614/0x610（走 SMU 邮箱），只能型号表或手填；
2. **cTDP 改装 / 换主板 / 换散热**：机器的电气能力已经不是出厂那个数；
3. **NVML 返回 N/A 的 Optimus 笔记本**（本机就是），型号表也可能没收录；
4. **探测失败**：驱动没装、服务被禁、非管理员且型号表未收录。

手填值不是"随便填"：`AbsoluteCpuMaxW=150` 是协议层硬边界，超过会被夹住；
写一个离谱的值（例如 150W）会被"预测稳态温度 > 安全线"直接 Block —— 两层防护。

#### 四、唯一事实源

`ParamConstraints.PlatformPl1MaxW/Pl2MaxW/GpuMaxW` 从 `const` 改成了**转发属性**，
指向 `PlatformPower` 的生效值。这样：

- `Specs`（Pl1/Pl2 的 Max）随设计功耗变，**用户改完立刻生效**（缓存键是设计功耗+PL2 上限）；
- 界面提示 `W（0=不改，PL1 ≤ 45）` 里的 45 也跟着变；
- 配置档表格里 PL1 那一行的"机理约束"文案同样动态；
- 支持报告新增「平台功率（上限来源）」段，排查时能直接看到"这个 45 是哪来的"。

一个实现细节值得记：`AutoCpuController.Update(maxW = ...)` 的默认参数**不能**用运行期属性，
C# 要求编译期常量。所以改成 `maxW = 0` 表示"用本机设计功耗"，在方法体内解析。

#### 五、自检

`PlatformPower.SelfTest()` 5 组：

- 型号表把 i7-7700HQ 识别为 45W、GTX 1050 Ti 识别为 75W；未知型号不得命中；
- 无 MSR 时来源必须是型号表或兜底（不能假装是 MSR 读出来的）；
- 手填 28W 必须覆盖一切，且 PL2 上限随之变成 35W；
- 手填 9999W 必须被夹到 150W；
- 配置改回 0（自动）后不得残留手填标记。

命令行：`tplab power`（看探测与来源）、`tplab power --set-cpu 28 --set-gpu 50`（验证覆盖）。

### 14.16 有效频率为什么会算出 7461MHz（v1.9.6）

用户截图：`CPU 有效频率 7461MHz`，副标题却是「瞬时倍频 3610MHz、负载 17%、9W」。
7461 / 2800 = 2.66×，而 i7-7700HQ 的物理上限是 3.8/2.8 = **1.36×** —— 这个数不可能存在。

四个错误叠在一起，任何一个单独都足以让它失真：

#### 一、把 64 位计数器截成 32 位再相减

`IA32_APERF/MPERF(0xE8/0xE7)` 是 64 位计数器，旧代码写成：

```csharp
ulong a = (uint)aperf, m = (uint)mperf;   // ← 只留低 32 位
ulong da = (uint)(a - _lastAperf[lp]);
```

APERF 在 3.6GHz 下每秒增 3.6e9，低 32 位（4.29e9）**1.19 秒就回绕一次**。
引擎 3 秒采一次样，等于每个窗口丢 2~3 圈；两个计数器速率不同、丢的圈数也不同，
比率就随机漂到 2 倍以上。算一下就很清楚：

```
dt=3s：APERF 增量 1.08e10 → 低 32 位回绕 2.51 次（丢 2 圈）
       MPERF 增量 8.40e9  → 低 32 位回绕 1.96 次（丢 1 圈）
       丢的圈数不同 → 比率不再是 1.286
```

修法：**全程 64 位无符号差值**（3.6GHz 下要 146 年才回绕）。

#### 二、绑核失败时照样记账，基线被跨核污染

`SetThreadAffinityMask` 失败返回 0，旧代码仍然把读到的值写进该核的基线数组。
于是下一轮变成「A 核的 APERF 减 B 核的 MPERF」。三个后果叠在一起：

- 线程池线程被调度到任意核，读到的根本不是目标核的计数器；
- 每轮轮转 `lp`，前后两次永远不是同一个核；
- 程序被限制亲和性时（任务管理器设过），按 `0..n-1` 绑核会全部失败。

修法：绑不上就**跳过该核**（不建基线、不参与求和）；枚举的是
`GetProcessAffinityMask` 给出的**允许核心位图**，不是 `0..ProcessorCount-1`。

#### 三、拿 MPERF 当分母，等于只统计"醒着的时间"

`MPERF` 只在 C0（核心活跃）里推进。所以 `基准频率 × ΔAPERF/ΔMPERF` 得到的是
**"C0 期间的平均频率"**，不是"这段时间的平均频率"。17% 负载、大部分时间在 C-state 时，
它会报 2.4GHz 甚至更高 —— 看起来像"没干活却跑得很高"。

修法：分母换成**实际经过的时间**：

```
有效频率 = ΔAPERF / Δt
```

这个定义的三个好处：

1. 物理意义直白：这段时间平均每秒交付了多少个时钟周期（与任务管理器同口径）；
2. 天然不会超过睿频上限（不需要额外夹）；
3. 基准频率退化为**交叉校验**角色 —— 即便注册表 `~MHz` 读错，结果也不会跟着错。

原来的比率作为辅助信息保留：`C0 内平均 = 基准频率 × ΔAPERF/ΔMPERF`。
两者一对比就能区分「被降频」和「只是没活干」——这正是控温要回答的问题。

#### 四、没有任何物理上限校验

旧代码只有一句 `effMhz is > 100 and < 8000`，而 7461 正好落在里面。
现在三道门，任何一道不过就**不显示数字**（UI 退回瞬时倍频并写明原因）：

```
窗口 ≥ 0.2s
ΔMPERF ≤ 基准频率 × Δt × 1.05      ← 计数器读数本身的交叉校验
30MHz ≤ ΔAPERF/Δt ≤ 最高频率 × 1.02  ← 物理上限
```

#### 五、验证

新增 `tplab perf`（现场连采两次、打印有效/C0 内/瞬时/包功率，并自检"是否超过单核 turbo"），
以及 `PerfMetrics.SelfTest()` 7 组：

| 用例 | 期望 |
|---|---|
| 3.4GHz 满载、窗口 3s（增量 1.02e10 > 2^32） | 算出 ≈3400MHz（同时证明 64 位差值正确）|
| **截图里的 7461MHz** | 判无效，理由必须是「超过芯片最高频率」|
| 1.2GHz 平均 | ≈1200MHz（墙钟平均，不是 C0 平均）|
| 深睡（ΔAPERF=5000） | 判无效 |
| ΔMPERF 超基准频率×窗口 | 判无效，理由含「MPERF」|
| 0.05s 窗口 | 判无效 |
| 单核 3.8GHz | 必须通过（不能把合法 turbo 判成错误）|

#### 六、这条经验的通用形式

**凡是"两个计数器相除"的指标，都要问三件事**：位宽够不够、两次读数是不是同一个源、
分母统计的时间窗和你要表达的口径是不是一回事。三处都错的时候，结果不会明显异常 ——
它只是变成一个"看起来很像真的"的错数（7461MHz 而不是 0 或 NaN），这比崩溃更难发现。

### 14.17 风扇数字不对：单位混用 + 只看退出码（v1.9.7）

用户反馈：**风扇声音明显变大，界面数值几乎不动。**

#### 一、先看现场，不猜

```
nbFC status -a
  Auto control enabled : True        ← 关键：仍由 NBFC 自动曲线控制
  Target fan speed     : 0.00        ← 我们的指令没有落地
  Current fan speed    : 112.69      ← 197 步里的 57%，不随任何手动写入变化
```

程序日志当天**一条 "NBFC 已设置" 都没有**。逐条实验后找到两个独立的单位错误：

| 实验 | 结果 | 说明 |
|---|---|---|
| `nbfc set -s 30` | `Target=30.00`、`Auto=False` | `-s` 收的是**百分比** |
| `nbfc set -s 79` | `Target=79.00` | 同上，不会被当步进 |
| `nbfc set -s 147` | **`Auto=True`、`Target=0.00`** | **越界值让 NBFC 静默退回自动曲线**，退出码仍是 0 |

#### 二、错误一：写入把百分比换成了步进

```csharp
// 旧代码（错）
int rawValue = (int)Math.Round(percent * WriteRange / 100.0);   // WriteRange=197
Run($"set -s {rawValue}");
```

`WriteRange` 来自 `Fan speed steps: 197`，那是 **EC 寄存器量程**，只对回读有意义。
`set -s` 要的是百分比，于是：

```
曲线给 45% → 发送 89  → NBFC 理解为 89%
曲线给 51% → 发送 100 → 边界
曲线给 75% → 发送 148 → 越界 → NBFC 静默切回自动曲线（Auto=True）
```

后果正好对上现象：**超过约 51% 时我们不但没接管，还把风扇交回给 NBFC 自动曲线**。
用户听到的"变大声"来自 NBFC/BIOS 的自动曲线，界面显示的是我们自己的目标值 ——
两者从这一刻起就没有关系了。

#### 三、错误二：回读又把百分比当步进

```csharp
// 旧代码（错）
s.TargetFanPct = tgt * 100.0 / span;     // 79 → 40%
```

`Target fan speed` 本来就是百分比，再除以 197 会得到 40%。所以就算写对了，
界面也只会显示"指令 75%、回读 40%"，看起来像"写进去了但没生效"。

#### 四、错误三：只认退出码，不认结果

`nbfc set` 的退出码是 0 并不代表风扇被接管（见上表的 147 那条）。
旧代码 `if (st.ok) return true`，于是"命令执行成功"被当成"控制生效"。

#### 五、修法

1. **写入传百分比**，`WriteRange` 只用于解释回读的 `Current`（EC 原始步进）；
2. **写完立刻回读校验**：必须 `Auto control=False` 且 `|Target−请求| ≤ 2%` 才算成功，
   否则带原因返回失败（并进 30 秒退避，避免压 EC）；
3. **界面只显示确认生效的值**：`AppliedFanPct` 只在 `LastWriteApplied=true` 时更新；
   失败时显示 `--` + 橙色原因（`未生效（目标 46%）：NBFC 未接管…`）；
4. **区分"节流跳过"与"失败"**：跳过时保持上一次已生效值、不动 `_fanOut`，下一拍重试；
5. 诊断页新增「NBFC 接管状态（写入是否真的生效）」，直接显示
   `Auto control / Target / EC 寄存器`，不再让用户靠听声音判断。

#### 六、`Current fan speed` 到底是什么

本机在 20% / 79% / 100% 三次写入后，它始终是 `112.69`（197 步的 57%）。
说明它既不是转速、也不是实际占空比，而是**EC 里某个寄存器当前的值**（NBFC 按配置里的
寄存器区间换算出来的）。所以：

- **不能**把它当"实测风扇"，旧版拿它做"风扇实测"卡片是这个误会的源头（v1.7 已删）；
- **能**作为诊断信息（`EC 寄存器=112.7/197 步`），但不足以证明控制生效；
- 真正能证明"我们接管了"的只有 `Auto control=False && Target≈请求`。

#### 七、验证

`NbfcBridge.SelfTest()` 3 组（真机抓的原始文本）：Target 79 必须解析成 79%（不是 40%）、
Auto=true 必须判为未接管、缺 `Fan steps` 字段时不能崩。
端到端：`tplab fan --set 40` → 回读 `Auto control=False · Target=40%`（修复前发的是 79）。

### 14.18 数值口径：为什么 GPU 比 OEM 工具高 9℃（v1.9.8）

用户把 OMEN Gaming Hub 和本程序并排截图：

| 指标 | 本程序 | OMEN Hub | 差 |
|---|---|---|---|
| CPU 温度 | 53.0℃ | 53℃ | 0 |
| GPU 温度 | **49.5℃** | **41℃** | **+8.5** |
| CPU 负载 | **25%** | **39%** | **−14** |
| GPU 负载 | 0% | 0% | 0 |

#### 一、GPU 温度：取到了 Hot Spot

`tplab sensors` 把现场摊开（真机数据）：

```
GpuNvidia/GTX 1050 Ti :: Temperature :: GPU Core     :: 42.0
GpuNvidia/GTX 1050 Ti :: Temperature :: GPU Hot Spot :: 51.0
```

旧代码是这么挑的：

```csharp
if (name.Contains("Core") || name.Contains("GPU"))     // ← "GPU Hot Spot" 也满足
    a.GpuTemp = Math.Max(a.GpuTemp, v);                 // ← 再取 max
```

于是"GPU 温度"报的是**热点**。热点是 die 上最热的一点，比核心高 8~12℃ 是正常物理现象，
不是传感器坏了 —— 但拿它当"GPU 温度"，就比所有 OEM 工具都高，看起来像程序在乱算。

修法：显式分层，主指标只认 `GPU Core`；`Hot Spot` 单独存字段，放在副标题与悬浮里作参考。

#### 二、CPU 温度：取到了 Core Max

本机同时有：

```
CPU Package 59     ← 与任务管理器/OEM 同口径（主指标）
Core Max    60     ← 最热单核
Core #1..#4 57/59/54/60
Distance to TjMax 43/41/46/40   ← 这是"距上限的余量"，不是温度！
```

旧代码 `if (Package || Tdie || Tctl || CoreMax) max(...)` 直接把 Core Max 也算进来，
显示的是最热单核（高 1~3℃）。另外 `Distance to TjMax` 会被塞进"候选"，
一旦 Package 缺失就会拿 43 当温度 —— 这次没有触发，但属于同一类错误，一并挡掉。

修法：`Package`（AMD 为 `Tdie`/`Tctl`）→ `Core Max` → 各核最大，三级回退，顺序固定；
`Distance to TjMax` 显式排除。

#### 三、CPU 负载：多个调用方把窗口压成了 200ms

`CpuUsageCounter` 是**有状态**的：每次 `Next()` 都重设基线并做 EMA。
但 `Read()` 会被多个地方按不同节奏调用（引擎 tick ≈1Hz、UI 刷新 ≈4~5Hz），
于是实际统计窗口被压到 200~250ms，再叠加 EMA 的滞后 —— 与任务管理器的 1 秒窗口
差十几个百分点，方向还不固定（升载时偏低、降载时偏高）。

修法：固定 **≥1 秒**窗口；窗口未到时直接返回上一次结果（不挪基线）。
同一份数据谁先读都一样，读数也与任务管理器同量级。

#### 四、内存占用（新增指标）

用 `GlobalMemoryStatusEx`：已用 = 总量 − 可用，与任务管理器"性能 → 内存"同一组数。
实测 `7.5 / 15.9 GB（47%）`，与 OEM 面板的 `7.6GB / 16GB（48%）` 一致。

不用监控库的 "Memory Used"：它可能是已提交/工作集/物理三种口径之一，彼此差很多，
与系统面板对不上时无法解释。

#### 五、仪表盘现在长这样

```
CPU 温度  Package        GPU 温度  Core
          悬浮：Package / 最热核心        悬浮：核心 / 热点
CPU 频率  有效（MSR 可用时）              内存占用  % + 已用/总量
风扇      下发占空比（已回读确认）
```

#### 六、新增 `tplab sensors`

"数值对不上"这类问题不该靠猜。这个命令一次列出：

1. 程序**实际采用**的每个值（含取的是哪个传感器）；
2. 全部温度传感器的原始值与名字（所以一眼能看出 Package/CoreMax/HotSpot 差多少）；
3. 每个值的口径说明。

本节的结论全部来自这条命令，而不是读代码推测。

#### 七、顺带修掉一个"永远不显示"的坑

有效频率的 MPERF 交叉校验原来卡 `≤ 基准×Δt×1.05`。如果主板把 P1 报得比实际低
（或注册表 `~MHz` 不准），这个门槛会让有效频率**永远**算不出来 —— 比不显示更糟。
现在放宽到 3×（只挡"明显不是计数器"的情况），偏差写进说明文字，不影响计算。

### 14.19 CPU 温度"突然跳一下"：读数毛刺，不是采样太频繁（v1.9.9）

现象：盯面板时 CPU 温度会**毫无征兆地跳高一截**，一秒后又掉回来；游戏里偶尔还能感到
一瞬间的卡顿（超温保护把 PL1 压到 10 W 又放开）。

#### 一、先看是不是采样太频繁 —— 不是

采样越慢只会**漏掉**尖峰，不会制造尖峰。1 s 采样对 500 ms 的突发已经有 50% 概率漏掉；
把间隔放到 2 s 只会让"偶发高点"更容易被最后一帧撞上，观感更糟。所以方向相反：
要看清突发应该**加密**采样，而不是放慢。

#### 二、真机数据里的毛刺长什么样

`lab-data/lab-deep1-20261028-191903.csv`（707 行，1 s 采样）逐拍分析：

| 统计 | 结果 |
|---|---|
| 孤立尖点（单拍偏离前后均值 ≥8℃） | **43 / 704 = 6.1%** |
| 单拍最大跳变 | **35.5℃** |
| 尖点处"按 R=1.21 本该需要的额外功率"（中位数） | **9.5 W** |
| 尖点处实测功率增量（中位数） | **−0.5 W** |

最极端的一次：

```
t=27.7s  47℃ → 68℃ → 47℃     功率 10.2W → 11.7W → 9.2W
t=30.6s  47℃ → 85℃ → 52℃     功率  9.2W → 15.4W → 14.5W
```

涨 38℃ 需要额外 31 W（38 ÷ 1.21），实测功率只动了 0.9 W。**物理上不成立。**
所以这些不是硅片在发热，是 DTS 读数偶发取到了非温度值（经 Ring0 读 MSR，多程序争用时
会读到别的域/未初始化值）。判据只有一条，且是物理的：**温度涨 X℃ 必须有 X/R 瓦的功率跟着**。

#### 三、危害：不是显示难看，是会误触发保护

`CriticalTempC = 95℃`。上面 85℃ 那次没踩线，但同批数据里还有 93℃、96℃、97℃ 的尖点 ——
随便一次踩到 95 就会走"超温保护"分支：PL1/PL2 压到 10/12 W、EPP=255、风扇 100%，
下一拍温度掉回来又恢复。用户体感就是**突然顿一下 + 风扇忽然狂转**。

#### 四、修法：显示和控制都走 5 点滑动中值

新增 `Core/TempFilter.cs`：

- 窗口 5、采样 1 s → 覆盖 5 s，天然免疫单点毛刺；
- 中值而不是平均：平均会把 85℃ 摊进后面几拍（47/85/52 → 61，之后 3 秒都偏高），
  中值直接丢掉异常点（→ 52）；
- 无效读数（≤1℃ 或 >125℃）**不入窗口**，避免 0 值把中值拉低；
- 窗口未满时取偏小的中位（count=2 取较小值），宁可晚一拍升温，也不让启动那一两拍漏刺。

真机 707 行回放：**尖点 43 → 5（6.1% → 0.7%）**，剩下的 5 个全是真实阶跃
（压测开始 43→93→97、掉载 96→58→66），不是毛刺。

代价与兜底：

| 影响面 | 代价 | 处理 |
|---|---|---|
| 显示 | 滞后 1~2 s | 无感 |
| 风扇（3 s 才写一次 EC） | 无 | — |
| PI / 热阻估计（τ_hs≈130 s） | 无 | — |
| 超温保护 | 响应推后 1~2 s | 加"原始值连续 2 拍越线"安全阀；原始单拍 ≥ 保护线+3℃ 立即保护 |

#### 五、数据仍然可追溯

- 界面大数字 = 滤波值；悬浮提示里给出"原始 xx℃ / 最热核心 xx℃"；
- CSV 新增 `CpuTempRawC` 列：`CpuTempC` 是滤波值，`CpuTempRawC` 是原始读数；
- `tplab tempcheck [--sec N]`：连续采样并**当场判定**每一次跳变属于"毛刺（功率不匹配）"
  还是"真实阶跃（功率同步）"。这是验证这类问题的唯一可靠方式 —— 不看单点值，看它有没有功率。

### 14.20 频率"对不上任务管理器"：三个频率口径的区分（v1.9.10）

用户把本程序与任务管理器并排：本程序 **1164 MHz**，任务管理器 **3.59 GHz**，负载 3%。
差 3 倍，看起来就是算错了。

#### 一、任务管理器的「速度」到底是哪个量

任务管理器「性能 → CPU → 速度」读的是 `\Processor Information\Processor Frequency` 计数器：

```
Processor Frequency = %Processor Performance × 最高频率
%Processor Performance = APERF / MPERF        ← 只在 C0（核心醒着）时两个计数器才推进
```

所以它是**「醒着时的平均频率」**，不是墙钟平均，也不是瞬时请求倍频。证据：
本机基准 2.81 GHz，显示 3.59 GHz → 比率 1.278；而 3.59/2.81 = 1.2776，
不是任何整数倍频档（34/35/36/38 × 100 MHz），只能是平均值。

`PerfMetrics` 早就算了这个量，只是名字叫 `C0Mhz`：

| 量 | 公式 | 含义 | 空闲 3% 负载时 |
|---|---|---|---|
| 有效频率 `EffectiveMhz` | `ΔAPERF / Δt` | 墙钟平均，**把休眠时间摊进分母** | 1164 MHz |
| 醒着频率 `C0Mhz` | `基准 × ΔAPERF/ΔMPERF` | 只在 C0 内统计 | ≈3590 MHz |
| 瞬时倍频 | MSR 0x198 当前倍频 | 内核请求的 P-state | 3610 MHz |

三个数都是对的，回答的问题不同。任务管理器给的是第二个。

#### 二、v1.9.6 为什么选了第一个

当时的目标是「不要出现 1% 负载 3.6GHz 这种看不懂的数」，于是把主指标换成有效频率。
副作用是：**它和任何系统自带工具都对不上**，用户每次并排看都会认为程序算错。
而且 1.9.6 的注释还把这个量与任务管理器写成"同口径"——那句话是错的，本版一并改正。

#### 三、本版口径

- **主数字 = 当前频率（`C0Mhz`）**，与任务管理器同口径 → 并排能对上；
- **副标题 = `有效 1164MHz · 轻载`** → 回答"实际交付了多少"，并保留限制度；
- **悬浮 = 三个口径全列** + 芯片档位（单核 3800 / 全核 3400），避免"3587 > 全核上限"的困惑；
- `tplab perf` 的 Detail 同时打印「有效 xx（墙钟平均）· 醒着 xx（与任务管理器同口径）」。

#### 四、判据（下次再遇到"对不上"先问这三句）

1. 这个数是**墙钟平均**、**C0 内平均**，还是**瞬时请求值**？
2. 分母里有没有算休眠时间？
3. 传感器的**统计窗口**多长（任务管理器约 1 s，本程序 3 s；只有窗口不同才正常差几个百分点）。
